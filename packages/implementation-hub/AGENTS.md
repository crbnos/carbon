# @carbon/implementation-hub

Implementation Hub, Personal Pages layout — onboarding blueprint, pure logic, server DB helpers, and presentational UI for company setup. The hub is one page per person: Carbon staff define each person's page in a JSON page file (`implementationMember`); a person without one sees an empty hub. See `EXTENDING.md`.

## Two layouts

- Carbon has two Implementation Hub layouts. `implementationHub.layout` (`implementationLayout`: `Company Plan`, `Personal Pages`) holds the one a company uses; the default is `Company Plan`, so every company enrolled before the column existed, and every company that enrolls itself, keeps it.
- Company Plan is the hub's 18 pages and sidebar: `@carbon/onboarding` and the ERP's `x+/get-started+/` routes. Keep both exactly as they are; this package never imports them.
- Personal Pages is this package and the ERP's `x+/implementation+/` routes, with the priority set page. The layout route's `handle.sidebar` (`ImplementationSidebar`) links them: Pages (My Page for a customer) and Priority Set, and for Carbon staff the hub's Settings page (enrolment and layout).
- Which hub a company gets is decided in one place: `usesPersonalPages(hub)` in the ERP's `modules/shared/shared.models.ts`. The nav item, the home card, the app shell's signals, the Personal Pages layout's redirect, the Settings page and the `/state` write guard all call it. A per-company rollout rule replaces it there.
- Both layouts read the same hub tables. A card ticks the same state key, with the same value, as the item's Company Plan page. So that a Company Plan company keeps exactly the hub it had, the `/x/implementation/state` action refuses every write the Company Plan hub reads (`changesCompanyPlanHub`, `logic/access.ts`) until the company uses Personal Pages; page files, assignments and priority set answers are written before a switch.
- Only Carbon staff (an internal email) with `update: "settings"` change the layout: the unpublished `setImplementationLayout` service function, from the hub's Settings page (`x+/implementation+/settings.tsx`, posting to `layout.tsx`). Enrolling from that page starts the company on Personal Pages.
- Routing: the Personal Pages layout sends the company's own people of a Company Plan company to `/x/get-started`. Staff reach Personal Pages in any company by its URL, to load pages before a switch and to reach Settings. The nav item follows the layout; the home page's summary card shows for Company Plan only. `/x/get-started` itself is unchanged, so a Personal Pages company's people can still open it by URL.

## Always

- **Use the three-export structure**: `@carbon/implementation-hub` (logic + types), `@carbon/implementation-hub/server` (DB helpers), `@carbon/implementation-hub/ui` (React components)
- **Follow Carbon service convention** — server functions take supabase client as first arg, return `{ data, error }` (never throw)
- **Keep logic pure and client-safe** — `src/logic/` contains visibility, timeline, board, guide, and overlay logic with no server deps
- **Use zustand for UI state** — `hubStore` manages the Implementation Hub's client-side state via `HubProvider`

## Ask First

- Modifying the `TEMPLATE_KEY` or `TEMPLATE_VERSION` constants (affects enrolled companies)
- Adding new DB tables or columns (needs migration + RLS)
- Changing the onboarding step ordering or visibility logic

## Never

- Import server-only modules (`@supabase/supabase-js`, DB client) from the client-safe barrel export
- Hardcode company-specific setup steps — use the template/content system

## Validation Commands

```bash
pnpm --filter @carbon/implementation-hub test        # vitest
pnpm --filter @carbon/implementation-hub typecheck   # tsc --noEmit
```

## Key Patterns

- **Content-driven**: `src/content/` defines the template blueprint (steps, sections, exclusions)
- **Template version 2**: `TEMPLATE_VERSION` (`src/content/index.ts`) is 2. Nothing completes from detected data: a person ticks every step, nested product steps included. Detection signals and setup counts are evidence only. Companies are enrolled by `@carbon/onboarding` (version 1); this package's `enrollImplementation` is not called by the ERP
- **Single write path**: `applyHubMutation(client, actor, action)` (`src/apply-mutation.ts`, exported from `@carbon/implementation-hub/server`) runs every hub mutation. The ERP's `/x/implementation/state` action calls it. The access decision is the pure `refusalFor(actor, action, row)`; RLS is the backstop. Each tick records `actor.source` (`customer`, `staff`, `mcp`) and clears its verification
- **Evidence**: `getSetupCounts(client, companyId)` (server) runs one head count per `ONBOARDING_COUNT_KEYS` entry (`src/logic/status.ts`); a failed read is null and listed in `unavailable`, never zero. `src/content/evidence.ts` maps Setup Map rows (`SETUP_ROW_EVIDENCE`) and nested product steps (`PRODUCT_STEP_EVIDENCE`) to count keys; views read `useCounts()` and render `EvidenceCount`, which shows to Carbon staff only and not while they preview the customer's view (`useShowsStaffDetail`), so a customer's card shows only its tick. Evidence never completes a step. The ERP caches the counts in redis (`getImplementationCounts`, `shared.service.ts`); `getHubStatus` returns progress and counts in one read
- **Access and enrolment**: `hubAccess(enrolled, isInternal)` (`logic/access.ts`) is the one rule. Carbon staff (`isInternalEmail`) reach the hub in every company they belong to, enrolled or not, and opening it creates nothing; the ERP's `x+/implementation+/_layout.tsx` gives an unenrolled hub the settings enrolment would create (`UNENROLLED_HUB`); staff open it by its URL until the company is enrolled. The company's own people reach the hub only once the company is enrolled (an `implementationHub` row): enrolment is when the hub becomes visible to them. Staff enrol from the hub's Settings page (Enroll company), which posts to `x+/implementation+/enroll.tsx` (staff need no settings permission there; everyone else needs `update: "settings"`). The hub tables reference `company`, not `implementationHub`, so pages and priority answers are written before enrolment; every other write waits for a Personal Pages hub (see Two layouts)
- **Per-person pages**: `implementationMember` holds one page file per person (`memberPageValidator`, `models.ts`). `logic/page.ts` builds the catalogue of placeable hub items (`buildPageCatalogue`), checks a page (`checkMemberPage`: schema, unknown items, duplicates) and resolves its cards (`resolveMemberPage`, `cardState`, `pageProgress`). A card placing a hub item ticks that item's existing state key; a custom card ticks `customCardKey(userId, key)`. Writes are the `setMemberPage` / `deleteMemberPage` intents, Carbon staff only. `ui/MemberPageView.tsx` renders the page; the ERP's `x+/implementation+/_index.tsx` adds the staff bar (view as, preview as customer, load, export, catalogue, remove). Its person picker lists everyone in the company, with their `employees` status (Active, Invited, Inactive; inactive sorts last and is muted), in three groups from `groupHubPeople`: Carbon users (by email, with or without a page), configured users (a page) and unconfigured users (no page); choosing someone without a page offers Set up page, which opens the load modal with `starterMemberPage` for them. The picker reads people through a `bypassRls` client, like the Employees screen: invites have no read policy, so the `employees` view reports an invited person as Inactive to the signed-in client. Anyone in the company can be given a page, whatever their status: an invited person's waits for their first sign-in, an inactive person's for a new invite. `setMemberPage` requires only that the person is an employee of the company. **Questions**: a page's question cards show as one numbered list above its sections (`splitPageQuestions`, `ui/PageQuestions.tsx`), in page order; a section left with no cards is dropped, and page progress still counts the questions. A question row may list `options` (and `multiple`): the list shows choice cards with Not sure (`QUESTION_NOT_SURE`, stored `?`, shown as a grey Not sure badge while the question stays open), otherwise a typed answer in a field that grows with its text. Answering is the `answerQuestion` intent (`logic/question.ts`: `answerQuestionPayload` checks the choices against the options): one write saves the answer and sets `check:question.<rowId>` to answered when there is a typed answer or a chosen option other than Not sure, and back to open otherwise; the hub store shows it at once (`optimisticAnswers`, released by `withPendingAnswers`). A card draws its lower panel only when it has something in it, and the row's source (`SourceBadge`: AI agent, handover, interview) shows to Carbon staff only, and not while they preview the customer's view
- **Editing a page in place**: Carbon staff see a person's page as `ui/MemberPageEditor.tsx` (`MemberPageView` switches to it when `useCanEdit()` and the app passes an `editor`), the Company Plan hub's pattern: text saved on blur (`EditableInput`), an Add control per section, a ⋮ menu per card, no drawer. It shows every section with all its cards, questions included (the read view lifts questions into one list). Page changes are the pure helpers in `logic/page-edit.ts` (`editPage`, `editSection`, `editCard`, `placeCard`, `removeCard`, `removeSection`, `moveCard`, `moveSection`, `moveCardToSection`, `newCustomKey`): a section left without cards goes with its last card, the page's only card and only section cannot be removed (null; Remove page removes the page), a custom card's key is made once from its title and kept. Each page change saves the whole page through `setMemberPage`; the ERP route saves on a fetcher of its own and shows the edited page until the save settles, then what the server kept, and toasts a refused save. A company item's own fields (its title cell, `PAGE_ROW_FIELDS`; a question's options and Pick several; a customization's status, type of work, estimate in days and the requirement it serves) are `updateRow`; a customization card shows its type of work where other cards show their group, the estimate beside the due date and the requirement it serves (`requirementChoices` lists the ones it can serve), and none of them until staff set them; Delete item is `deleteRow` with the card removed from the page. Add card offers a hub item from the catalogue not on the page, a custom card (title, text, link) or a new company item of any placeable collection (`PAGE_ROW_COLLECTIONS`): the new row and its card are one `addRow` with `place` (`{ page, target }`, `parsePlacement`), staff only, which inserts the row and then saves the page through the same check as `setMemberPage` (`saveMemberPage`); if the page then fails, the row stays and can be placed from the catalogue. **Preview as customer** (staff bar) sets a session cookie scoped to `/x/implementation` (`useImplementationPreview`, the Company Plan hub's mechanism): the layout's loader reads it, `previewing` hides the editor and the staff-only detail (`useShowsStaffDetail`: source chips), and the page reads as its person sees it
- **Priority sets**: which of 67 Carbon features (`content/priority-set.ts`, generated from markdown kept outside the repo; keys are stored) a company needs in category 0 (before go-live), 1, 2 or 3. `computePrioritySet` (`logic/priority-set.ts`) is the one computation, from a questionnaire's answers and staff overrides, starting blank (every company does; a stored `priority.start` = `defaults` starts from the usual categories); needs pull prerequisites forward. Answers are hub field values (`priority.start`, `priority.answer.<question>`, `priority.system.<row>`, `priority.systems.custom`, `priority.tools`, `priority.override.<feature>`) written only by the `setPriority` intent; `checkPriorityWrite` re-validates each write and `refusalFor` limits overrides to Carbon staff. Each answer also carries a companion field `priority.via.<answer key without priority.>` (`priorityViaKey`): `priorityFieldValues` (`apply-mutation.ts`) writes `assistant` when the actor's source is `mcp` and empty otherwise, so a later answer on the page clears the mark; the page tags marked answers "Entered by your AI assistant". A question may carry `why` and `learnMore` (docs.carbon.ms pages); the page shows them under Why it matters, closed by default. `ui/PrioritySetView.tsx` holds its parts: `PrioritySetProvider` (state, the pending writes, export) with `usePrioritySet`, `PrioritySetQuestions` (choice cards per question, `MultiChoiceCardGroup` for pick-all questions, a table for current tools) and `PrioritySetPanel` (the live set by category, then Maybe; a ⋮ Set Category… modal for Carbon staff). Today's tools (the systems question) is a list of tools (`priority.tools`, encoded by `encodeTools`), asked by function, with each tool's follow-up (areas, setup, plan, integration) at the end of the questionnaire; `priorityToolSupport` matches a named tool to `PRIORITY_TOOLS` (a staff note shown to Carbon staff only). The ERP route `x+/implementation+/priority-set.tsx` lays them out as a `DocumentPage` (questions in the column, the set in the side panel) at `/x/implementation/priority-set`, reached from a person's page by the `priority:questionnaire` card. The provider resends every unconfirmed write with each save, because the shared hub fetcher cancels a save in flight
- **Assignments**: one assignee per hub item in `implementationAssignment`, keyed by the item's status key: `task:<key>`, `flag:setup.<key or row id>`, or `row:<row id>` for a custom row (`rowItemKey`). Written by the `setAssignee` intent and read by `getHubStatus`; the per-person page shows none
- **Tests and the Lingui macro**: content modules mark copy with `msg` from `@lingui/core/macro`, a compile-time transform vitest does not run. `vitest.config.ts` aliases it to `test/lingui-macro.ts`, which builds the same `MessageDescriptor` with the source text as `message`, so tests import real content and assert on `descriptor.message`
- **Logic layer**: `src/logic/` — pure functions for visibility, timeline, board layout, guide flow, readiness (`planTasks`: the one task list every view counts progress from), the overdue cascade (`cascade.ts`, walking `content/dependencies.ts`), and `buildHubPlan` (`hub-plan.ts`, the plan `getHubStatus` returns)
- **UI primitives**: `src/ui/PageCardParts.tsx` (`CardStatus`, `PriorityProgress`, shared by the page and its editor); `src/ui/primitives/` — `PageHeader`, `StatusToggle`, `EditableInput`, `EvidenceCount` / `VerifiedBadge` / `SourceBadge` (`HubEvidence.tsx`), `LearnLink`, and the status tokens
- **Views**: `MemberPageView` (with `MemberPageEditor` for staff) and `MemberPageEmpty` (the hub), `OnboardingHubSummary` (the ERP home card). The 18 pages the per-person page replaced are recorded, with their user stories, outside the repo
