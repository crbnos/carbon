# @carbon/implementation-hub

Implementation Hub 2.0 — onboarding blueprint, pure logic, server DB helpers, and presentational UI for company setup. Implementation Hub 2.0 is one page per person: Carbon staff define each person's page in a JSON page file (`implementationMember`); in a company on 2.0, a person without one does not see the Implementation Hub at all. See `EXTENDING.md`.

## Two versions

- Carbon has two versions of the Implementation Hub. `implementationHub.hubVersion` (`implementationHubVersion`: `1.0`, `2.0`) holds the one a company uses; the default is `1.0`, so every company enrolled before the column existed, and every company that enrolls itself, keeps it. Staff text names both versions; the company's own people see only "Implementation Hub" (`implementationHub2Name`, `shared.models.ts`: nav, breadcrumb and sidebar).
- Implementation Hub 1.0 is the 18 pages and sidebar: `@carbon/onboarding` and the ERP's `x+/get-started+/` routes. Keep both exactly as they are; this package never imports them.
- Implementation Hub 2.0 is this package and the ERP's `x+/implementation+/` routes, with the priority set page. The layout route's `handle.sidebar` (`ImplementationSidebar`) links them: Pages (My Page for a customer) and Priority Set, and for Carbon staff the Implementation Hub Settings page (enrolment and version).
- Which version a company gets is decided in one place: `usesImplementationHub2(hub, enabled)` in the ERP's `modules/shared/shared.models.ts`. A company gets 2.0 only when the `implementation-hub-2` flag (`packages/env/src/flags.ts`, default off) is on for it and its version is 2.0; anything else gets 1.0, so taking a company out of the flag puts it back there with its pages kept. The flag is read on the server with the company alone (`implementationHub2Enabled`, `shared.service.ts`), so everyone in a company gets the same version; the app shell returns it beside the hub row (`implementationHub2Enabled`) for the nav item, the home card and 1.0's notice (`useImplementationNavItem.tsx`, `NewImplementationHubNotice.tsx`). The 2.0 layout's redirect, the Settings page, the `/state` write guard and the app shell's signals read it on the server. Rules name companies, never people or percentages. After the beta the flag is deleted and the `hubVersion` column alone decides.
- Both versions read the same hub tables. A card ticks the same state key, with the same value, as the item's 1.0 page. So that a company on 1.0 keeps exactly the Implementation Hub it had, the `/x/implementation/state` action refuses every write 1.0 reads (`changesImplementationHub1`, `logic/access.ts`) until the company uses 2.0; page files, the files on a page, assignments and priority set answers are written before a switch.
- Only Carbon staff (an internal email) with `"settings.company": "Edit"` change the version: the unpublished `setImplementationHubVersion` service function, from the Implementation Hub Settings page (`x+/implementation+/settings.tsx`, Version card, posting to `version.tsx`). It refuses 2.0 while the flag is off for the company, and the page disables that switch and says so. Enrolling from that page starts the company on 2.0 when the flag is on for it, and on 1.0 otherwise. While a company is not on 2.0, staff on its 2.0 pages see a notice naming the missing step: the flag, enrolment or the version switch.
- Routing: the 2.0 layout sends the company's own people of a 1.0 company to `/x/get-started`, and those of a 2.0 company without a page to the home page. Staff reach 2.0 in any company by its URL, to load pages before a switch and to reach Settings. The nav item follows the version; in a 2.0 company it, the reopen entry (Settings → Company) and 1.0's notice show only to Carbon staff and the people with a page (`implementationHub2Opens`, which the app shell computes with `hubAccess`); the home page's summary card shows for 1.0 only. `/x/get-started` itself is unchanged, so a 2.0 company's people can still open it by URL; the notice pointing to the new Implementation Hub shows there only to those who open it.

## Always

- **Use the three-export structure**: `@carbon/implementation-hub` (logic + types), `@carbon/implementation-hub/server` (DB helpers), `@carbon/implementation-hub/ui` (React components)
- **Follow Carbon service convention** — server functions take supabase client as first arg, return `{ data, error }` (never throw)
- **Keep logic pure and client-safe** — `src/logic/` contains visibility, timeline, board, guide, and overlay logic with no server deps
- **Use zustand for UI state** — `hubStore` manages the Implementation Hub's client-side state via `HubProvider`

## Ask First

- Modifying the `TEMPLATE_KEY` or `TEMPLATE_VERSION` constants (affects enrolled companies)
- Adding new DB tables or columns (needs migration + RLS)
- Changing the onboarding step ordering or visibility logic

## Never

- Import server-only modules (`@supabase/supabase-js`, DB client) from the client-safe barrel export
- Hardcode company-specific setup steps — use the template/content system

## Validation Commands

```bash
pnpm --filter @carbon/implementation-hub test        # vitest
pnpm --filter @carbon/implementation-hub typecheck   # tsc --noEmit
```

## Key Patterns

- **Content-driven**: `src/content/` defines the template blueprint (steps, sections, exclusions)
- **Template version 2**: `TEMPLATE_VERSION` (`src/content/index.ts`) is 2. Nothing completes from detected data: a person ticks every step, nested product steps included. Detection signals and setup counts are evidence only. Companies are enrolled by `@carbon/onboarding` (version 1); this package's `enrollImplementation` is not called by the ERP
- **Single write path**: `applyHubMutation(client, actor, action)` (`src/apply-mutation.ts`, exported from `@carbon/implementation-hub/server`) runs every hub mutation. The ERP's `/x/implementation/state` action calls it. The access decision is the pure `refusalFor(actor, action, row)`; RLS is the backstop. Each tick records `actor.source` (`customer`, `staff`, `mcp`) and clears its verification
- **Evidence**: `getSetupCounts(client, companyId)` (server) runs one head count per `ONBOARDING_COUNT_KEYS` entry (`src/logic/status.ts`); a failed read is null and listed in `unavailable`, never zero. `src/content/evidence.ts` maps Setup Map rows (`SETUP_ROW_EVIDENCE`) and nested product steps (`PRODUCT_STEP_EVIDENCE`) to count keys; views read `useCounts()` and render `EvidenceCount`, which shows to Carbon staff only and not while they preview the customer's view (`useShowsStaffDetail`), so a customer's card shows only its tick. Evidence never completes a step. The ERP caches the counts in redis (`getImplementationCounts`, `shared.service.ts`); `getHubStatus` returns progress and counts in one read
- **Access and enrolment**: `hubAccess({ isInternal, enrolled, usesHub2, hasPage })` (`logic/access.ts`) is the one rule, used by the 2.0 layout, the `/state` action and the app shell (`opensImplementationHub2` for the nav). Carbon staff (`isInternalEmail`) reach Implementation Hub 2.0 in every company they belong to, enrolled or not, and opening it creates nothing; the ERP's `x+/implementation+/_layout.tsx` gives an unenrolled hub the settings enrolment would create (`UNENROLLED_HUB`); staff open it by its URL until the company is enrolled. The company's own people reach it only once the company uses 2.0, and only with a page of their own (an `implementationMember` row): loading a person's page is what shows them the Implementation Hub. Anyone else is sent home before the layout reads any hub data, and the `/state` action refuses all of their writes. The app shell reads the person's page row only while the flag is on for the company, and never for staff; a person given a page sees the nav item on the shell's next load (at most five minutes, or a reload). Staff enrol in one click from three places, all posting to `x+/implementation+/enroll.tsx` (staff need no settings permission there; everyone else needs `"settings.company": "Edit"`): the Implementation Hub Settings page (Enroll company); the not-enrolled notice on the pages view (Enroll on Implementation Hub 2.0); and, when the `implementation-hub-2` flag is on for the company, the ERP home page's enrol card, which for Carbon staff enrols onto Implementation Hub 2.0 instead of 1.0 (`implementationHub2Enabled` on `ImplementationHubData`). An enrolment onto 2.0 emails no one, since no one but staff sees it until a page is loaded; an enrolment onto 1.0 emails the company's admins, as self-serve enrolment does. The notice and the home card send `redirectTo`, so staff land on the people's pages; the action redirects only on this origin. The hub tables reference `company`, not `implementationHub`, so pages and priority answers are written before enrolment; every other write waits for the company to be on 2.0 (see Two versions). Staff-only detail never reaches anyone else's browser: the layout loader gives the company's own people the rows and ticks through `rowsForCustomer` and `checkStatesForCustomer` (`logic/access.ts`), which drop where a row or tick came from and a customization's type of work, estimate and served requirement; staff get everything, and while previewing it is hidden on screen. RLS still lets any employee read these tables through the API, like Implementation Hub 1.0
- **Per-person pages**: `implementationMember` holds one page file per person (`memberPageValidator`, `models.ts`). `logic/page.ts` builds the catalogue of placeable hub items (`buildPageCatalogue`), checks a page (`checkMemberPage`: schema, unknown items, duplicates) and resolves its cards (`resolveMemberPage`, `cardState`, `pageProgress`, `pageOverdue`). A card placing a hub item ticks that item's existing state key; a custom card ticks `customCardKey(userId, key)`. Writes are the `setMemberPage` / `deleteMemberPage` intents, Carbon staff only. `ui/MemberPageView.tsx` renders the page; the ERP's `x+/implementation+/_index.tsx` adds the staff bar (view as, preview as the person, load, export, catalogue, remove). Its person picker lists everyone in the company, with their `employees` status (Active, Invited, Inactive; inactive sorts last and is muted), in three groups from `groupHubPeople`: Carbon users (by email, with or without a page), configured users (a page) and unconfigured users (no page). Beside each person whose page has something to tick it shows the page's progress pill and a red count of its open cards past their due date (`pageOverdue`, the rule a card's Overdue badge follows), so staff find late work without opening every page; choosing someone without a page offers Set up page, which opens the load modal with `starterMemberPage` for them. The load modal also guides drafting a page with Claude: Copy prompt puts `pageDraftPrompt` (`logic/page-prompt.ts`) on the clipboard, holding the person, the page format and rules, the company's priority set (category 0 and 1 features, each with the cards `FEATURE_CARDS` in `content/feature-cards.ts` suggests, then the set's markdown export) and every catalogue card; staff paste the answer back and load it through the usual check. `FEATURE_CARDS` keys on both sides are stored, and `page-prompt.test.ts` checks every one exists. The picker reads people through a `bypassRls` client, like the Employees screen: invites have no read policy, so the `employees` view reports an invited person as Inactive to the signed-in client. Anyone in the company can be given a page, whatever their status: an invited person's waits for their first sign-in, an inactive person's for a new invite. `setMemberPage` requires only that the person is an employee of the company. **One table**: the page shows its cards as one table in file order, a row per card (`ui/PageTable.tsx`: `PageTable`, `PageRow`, `PageCell`, `CardTitle`, shared with the editor); below the md breakpoint each row stacks into a block. Sections are not shown: the format keeps `sections` and the section helpers in `logic/page-edit.ts`, the views flatten them (`pageCards`) and the editor saves every card in the first section (`singleSection`). A row is answered or ticked in place (`RowAnswer`): a question with options takes a select (several: a multi-select), a typed question a one-line answer, every other card its To do / Done or scope toggle. A row with more than it shows (its details, a note, fields, a checklist, files, a file request, a long answer, links) is a button stretched over the row that opens the card in a modal (`PersonCardModal`), with the chevron as the hint; the controls in the row sit above it (`relative z-10`). A question marked Long answer (`longAnswer` on the row, only without options) is answered in the modal only. Page progress counts the questions like any card. **Card fields**: a card may carry `fields` (up to 20): a label with a value, or a label with `points`, a checklist its person ticks in the modal (`CardFieldsView`). A point's tick is a check state, `pointKey(userId, cardId, text)` (`logic/page-files.ts`), so rewording a point starts it unticked; `cardChecklists` and `checklistProgress` (`logic/page.ts`) read them. The person's Done toggle stays disabled until every point is ticked (`CardStatus`); Carbon staff mark it either way. **Files**: a card with `askForFile` takes files from its person; Carbon staff attach to any card. `ui/PageFiles.tsx` (`CardFiles`) lists a card's files, uploads and removes them through the `PageFiles` the app supplies (`MemberPageView` prop `files`). The ERP route stores each upload in the company's bucket under `<companyId>/implementation/<userId>/<folder>/<name>` (`pageFilePath`, `useFileUpload`), then records the batch with one `attachFile` (files are `implementationFile` rows: person, card, path, name, size), on a fetcher of its own; `removeFile` deletes the row and the `/state` action then removes the stored file. `attachFileRefusal` (`apply-mutation.ts`) lets a person attach only on their own page to a card that asks for a file; `attachedFileProblem` (`logic/page-files.ts`) refuses a path outside the person's folder, a type the page does not take (`PAGE_FILE_EXTENSIONS`: documents, images, spreadsheets, presentations, PDFs and CAD drawings; no archives or programs) and a file over 50 MB, the bucket's limit; `canRemovePageFile` lets a person remove only the files they attached. Files are not scanned for viruses: Carbon has no scanner. Like every company file, a page's files are readable by any employee of the company through the API; the app shows them only on their page. Removing a page leaves its files: loading a page for the person again shows them. A question row may list `options` (and `multiple`): the modal shows choice cards and the row a select, each with Not sure (`QUESTION_NOT_SURE`, stored `?`, which leaves the question open), otherwise a typed answer. Answering is the `answerQuestion` intent (`logic/question.ts`: `answerQuestionPayload` checks the choices against the options): one write saves the answer and sets `check:question.<rowId>` to answered when there is a typed answer or a chosen option other than Not sure, and back to open otherwise; the store shows it at once (`optimisticAnswers`, released by `withPendingAnswers`). The row's source (`SourceBadge`: AI agent, handover, interview) shows in the modal to Carbon staff only, and not while they preview the customer's view
- **Board**: Carbon staff switch the pages view to a board (`?view=board`, the staff bar's Board button; not while previewing): every card on every page in the company, in four columns from `buildPageBoard` (`logic/page-board.ts`): Overdue, due in the next two weeks, later or undated, and Done, each by due date. Only cards that can be done are on it (training and decisions have no done state; removed items are left out). `ui/PageBoard.tsx` renders it read only; a card opens its person's page, where it is ticked. There is no Gantt chart: cards carry one due date and no start date, duration or dependency.
- **Editing a page in place**: Carbon staff see a person's page as `ui/MemberPageEditor.tsx` (`MemberPageView` switches to it when `useCanEdit()` and the app passes an `editor`): the page title and introduction saved on blur (`EditableInput`), then one table, a row per card with a read-only summary (type and group, title and the first line of its details, `CardSummary`: a question's options and answer, a customization's estimate, the link, evidence, fields, checklists with their progress, files; the note, the due date, the status toggle and a ⋮ menu: Edit card, Move up, Move down, Remove from page, Delete item). A row opens the card in a modal (`CardEditModal`; its form is inside `ModalContent`, so it starts from the card on each open) that edits everything at once and saves on Save: title, details and link, a question's options, Pick several and Long answer, a customization's status, type of work, estimate and the requirement it serves, the note, the due date, the card's fields (`FieldsEditor`: values and checklists, up to 20), Ask for a file and the card's files. Its page fields are one `editCard` saved through the editor; its item fields one `updateRow`. Page changes are the pure helpers in `logic/page-edit.ts` (`editPage`, `editCard`, `cleanFields`, `placeCard`, `removeCard`, `moveCard`, `singleSection`, `findPageCard`, `newCustomKey`; the section helpers `editSection`, `removeSection`, `moveSection`, `moveCardToSection` stay for page files and are not used by the app): a custom card's key is made once from its title and kept. Each page change saves the whole page through `setMemberPage`; the ERP route saves on a fetcher of its own and shows the edited page until the save settles, then what the server kept, and toasts a refused save. A company item's own fields (its title cell, `PAGE_ROW_FIELDS`; a question's options and Pick several; a customization's status, type of work, estimate in days and the requirement it serves) are `updateRow`; a card that cannot be done (training, a requirement, an item removed from the Implementation Hub) takes no due date (`takesDueDate`): the editor offers none and the page shows none; a customization card shows its type of work where other cards show their group, the estimate beside the due date and the requirement it serves (`requirementChoices` lists the ones it can serve), and none of them until staff set them; Delete item is `deleteRow` with the card removed from the page. A card shows one of four types (`PAGE_CARD_TYPE`, `content/page.ts`): To-do, Question, Decision (in or out of scope) or Learn; the finer kinds (`PAGE_CARD_KIND_LABEL`) show only in the catalogue picker and its export, to tell apart cards with the same title. A to-do's toggle reads To do / Done whatever its kind. A customization's type of work, estimate and the requirement it serves show to staff only. Add card puts the card at the end of the page and offers five choices: a catalogue card not on the page, a To-do (a custom card: title, details, link), or a new company Question, Decision (a requirement row) or Customization; new objectives and setup, data and cutover rows are no longer offered (a to-do covers them), and rows made before still show and edit. The new row and its card are one `addRow` with `place` (`{ page, target }`, `parsePlacement`), staff only, which inserts the row and then saves the page through the same check as `setMemberPage` (`saveMemberPage`); if the page then fails, the row stays and can be placed from the catalogue. **Preview as** (staff bar; the person's first name, or "user" when they have none) sets a session cookie scoped to `/x/implementation` (`useImplementationPreview`, Implementation Hub 1.0's mechanism): the layout's loader reads it, `previewing` hides the editor and the staff-only detail (`useShowsStaffDetail`: source chips), and the page reads as its person sees it
- **Priority sets**: which of 67 Carbon features (`content/priority-set.ts`, generated from markdown kept outside the repo; keys are stored) a company needs in category 0 (before go-live), 1, 2 or 3. The set is the company's, answered by one person: the person whose page has the questionnaire's card (`PRIORITY_CARD`, `hasPriorityCard`, `prioritySetHolder` in `logic/page.ts`). A page with the card is refused while another person's page has it (`saveMemberPage`); `setPriority` from anyone but Carbon staff and that person is refused; the sidebar shows Priority Set to staff and that person only, and its route sends anyone else to their page. Staff answer it with anyone else in a workshop. Set up page puts the card on the starter page only while nobody has it. `computePrioritySet` (`logic/priority-set.ts`) is the one computation, from a questionnaire's answers and staff overrides, starting blank (every company does; a stored `priority.start` = `defaults` starts from the usual categories); needs pull prerequisites forward. Answers are hub field values (`priority.start`, `priority.answer.<question>`, `priority.system.<row>`, `priority.systems.custom`, `priority.tools`, `priority.override.<feature>`) written only by the `setPriority` intent; `checkPriorityWrite` re-validates each write, `refusalFor` limits overrides to Carbon staff, and `applyHubMutation` limits answers to staff and the assigned person. Each answer also carries a companion field `priority.via.<answer key without priority.>` (`priorityViaKey`): `priorityFieldValues` (`apply-mutation.ts`) writes `assistant` when the actor's source is `mcp` and empty otherwise, so a later answer on the page clears the mark; the page tags marked answers "Entered by your AI assistant". A question may carry `why` and `learnMore` (docs.carbon.ms pages); the page shows them under Why it matters, closed by default. `ui/PrioritySetView.tsx` holds its parts: `PrioritySetProvider` (state, the pending writes, export) with `usePrioritySet`, `PrioritySetQuestions` (choice cards per question, `MultiChoiceCardGroup` for pick-all questions, a table for current tools) and `PrioritySetPanel` (the live set by category, then Maybe; a ⋮ Set Category… modal for Carbon staff). Today's tools (the systems question) is a list of tools (`priority.tools`, encoded by `encodeTools`), asked by function, with each tool's follow-up (areas, setup, plan, integration) at the end of the questionnaire; `priorityToolSupport` matches a named tool to `PRIORITY_TOOLS` (a staff note shown to Carbon staff only). The ERP route `x+/implementation+/priority-set.tsx` lays them out as a `DocumentPage` (questions in the column, the set in the side panel) at `/x/implementation/priority-set`, reached from a person's page by the `priority:questionnaire` card. The provider resends every unconfirmed write with each save, because the shared hub fetcher cancels a save in flight
- **Assignments**: one assignee per hub item in `implementationAssignment`, keyed by the item's status key: `task:<key>`, `flag:setup.<key or row id>`, or `row:<row id>` for a custom row (`rowItemKey`). Written by the `setAssignee` intent and read by `getHubStatus`; the per-person page shows none
- **Tests and the Lingui macro**: content modules mark copy with `msg` from `@lingui/core/macro`, a compile-time transform vitest does not run. `vitest.config.ts` aliases it to `test/lingui-macro.ts`, which builds the same `MessageDescriptor` with the source text as `message`, so tests import real content and assert on `descriptor.message`
- **Logic layer**: `src/logic/` — pure functions for visibility, timeline, board layout, guide flow, readiness (`planTasks`: the one task list every view counts progress from), the overdue cascade (`cascade.ts`, walking `content/dependencies.ts`), and `buildHubPlan` (`hub-plan.ts`, the plan `getHubStatus` returns)
- **UI primitives**: `src/ui/PageCardParts.tsx` (`CardStatus`, `CardFieldsView`, `PriorityProgress`), `src/ui/PageTable.tsx` (the page table) and `src/ui/PageFiles.tsx` (`CardFiles`, `PageFiles`), shared by the page and its editor; `src/ui/primitives/` — `PageHeader`, `StatusToggle`, `EditableInput`, `EvidenceCount` / `VerifiedBadge` / `SourceBadge` (`HubEvidence.tsx`), `LearnLink`, and the status tokens
- **Views**: `MemberPageView` (with `MemberPageEditor` for staff) and `MemberPageEmpty` (a person with no page), `OnboardingHubSummary` (the ERP home card). The 18 pages the per-person page replaced are recorded, with their user stories, outside the repo
