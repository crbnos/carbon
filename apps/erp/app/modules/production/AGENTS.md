# Production Module

Work orders (jobs), scheduling, routings (operations), bill of materials, procedures, production events/quantities, maintenance dispatches/schedules, demand forecasting, and MRP integration.

## Key Domain Concepts

- **Job** — production work order. Statuses: Draft → Planned → Ready → In Progress → Paused → Completed → Closed → Cancelled. `isJobLocked(status)` returns true for Completed/Closed/Cancelled. MUST check before allowing edits.
- **Job Make Method** — a job's manufacturing method (BOM + routing). Root method has `parentMaterialId = null`; sub-assemblies nest via `parentMaterialId`. Created by the `get-method` edge function.
- **Job Operation** — routing step within a make method. `operationType` (shared enum): `Process`, `Assembly`, `Inspection` (in-house on a work center), or `Outside Processing` (subcontracted to a supplier process). Statuses: Todo → Ready → In Progress → Done. Ordered by `order` column.
- **Job Material** — BOM line within a make method. Each has a `methodType` (Pull from Inventory, Purchase to Order, Make to Order) that drives procurement.
- **Production Event** — time tracking (Labor/Machine/Setup) against an operation.
- **Production Quantity** — output recording (Production/Scrap/Rework) against an operation with optional `scrapReason`.
- **Procedure** — versioned work instructions linked to operations via `processId`. Statuses: Draft/Active/Archived.
- **Assembly Instructions** — 3D animated work instructions, available to all users. (Previously gated to Carbon-internal emails via `requireAssembliesInternal` / `useFlags().isInternal`; that gate was removed to ship publicly.) **Versioned** (Draft/Published/Archived) as **row-per-version**, not an in-place counter: sibling versions are grouped by a self-referential `assemblyInstruction.rootInstructionId` (NULL = "I am the root"; group root = `rootInstructionId ?? id`, siblings = `id = root OR rootInstructionId = root`). `copyAssemblyInstructionAsVersion` spins a new editable **Draft** as a perfect copy (`version = max+1`, deep-copies steps with `parentStepId` remapped + each step's materials/slides/tools). `activateAssemblyInstructionVersion` makes a version active: publishes it, **archives the prior Published sibling**, and repoints `jobOperation.assemblyInstructionId` from other group versions to it — but only for active operations (status ≠ Done/Canceled) on active jobs (`!isJobLocked`). Only Draft is editable; the header exposes a "Versions" switcher + Make Active / New Version. `updateAssemblyInstructionStatus` no longer bumps `version`. The **list** (`getAssemblyInstructions`) reads the `assemblyInstructions` **view** (not the base table): it collapses each group to its latest version (`WHERE version = MAX(version)` per `rootInstructionId ?? id`) and rolls every sibling into a `versions` jsonb array, mirroring the `procedures` view — the table shows a `Version N` subtitle on the name plus a "Versions" hover card. Migration `20260730153412_assembly-instructions-view.sql`.
- **Maintenance Dispatch** — reactive/scheduled repair for work centers with comments, events, items, and linked work centers.
- **Scheduling** — forecast-first finite scheduling run **IN-PROCESS in Node** via `runLocationSchedule` / `runExpediteWhatIf` from `@carbon/ee/planning` (the ERP app and `@carbon/jobs` call it directly — no edge cold-start/HTTP hop; the `schedule` Deno edge function was DELETED, and the engine now lives in `packages/ee/src/planning/scheduling/`). It regenerates a **whole LOCATION** in one deterministic FORWARD-ASAP pass (no backward JIT pass in placement, no `initial`/`reschedule` modes). Machine availability comes from a per-work-center ladder: `workCenter.alwaysOn` = 24×7 lights-out → explicit `workCenterShift` rows → the location's `shift` rows → a stock Mon–Fri 8h week; open maintenance dispatches flagged `takesWorkCenterOffline` subtract downtime from those windows. Work centers are finite (capacity 1 — one op at a time) AND, for ability-gated processes, qualified PEOPLE are finite: work only accumulates while a qualified employee is on shift (`employeeShift` ⋈ `shift`; no shift assignment = the job location's calendar) and not reserved elsewhere. Started ops net **remaining work** only — labor+machine scaled by `(1 − quantityComplete/operationQuantity)`, setup done once any `productionEvent` exists. Placements persist as `capacityReservation` rows (a materialized output: delete-by-job + bulk insert per run, `scenarioId IS NULL`; `WorkCenter` + `Employee` kinds — `OperatorPool` is read-tolerated legacy, never written); the run also writes `job.projectedCompletionAt` (forecast finish) and clears the job's schedule-outdated stamps. **Dual dates** (`20260818031629_dual-dates.sql`, spec `.ai/specs/2026-08-15-dual-dates-due-vs-projected.md`): every regen writes each op's forward projection — `startDate` (projected start day) + `jobOperation.projectedCompletionAt` (projected finish instant) — and DIFF-writes `jobOperation.dueDate` from a backward demand-anchored need-by pass (`computeNeedByDates`, `packages/ee/src/planning/scheduling/need-by-calculator.ts` — a pure pre-placement step: reverse-topo from `job.dueDate`, `operationLeadTime` + assembly lead times, day lengths from the work centers' real calendars). Targets NEVER floor placement; `manuallyScheduled` = a human owns the need-by (the pin is taken as-is, propagates upstream, and is never overwritten — pinned ops still place normally; the old frozen-window branch is gone). An op projected past its need-by gets an informational amber behind-target state (BOP rows, ops-board `ItemCard`, MES operation detail) — never per-op `hasConflict`; when the job is late, the cause sentence appends "First behind target: {op} (due X, projected Y)". `jobOperation.priority` = the per-work-center placement order (reservation start ascending) — one source of truth for dispatch order (there is no configurable dispatch-sequencing policy). **People assignments** (manning board, `peopleAssignment`) make a staffed station a TEAM: the station still runs ONE op at a time, but the whole team present is booked on that op together — labor is parallelized across the present people (two people halve the labor wall-clock; setup and machine time are never compressed). Gated ops team-book people∩qualified on their assigned dates, falling back to an any-qualified single-person relay — but the board is a COMMITMENT, not a soft preference: the fallback may only draw on true FLOATERS (people with NO board assignment anywhere in the horizon, via `assignmentsByEmployee.has(id)`). A person you have manned anywhere is spoken for and is never pulled to a station they weren't assigned to — so moving your only welder off a station makes that station's op an unschedulable placeholder (visible on the Forecast) rather than silently double-booking the welder or shoving the op onto an unmanned weekend. A blank board leaves every qualified person a floater ⇒ classic any-qualified fallback, unchanged. Ungated ops at a staffed station are manned the same way with machine-only fallback. **Require-staffing policy** (`location.requiresStaffing`, per-location, default off, edited on the Production settings page (Settings → Production → Scheduling)): when ON, the scheduler places work ONLY where an operator is manned — the gated floater fallback and the ungated machine-only fallback are both removed, EXCEPT lights-out (`workCenter.alwaysOn`) stations keep running unattended. An op with no manned coverage (and not lights-out) becomes an unschedulable placeholder, so work routes to the staffed work centers and unstaffed ones get nothing. Threaded through `provider.getLocationRequiresStaffing` + `getAlwaysOnWorkCenterIds` → `FiniteSchedulingContext.requiresStaffing` + `capacity.workCenter.alwaysOn`. `peopleAbsence` subtracts the person's availability for that date everywhere; `peopleAssignment.overtimeHours` lengthens the person's day (window extension) and `peopleAssignment.hours` splits deal the day out per station sequentially — all as pure window edits before allocation. A blank board changes nothing. To reschedule, call `notifyScheduleInputsChanged` (stamps jobs; the debounced wave regenerates the whole location) — never direct date writes. An expedite what-if (`expediteJobId`) re-runs the sim with one job first, simulate-only, and returns its projected completion.
- **Ability requirements** — resolved through the operation's PROCESS: `process.requiresAbility` → the ability linked 1:1 to the process (`ability.processId`) → **presence-based** `employeeAbility` qualification (a row exists ∧ not expired; no `active`/`trainingCompleted` gate). Gates both the scheduler's operator pools and MES operation start. There are no operation-level ability tables.

## Safety

### Always
- MUST use `recalculateJobRequirements` after changing job materials or operations — it recalculates quantities and costs.
- MUST use `notifyScheduleInputsChanged` to reschedule — it stamps affected jobs schedule-outdated and the debounced wave regenerates the whole location. Never write `jobOperation.startDate`/`projectedCompletionAt`/`dueDate` directly (the one sanctioned manual write is pinning a need-by via `updateJobOperationDueDate`).
- MUST check `isJobLocked(status)` before allowing edits — Completed/Closed/Cancelled jobs are locked.
- MUST scope queries by `companyId`; jobs are also scoped by `locationId`.
- MUST use `calculateJobPriority` for priority — it computes from deadline type and due date. Never set `job.priority` manually.

### Ask First
- Deleting jobs that have posted production events or inventory movements.
- Changing job status backwards (e.g., Completed → In Progress).
- Running MRP (`runMRP`) — it can create/modify planned orders system-wide.

### Never
- Directly modify `jobOperation.startDate`/`projectedCompletionAt` — engine-owned forward projections, rewritten every regen. `jobOperation.dueDate` is the engine-computed need-by target; the only manual write is a pin through `updateJobOperationDueDate` (sets `manuallyScheduled`, after which the engine never overwrites it).
- Delete job operations that have production events recorded against them.
- Set `job.priority` manually — it's calculated by `calculateJobPriority`.

## Key Data Model

| Table / View | Purpose |
|---|---|
| `job` / `jobs` (view) | Work order header: item, quantity, dates, status, priority |
| `jobMakeMethod` | Manufacturing method instance; tree via `parentMaterialId` |
| `jobOperation` | Routing step: process, times, work center, status, dual dates (`dueDate` = backward need-by target; `startDate` + `projectedCompletionAt` = forward projection) |
| `jobMaterial` | BOM line: item, quantity, methodType, unitCost |
| `jobOperationStep` / `jobOperationParameter` / `jobOperationTool` | Work instruction details on operations |
| `jobOperationDependency` | Operation sequencing dependencies |
| `capacityReservation` | Materialized finite-capacity slot allocations (delete-by-job + bulk insert per regen, `scenarioId IS NULL`; WorkCenter / Employee kinds — OperatorPool is read-tolerated legacy, never written). `isPlaceholder = true` rows are non-binding markers for ops the scheduler could NOT place (no qualified operator / no feasible slot); they surface the op on the Forecast but are excluded from the live snapshot (`getLiveReservations`) so they never hold capacity against other jobs |
| `peopleAssignment` / `peopleAbsence` | Manning board: person→work-center per date (optional shift; unique per person/day/shift) and person-out-for-date flags; consumed by the People page (`x+/priority+/people.tsx` — Board/Matrix/Capacity views via `?view=`; the route delegates to `ui/Schedule/People/` components: `PeopleHeader`, `PeopleBoard` + `PeopleCard` + `PeopleColumn`, `PeopleWeekBoard`, `PeopleMatrix`, `PeopleCapacity`, `PeopleHoursModal`, `OvertimeDialog`, `TimeOffDialog`, with the shift-hours/time ladders and shared types in `peopleShared.ts`; the Capacity view's demand/scheduled buckets come from `buildPeopleCapacityBuckets` in `peopleCapacity.server.ts`), the MES station default, and the scheduling engine |
| `workCenterShift` | Which shifts a work center operates (availability-ladder rung 1); empty = all shifts at the location. Owned by the resources module; the scheduler reads it. `workCenter.alwaysOn` (24×7) is the lights-out override |
| `jobOperationQueueTime` (view) | Ready → first productionEvent queue time (`jobOperation.readyAt` stamped by trigger) |
| `productionEvent` | Time tracking: type (Labor/Machine/Setup), start/end, employee |
| `productionQuantity` | Output: type (Production/Scrap/Rework), quantity, scrapReason |
| `procedure` / `procedureStep` / `procedureParameter` | Versioned work instructions |
| `assemblyInstruction` / `assemblyInstructionStep` | 3D model-based assembly instructions (Draft/Published/Archived); steps carry `componentNodeIds` + `motion`/`camera` JSON for the viewer, a `buildWave` INTEGER (the step's longest-path level in the planner's precedence DAG — steps sharing a wave have no ordering constraint and can be built in parallel by different people/stations; NULL for cycle-affected or hand-authored steps; informational, `sortOrder` still governs playback), and `warnings.needsSupport` (a part in the step tips once placed — center of mass outside the support polygon of the parts below it — likely needs a fixture or a second hand; shown as a "Hold" badge) AND the typed-step fields mirrored from `jobOperationStep` (`type` `procedureStepType`, tiptap `description` with derived `instructionText`, `required`, UoM/min/max, `listValues`) for eventual copy into job operations. `motion`/`camera` are authored directly in the 3D viewer (drag the red waypoint path → relative `linear`/`L` motion; "Set view" captures the camera pose), autosaved via `updateAssemblyStepMotion` / the `steps/motion/$stepId` route — separate from the step form's `upsertAssemblyInstructionStep` (which rewrites `title`/typed fields). There is no numeric motion editor. **Step camera is a discriminated union**: a manual `{position,target,fov}` pose (applied verbatim), OR a planner hint `{source:"plan",direction}` — a mesh-precise view DIRECTION the Rust planner bakes per step (`crates/planner/src/view.rs` `best_view_direction`: sight lines against the real triangles of everything installed earlier, so it sees a hollow enclosure's open top where the viewer's AABB scoring can't). The viewer applies the hint with LIVE framing — target, standing distance, frustum fit at the real viewport aspect (`fitFraming`, `@carbon/viewer`). `null` = fully live AABB framing (fallback for hand-edited steps / old plans). Generated steps carry the plan hint (the TS-side camera bake was removed); re-motion refreshes it but never clobbers a manual pose. Playback visibility is presence-based (`@carbon/viewer` `visualForComponent`): a component exists on the canvas only once its step has run; components no step installs render like future-step ones (hidden during playback, future-components toggle while paused). AABB fallback motions for `"none"`-motion steps consider only PRIOR-step components as obstacles and fade in when no collision-free path exists or when the component interpenetrates a present component (mated parts — sliders on rails, fasteners in bores — never get fabricated paths; the planner is the only authority for those) |
| `assemblyInstructionStepMaterial` | BOM parts consumed at a step (`stepId` → `itemId` + optional quantity; stored by itemId so links survive make-method re-versioning; picker limited to the item's make-method BOM; UNIQUE `(stepId, itemId)`). Auto-populated from `assemblyComponentMapping` via `syncAssemblyStepMaterialsFromMappings` — additive only (manual quantities/deletions survive), triggered on step generation, component add, mapping create, and "Match BOM" |
| `assemblyInstructionStepSlide` | Per-step reference slides (image XOR 3D model via `modelUploadId`, caption, `size`, `annotations` JSONB pins), mirroring `methodOperationStepSlide`; authored in the step editor's Details tab and copied to `jobOperationStepSlide` by the BOP sync / get-method. The former `assemblyInstructionStepRequirement` / `assemblyStandardNote` tables (fixtures/consumables/notes/media) were dropped — a step definition is parts + tools + slides |
| `assemblyInstructionStepTool` | Tools used at a step (`stepId` → `itemId` of a tool-type item + `quantity`, UNIQUE `(stepId, itemId)`) — `itemId` is the same target `jobOperationTool.toolId` references, so the BOP sync maps rows 1:1 |
| `assemblyComponentMapping` / `assemblyUnit` / `assemblyPlanJob` | Geometry↔BOM item mapping, authored planner units (model-scoped "plan as one component" overrides), and geometry-service plan/convert job tracking. Planning is LAZY — conversion does not chain a plan run; the first "Generate Steps" click (or an explicit re-plan) starts it, pre-creating a Queued `assemblyPlanJob` row the worker adopts via `planJobId`. The clicking tab polls and auto-generates the steps when the plan lands |
| `maintenanceDispatch` / `maintenanceSchedule` | Equipment maintenance tracking |
| `demandForecast` / `demandProjection` | Demand planning data |
| `scrapReason` / `maintenanceFailureMode` | Reference data for production and maintenance |

## Key Service Functions

- `convertSalesOrderLinesToJobs` — creates jobs from sales order Make to Order lines
- `getJob` / `getJobs` / `getJobMethodTree` / `getJobMethodTreeArray` — job reads with method hierarchy
- `getJobMaterialsWithQuantityOnHand` — BOM with on-hand for shortfall visibility
- `getJobMaterialShortfallByItem` — priority-adjusted shortfall calculation
- `getJobOrderStatusMap` — procurement status indicators per material
- `recalculateJobRequirements` / `recalculateJobOperationDependencies` — recalculation after changes (`recalculateJobOperationDependencies` resolves the job's location and runs the whole-location schedule regen in-process via `runLocationSchedule` from `@carbon/ee/planning`)
- `notifyScheduleInputsChanged(companyId, kind, reason, entityId?)` — thin emitter of `carbon/schedule.inputs.changed` (kinds: `ability`/`shift`/`employee-shift`/`work-center`/`location`/`reorder`/`people`); stamps affected jobs and the debounced replan wave regenerates each stale location
- `getJobPromiseDate` — promise date = `job.projectedCompletionAt` (forward-ASAP forecast finish), null before the first regen (no operation-date fallback — `jobOperation.dueDate` is the backward need-by target, so max(op.dueDate) would just echo the job due date); returns the §7 `{ promiseDate, basis: "schedule", confidence }` contract (`confidence` "low" when the job has a conflicted op or a `scheduleOutdatedReason`, else "scheduled")
- `runMRP(client, db, params)` — triggers Material Requirements Planning **in-process** via `runMrp` from `@carbon/ee/planning`; the route action passes the Kysely handle (`getDatabaseClient()` from `~/services/database.server`) — it is NEVER constructed in this service file (which is bundled for the browser via the module barrel; enforced by the `no-db-client-in-service` conformance check). `recalculateJobOperationDependencies(client, db, params)` and `getJobExpediteForecast(client, db, …)` take the handle the same way. Formerly the `mrp` Deno edge function; preserves the `{ data, error }` shape
- `calculateJobPriority` — computes priority from deadline type and due date
- `getActiveJobOperationsByLocation` — schedule board data (RPC `get_active_job_operations_by_location`)
- `getPeopleAssignments` / `getPeopleAbsences` (single date) and `getPeopleAssignmentsRange` / `getPeopleAbsencesRange` (week) — people board/matrix reads; `upsertPeopleAssignment` (move semantics, optional partial-day `hours`) / `movePeopleAssignment` (station move with same-station merge, Kysely txn; returns `previousWorkCenterId` so `people.update.tsx` reschedules BOTH the source and destination work centers — otherwise the station the person LEFT keeps a stale booking) / `setPeopleAssignmentHours` (per-station hours; null = whole shift — lowering releases the remainder to the board's free-hours pool) / `setPeopleAssignmentOvertime` / `setPeopleOvertimeBulk` (one date or a `date`→`toDate` range — the board's Week horizon applies a whole week; optional department/shift scope, single UPDATE) / `deletePeopleAssignment` / `setPeopleAbsence` / `setPeopleAbsenceRange` (vacation as one action — a row per date, duplicates skipped) / `clearPeopleAbsence` / `copyPeopleBoard` (day; copies splits, not overtime) / `copyPeopleWeek` (whole Monday-start week, same skip rules) / `assignPeopleWeek` / `unassignPeopleWeek` / `movePeopleWeek` (week-basis manning for the Board's Week range: one row per working day from the shift's weekday flags, Mon–Fri fallback) / `setPeopleDay` (atomic reconciliation of a person's whole day — the `PeopleHoursModal` Working-hours editor's Save, also anchored on Matrix cells) — people mutations
- `getPeopleCapacityOperations` — open `jobOperation` hours for the Capacity view (excludes Done/Canceled ops and Draft/Planned/Completed/Cancelled/Closed jobs — released load only)
- `getCapacityReservationsForResources` — live reservations across jobs (resource timeline + Capacity view's Scheduled series)
- `getProductionPlanning` — MRP-driven production planning (RPC `get_production_planning`)
- `upsertMaintenanceDispatch` / `upsertMaintenanceSchedule` — maintenance management
- `getAssemblyInstruction(s)` / `upsertAssemblyInstructionStep` / `getAssemblyInstructionStepMaterials` — assembly instruction authoring; the step upsert derives `instructionText` from the tiptap `description` (viewer/MES consume the plain text)
- `getAssemblyInstructionVersions` / `copyAssemblyInstructionAsVersion` / `activateAssemblyInstructionVersion` — versioning (see the Assembly Instructions concept above). Routes: `x+/assembly+/$id.version.new.tsx` (copy → new Draft) and `x+/assembly+/$id.activate.tsx` (make active). Change-notice diffs of a `methodOperation` now surface its `assemblyInstructionId` (resolved to the instruction name), `inspectionDocumentId` (drawing/file name), and `operationType` via `stampOperationRefNames` + `ChangeNoticeDiffViewer` (items module)
- `updateAssemblyStepMotion` — partial `motion`/`camera` patch for one step, used by the 3D path/camera editor's autosave (never touches `title`/typed fields); `camera: null` clears the pose (return to auto-framing). Deleting an instruction also drops the model's cached plan via `deleteAssemblyInstruction` → `invalidateAssemblyPlanCache`
- `generateAssemblyStepsFromPlan` — plan.json → draft steps via `buildAssemblyStepGroups` (`@carbon/viewer`): sequence order, consecutive identical components merged, subassembly `groups` one step (titled by the unit `name`), `mergedInto` components riding their host's step; planner-flagged components (blockedBy / failed verification) store motion "none" + `warnings: { flagged, blockedBy }` (the viewer fades them in — no fabricated paths); a **floater fold** using the plan's `contacts` graph merges a placed-but-detached part with the immediately-following step that attaches to it (collision precedence forces the part in first, so it would otherwise render as a lone floating island for one step) — the pair installs as one rigid step along the detached part's motion; skipped on older plans lacking `contacts`; `mode: "regenerate"` replaces existing steps, refused while any step is `planConfidence: "manual"` or status `Done`. Persists a human `title` on every step via `describeStep` (`@carbon/viewer`) — real editable data, not just a render-time fallback. Seeds each step's materials from the component→BOM mappings (best-effort): auto-runs `autoMatchAssemblyComponents` once when the model has no mappings yet, and returns `unmappedComponentCount` (distinct geometry groups with no BOM item) which the generate route surfaces as a "use Match BOM" nudge
- `syncAssemblyStepMaterialsFromMappings` — adds mapped BOM items (`assemblyComponentMapping`) to steps' materials from their `componentNodeIds` (quantity = instance count in the step); additive + best-effort, never updates or removes rows; scopable by `stepIds` / `geometryHashes` / `onlyComponentNodeIds`. Called from the step-components autosave route (newly added nodes only), the mapping-create route (that hash only), and the "Match BOM" route (full backfill)
- `getAssemblyUnits` / `upsertAssemblyUnit` / `deleteAssemblyUnit` — model-scoped "plan as one component" overrides (`assemblyUnit`: `componentNodeIds[]` + optional `itemId`), authored from the BOM tree
- **Unit derivation**: the geometry planner itself auto-detects "detail swarms" — a populated PCB's hundreds of tiny components seated on a board — from pure geometry (`detect_swarm_units`, `crates/planner/src/pipeline2.rs`: a substantial host part + many tiny parts in narrowphase contact with it, each dwarfed by the host; fastener-named parts never join so screws keep their own animations). No BOM or LLM involved. The only TS-side unit source is the user-authored `assemblyUnit` rows ("plan as one component" from the BOM tree), which `loadPlanUnits` (`@carbon/jobs`) sends as `options.units`; the planner merges units for planning and expands them back to member leaves with a named `groups` entry (→ one titled step). Detected groups are ALSO materialized as `assemblyUnit` rows at step generation (`sourceGroupId` = the plan group id, e.g. `swarm:<hostNodeId>`; UNIQUE `(modelUploadId, sourceGroupId)`, upsert DO NOTHING so user renames/edits/deletions win within a plan — a regenerate re-materializes deleted ones) — the Components tab shows them like authored units with an "Auto" badge, and `loadPlanUnits` feeds them back to the planner as caller units so re-plans respect user edits. Flat multi-body STEP uploads (one PRODUCT, many solids, no assembly tree — the common Fusion/SolidWorks export shape) are split into per-solid components by the converter (`crates/occt-bridge` `read_step`), so they plan like proper assemblies instead of one un-plannable blob
- `getFlattenedBomMaterials` — the item's engineering BOM flattened through Make subassemblies; feeds the assembly BOM tree and the per-step material picker
- `syncAssemblyInstructionToOperation` — Assembly → job-operation re-sync (Kysely txn): copies an instruction's steps (any status) into a `jobOperation` as `jobOperationStep` rows (typed fields mirror 1:1), links per-step BOM parts via `jobMaterialStep` (itemId resolved against the operation's own `jobMaterial`), refreshes slides on synced steps (delete + recreate: the instruction's 3D model leads as a model slide at sortOrder 0, then the step's authored `assemblyInstructionStepSlide` rows), syncs tools (ensures a `jobOperationTool` per distinct tool item — never deleted, quantity only ratchets up — and rebuilds `jobOperationToolStep` links on synced steps), and sets `jobOperation.assemblyInstructionId`. Re-runnable via the `assemblyInstructionStepId` provenance marker (update matched / insert new / delete stale; hand-authored NULL-marker steps untouched; ON DELETE SET NULL demotes to hand-authored). Route `x+/assembly+/$id.sync-bop.tsx` (action-only, `production_update`, guarded to unlocked jobs); UI = "Sync Assembly Steps" on an Assembly operation in `JobBillOfProcess` (`AssemblyStepsSyncModal`), mirroring the "Sync Procedure" flow. **Method/quote operations only store the `assemblyInstructionId` pointer** — they never materialize steps; jobs inherit steps at get-method time (`insertAssemblyDataForJobOperation`, reading straight from the instruction) and re-sync on demand here. The MES assembly view uses the marker for **step-aware 3D playback**: `getAssemblyPlaybackByOperationId` (apps/mes operations.service) loads the linked instruction's GLB/graph/steps and `AssemblyView` mounts the `@carbon/viewer` `AssemblyPlayer` pinned to the operator's current step
