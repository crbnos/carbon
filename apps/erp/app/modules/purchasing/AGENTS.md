# Purchasing Module

Purchase orders, supplier management, supplier quotes/interactions, RFQs, procurement planning, and lessee leases (ASC 842). Handles the full procure-to-receive lifecycle including supplier approval workflows, quote finalization, and conversion to purchase orders.

## Key Domain Concepts

- **Purchase Order (PO)** — document sent to a supplier. Statuses (`purchaseOrderStatusType`, `purchasing.models.ts`): Draft → Planned (from a planning suggestion) → Needs Approval → To Review → To Receive → To Receive and Invoice → To Invoice → Completed, plus Rejected and Closed. MUST use `closePurchaseOrder` to close manually.
- **PO Revision** — `purchaseOrder.revisionId` counts amendments to a released order. Created ONLY when the header dropdown's "Create PO Revision" action posts `createRevision=true`; a plain Reopen never bumps. The write is `reopenPurchaseOrderAsRevision` (Kysely, `purchasing.service.ts`): a compare-and-swap that sets `revisionId = revisionId + 1` **in SQL** with the eligibility conditions (locked status + non-null `orderDate`) in the WHERE clause, so concurrent requests can't collide and an ineligible order matches 0 rows. `canCreatePurchaseOrderRevision` (`purchasing.models.ts`) is the matching pure predicate used to gate the menu item — keep the two in sync. Unlike quotes, a PO revision is in-place: no new row, receipts/invoices stay attached. Displayed as `PO000123-1` when > 0 via `getPurchaseOrderDisplayId` (`@carbon/documents/utils`) on the PDF, email, filenames, and UI; the two-tone in-app rendering uses `<RevisionSuffix>` (`~/components`).
- **Supplier Interaction** — umbrella entity linking a supplier quote to RFQs, POs, and documents. A supplier quote always lives under an interaction.
- **Supplier Quote** — vendor-side pricing with line-level price breaks (`supplierQuoteLinePrice`). Can be finalized (`finalizeSupplierQuote`) and converted to POs via the `convert` server function.
- **RFQ (Request for Quotation)** — solicits pricing from multiple suppliers. Links to supplier quotes via `purchasingRfqToSupplierQuote`. Statuses managed by `updatePurchasingRFQStatus`.
- **Conversion Factor** — when a supplier's UoM differs from stocking UoM, `conversionFactor` on `purchaseOrderLine` scales quantities at receipt: `inventoryQty = purchaseQty × conversionFactor`. See `.claude/rules/purchasing-conversion-factors.md`.
- **Purchasing Planning** — MRP-driven planned orders surfaced via `getPurchasingPlanning` (calls the `get_purchasing_planning_grid` RPC, which wraps `get_purchasing_planning` with the planning-horizon fence, first negative week, latest order date and the database-side action filters). Planning actions on PO lines are applied by `x+/purchasing+/planning.update.tsx` through `applyPurchasingPlanningActions(db, …)` — set-based, one Kysely transaction for the whole batch: the claim, one `UPDATE … FROM (VALUES …)` for the dates, one for the quantities (tax pair restated via `taxPairForQuantity`), one `DELETE` for the cancels (a Draft / Planned PO and nothing received or invoiced, in the statement), and the un-claim of refused rows (`planning-action-claims.ts`, shared with production). The drawer's inline edit of one line goes through `updatePurchaseOrderLineSchedule` (one Kysely UPDATE with the same Draft / Planned guard, returns `updated`). Planning changes a PO only while `isPurchaseOrderEditableFromPlanning` (Draft / Planned — not in approval, not sent). Ordering suggestions raises one PO per supplier per week (`planningPurchaseOrderWeek` + `findPlanningPurchaseOrder`, `purchasing.models.ts`), so each week's PO is finalized on its own and the later weeks stay editable from planning. An Increase / Decrease writes `quantityReceived` + the suggested quantity still to come (MRP reads a line's `quantityToReceive`), so a reopened, partly received line keeps its receipts. A row's ⋯ (expanded action lines and the drawer's Open Orders) carries the order's own commands from `usePurchaseOrderPlanningCommands` (`ui/Planning/`): **Reopen** / **Reopen as Revision** on a PO planning cannot change, posting `status=Planned` (+ `createRevision`) to the PO status route — Planned, NOT Draft, because Draft is not MRP supply (`openPurchaseOrderLines`) and a Draft PO's lines would be suggested again as a new order — and **Finalize** on a Draft / Planned PO, through `PurchaseOrderFinalizeModal` (now takes a `purchaseOrderId` prop) with its order + default CC from `api+/purchasing.purchase-order.$id.finalize.ts`.
- **Planning approval bypass** — `purchaseOrder.createdFromPlanning` (migration `20261006214907`) is set by the planning Order route on the POs it creates (and restored on planning POs it adds lines to). `upsertPurchaseOrderLine` / `deletePurchaseOrderLine` clear it BEFORE writing (`clearPlanningOrigin`), so any manual line change — PO page, API, MCP, kanban — sends the PO back through approval; planning's Apply and drawer edits (Kysely) never touch it. `$orderId.finalize.tsx` skips `isApprovalRequired` when the flag is set AND `companySettings.skipApprovalForPlanningPurchaseOrders` (default true, Settings → Planning → Purchase Order Approval) — failing closed on a read error.
- **Lease** — equipment or property the company leases FROM a supplier (the company is the lessee): a right-of-use asset and a lease liability on the books, payment rows the daily job turns into Draft purchase invoices, and a monthly schedule the lease run posts. See "Leases (sub-area)".
- **Reopen** — `purchase-order+/$orderId.status.tsx` treats a move to Draft OR Planned as a reopen (`PURCHASE_ORDER_REOPEN_STATUSES` / `isPurchaseOrderReopenStatus`): `purchasing_delete` from a locked status, pending approvals cancelled (from Needs Approval only by the requester or an approver), and an optional revision bump — `reopenPurchaseOrderAsRevision` takes the target status, `canCreatePurchaseOrderRevision` accepts either. A reopen to Planned skips the MRP run when the PO already was supply (Planned / To Receive / To Receive and Invoice).

## Safety

### Always
- MUST scope all queries by `companyId` — purchasing data is multi-tenant.
- MUST use the `convert` server function for supplier-quote → PO conversion — never hand-roll inserts.
- MUST preserve `conversionFactor` on PO lines when editing — it drives receipt quantity math.
- MUST use `finalizePurchaseOrder` / `finalizeSupplierQuote` for finalization — they enforce business rules.

### Ask First
- Changing PO status (approval/finalization workflows have business rules).
- Deleting suppliers or POs that may have linked receipts or invoices.

### Never
- Bypass the approval workflow by directly setting status to `To Receive`.
- Delete receipt lines that have already been posted to inventory.
- Directly INSERT into `purchaseOrder` — MUST use `insertPurchaseOrder` / `upsertPurchaseOrder`.

## Key Service Functions

- `getPurchaseOrder` / `getPurchaseOrders` / `getPurchaseOrderLines` — read POs
- `closePurchaseOrder` — marks a PO closed
- `shortClosePurchaseOrderLine` — Kysely transaction; sets a line's `receivedComplete` ("Stop/Resume Receiving") and recomputes the header status. Open-PO supply queries (`get_inventory_quantities`, `openPurchaseOrderLines`, `get_job_quantity_on_hand`) exclude `receivedComplete` lines, so short-closed remainders stop counting as incoming stock
- `convertSupplierQuoteToOrder` — calls the `convert` server function
- `duplicatePurchaseOrder` — copies a PO with new sequence
- `finalizePurchaseOrder` / `finalizeSupplierQuote` — lock documents for processing
- `sendSupplierQuote` — sends quote to supplier
- `getPurchasingPlanning` — MRP-driven planned order view (RPC `get_purchasing_planning_grid`)
- `applyPurchasingPlanningActions(db, { companyId, userId, actions })` — one Kysely transaction for a batch of planning actions on PO lines: the claim (Open → Actioned, returning each action's suggested quantity and date, which are what gets written), one `UPDATE … FROM (VALUES …)` for dates and one for quantities (`taxPairForQuantity` restates the tax pair), one `DELETE` for Cancels (Draft / Planned PO, nothing received or invoiced), then the refused claims are released. Returns `{ applied, alreadyApplied, refused, failed }`
- `updatePurchaseOrderLineSchedule(client, db, args)` — planning's single-line write (the order drawer's inline edit): `requiredDate` or `purchaseQuantity` on a line of a Draft / Planned PO, the guard inside the UPDATE; returns `{ updated, error }`
- `getSupplierApprovalContext` — reads approval workflow state
- `getPurchasingRFQ` / `getPurchasingRFQs` / `upsertPurchasingRFQ` — RFQ management
- `getSupplierQuotesForComparison` — side-by-side quote comparison
- `getDefaultAttachmentsForPO` — default document attachments for PO creation
- `getPurchaseReturnOrders` / `insertPurchaseReturnOrder` / `upsertPurchaseReturnOrderLine` — supplier-return CRUD; `confirmPurchaseReturnOrder` (Kysely row-locked caps: receiptLine received → PO line received×factor → invoice line×factor), `cancelPurchaseReturnOrder` / `completePurchaseReturnOrder` / `shortClosePurchaseReturnOrderLine`
- `getReturnableLinesForSupplier` (posted receipt lines minus already-authorized) — thin wrapper over the `get_returnable_receipt_lines` RPC, which does the `received − authorized > 0` filter, the search (receipt #, PO #, item readable id, item name), recency ordering, and limit/offset paging in SQL and returns `totalCount` on each row. Scales to thousands of receipt lines; the "Add lines from receipt" modal (`ReturnableReceiptLinesModal`) shows the 5 most recent and searches for the rest. / `getReturnableEntitiesForSupplier` (Available entities whose `attributes ->> Receipt` resolves to a posted receipt from the supplier) / `getReturnableEntitiesForReceiptLine` (Available entities from ONE receipt line, via `attributes ->> Receipt Line`) — the `$id.new` action uses it to auto-select the single entity when a tracked line is added from a specific receipt, persisting it at creation so it flows onto the shipment
- `createPurchaseReturnOrderCredit` (Kysely, shipped-minus-credited cap) / `getCreditableQuantitiesForPurchaseReturn` / `createReplacementPurchaseOrder` (linked-PO-line / supplierPart pricing)
- `createSupplierInteractionDocumentUploadUrl` / `createSupplierInteractionLineDocumentUploadUrl` — MCP file upload (step 1): presigned URLs for supplier-interaction (`supplier-interaction/{interactionId}`) and interaction-line documents; pair with `documents_insertUploadedDocument`. See `.claude/rules/mcp-tools-reference.md` → "File uploads"

## Leases (sub-area)

Lessee leases under ASC 842: the company leases an asset from a supplier. Spec `.ai/specs/2026-10-11-lessee-leases.md`. Lives inside this module: validators in `purchasing.models.ts` (`leaseValidator`, `leasePaymentValidator`, `leaseClassificationValidator`, `leaseModifyValidator`, `leaseTerminateValidator`, `leasePurchaseValidator`, the enum arrays `leaseStatuses` … `leasePaymentTypes`), reads and Draft writes in the "Leases" section of `purchasing.service.ts`, Kysely wrappers in `purchasing.server.ts`, UI in `ui/Leases/`, routes `x+/purchasing+/leases.tsx` (list, nav entry "Leases" in the `Manage` group of `usePurchasingSubmodules`) and `x+/lease+/` (`new` and `$id.setup.*` — the Draft setup wizard, see below —, `update` (one term at a time, Draft only), `$id.payments.*` (incl. `$id.payments.$paymentId.update`, one grid cell), the `$id` shell with `$id.details` / `$id.schedule` / `$id.events` for a lease past Draft, and the action routes `$id.activate`, `$id.classification`, `$id.invoice`, `$id.modify`, `$id.terminate`, `$id.purchase`, `$id.status` (intent `cancel`), `$id.delete`). Lifecycle math is pure in `packages/utils/src/lease-math.ts` (`@carbon/utils`: `generateLeasePayments`, `paymentMonthIndex`, `presentValueOfPayments`, `classifyLesseeLease` (the lessor's five tests via `classifyLessorLease`, plus the short-term election), `buildLesseeSchedule`, `remeasureLease`, `addMonths`, `leaseMonthEnds`), pinned by `lease-math.test.ts`. Schema: `20261011163133_lessee-lease-enums.sql`, `20261011163211_lessee-leases.sql`, `20261011192448_lessee-leases-rls.sql`, `20261011202305_lease-invoice-line-type.sql`.

RLS on the four lease tables: `purchasing_view` to read, `purchasing_*` to write (`company("purchasing", { read: "purchasing_view" })` in `packages/database/src/authz/manifest.ts`). The audit log entity `lease` covers `lease` + `leasePayment` (`audit.config.ts`).

- **Draft — the setup wizard.** A Draft is set up in the same wizard as contracts and rental agreements (`~/components/Setup`: `SetupFrame`, `SetupSteps`, `SetupBody` / `SetupSection`, `SetupFooter`, `TermForm`, `useCellSave`), steps `leaseSetupSteps` = Details → Payments → Accounting → Review (`ui/Leases/LeaseSetupSteps.tsx`, `path.to.leaseSetup(id, step)`). `new.tsx` renders step 1 (`LeaseDetailsForm`: Lessor, Leased Asset, Term, More Details; the payment and accounting terms ride along as hidden fields) and creates the Draft (`insertLease`, `leaseId` from the `lease` sequence, `discountRate` from `companySettings.leaseIncrementalBorrowingRate`), then redirects to `setup/payments`. `$id.setup.tsx` is the shell (refuses a non-Draft; Back / Next footer, Next disabled on Payments with no row; Review's footer has Save as Draft and Activate, gated by `leaseActivationGaps`, mirroring `activateBlocker`). `$id.setup.details` saves the details and cuts the rows again when a payment date changed. **Payments** (`LeasePaymentTerms` + `LeasePaymentsGrid`): each term saves on its own through `update.tsx` (`useLeaseTermSave`), and a payment-term change cuts the rows again with `regenerateLeasePayments` (`purchasing.server.ts`): one Kysely transaction that replaces EVERY row from `generateLeasePayments` (escalation on each anniversary, a short last period prorated by days, a Purchase Option row on `endDate` only when reasonably certain; a row due before `invoiceFromDate` is created `Skipped`, paid outside Carbon). The grid edits a row's period, due date and amount cell by cell (`$id.payments.$paymentId.update`, `upsertLeasePayment`); "Add Payment" and "Regenerate from Terms" stay. **Accounting** (`LeaseAccounting`): `LeaseClassificationPreview` live, with "Override" (`$id.classification`, `update: accounting`, Draft only, stores Operating or Finance with a reason, audit-logged), and the discount rate and classification inputs as `TermForm`s. **Review**: `LeaseSummary`, the gaps linked to their step, `LeaseCommencementPreview`. Opening a Draft (`$id._index`, `$id.details`) sends anyone with `update: purchasing` to its setup (`draftLeaseSetupPath`); a viewer sees the page. `insertLease` / `updateLease` (Draft only, refusal code `LEASE_NOT_DRAFT`) write only the picked `leaseTerms` (never status, classification or measurement; `invoiceFromDate` defaults to `commencementDate`).
- **Lifecycle** — the `post-lease` server function (`packages/server-functions/src/post-lease/`, permission `update: purchasing`, payload `{ type, leaseId, … }` in `validators.ts`). Each action is ONE Kysely transaction that locks the lease first (`lockLease`). Every action that posts needs the lessee account defaults plus the asset gain / loss on disposal defaults (`LESSEE_ACCOUNTS_REQUIRED`: "Set the lease (lessee) accounts in Accounting → Default Accounts before activating a lease"). All lessee journals are `sourceType 'Lease'`, lines `documentType 'Lease'` + `documentId` = the lease, with Supplier and Location dimensions (`postLesseeJournal`, `lease.ts`): Provisional before the accounting cutover, Posted after it. The journal-line builders are pure in `lessee.ts` (pinned by `lessee.test.ts`).
  - `activate` (`index.ts`): refuses a non-Draft lease, no payment rows ("A lease needs at least one payment row to activate") and a currency other than the base currency ("Leases in a foreign currency are not supported yet"). Classifies (`classifyLesseeLease` with `companySettings.leaseShortTermExpedient` and the shared `leaseMajorPartThresholdPercent` / `leaseSubstantiallyAllThresholdPercent`; an override wins), measures the liability at the PV of the payment rows, and stores the inputs. A **Short-Term** lease posts nothing and writes no schedule. Otherwise it posts `Lease Commencement LSE…` (Dr Right-of-Use Assets / Cr Lease Liabilities at the PV) and `writeSchedule` writes every lease month plus its `Interest` and `Amortization` run rows (`scheduleRowAccounts`: Operating books both rows' debit to Operating Lease Expense; Finance to Interest Expense – Leases and Amortization – Right-of-Use Assets; credits Lease Liabilities and Accumulated Amortization respectively). ROU amortization runs over the economic life when ownership transfers or the purchase option is reasonably certain, else the term (`amortizationMonths`).
  - **Commenced before the cutover** — when `commencementDate` < `companySettings.accountingCutoverDate`, `activate` posts `Lease Opening Balance LSE…` instead, dated the cutover (or the first open period after it, `resolveAccountingPeriod` `historical-with-shift`): Dr ROU at cost, Cr accumulated amortization and the carrying liability the schedule reaches on that date (`balancesBefore`), the difference to `retainedEarningsAccount` (`openingBalanceLines`; refuses without that default). Schedule rows before the date are written `Posted` with no journal.
  - `cancel`: a Draft is deleted. An Active lease is Cancelled only with no Invoiced payment, no run holding its rows (`heldByRun`) and no run-posted row; the commencement (or opening) journal is voided with a negated `VOID …` copy dated today (`voidLeaseJournal`), refused by `refuseVoidBeforeCutover` when that journal predates the cutover, and the schedule is deleted.
  - `modify` / `terminate` / `purchase` (`lifecycle.ts`) share `prepare`: an Active lease, a date on a lease-month boundary (Modify: the first day of a lease month; Terminate / Purchase: the last day), every run row before it Posted ("Post the lease run for … first"), no run holding a later row, no Invoiced payment due on or after it. Each records a `leaseEvent` and rewrites the schedule and Pending payments from the date; posted history never changes. **Modify** cuts the remaining payments again, remeasures (`remeasureLease`: the ROU moves with the liability; a decrease beyond the ROU is a gain), reassesses Operating / Finance over the remaining term (an override still wins), and posts `Lease Modification LSE…` when anything moved. A Short-Term lease cannot be extended past 12 months. **Terminate** deletes the Pending rows after the date (and any Purchase Option row), adds a `Termination Penalty` row, posts `Lease Termination LSE…` (liability and ROU off, the difference to `assetGainOnDisposalAccount` / `assetLossOnDisposalAccount`, which a Modify gain also credits) and sets `Terminated` + `endDate`. **Purchase** (Exercise Purchase Option; refused for Short-Term or with no `purchaseOptionAmount`) adds a `Purchase Option` row at the price, posts `Lease Purchase LSE…` (the asset class's asset account at net ROU + price − carrying liability, see `.claude/rules/fixed-asset-lifecycle.md`), inserts an **Active** `fixedAsset` of the chosen in-service class, and sets `Purchased` + `fixedAssetId`.
- **Invoicing** — the `create-lease-invoices` server function (`packages/server-functions/src/create-lease-invoices/`, `{ asOf, leaseId? }`, `update: purchasing` + `create: invoicing`): per lease that is Active, Expired, Terminated or Purchased with a Pending row due on or before `asOf`, ONE Draft `purchaseInvoice` per due date with one `Lease` line per row, the rows stamped `Invoiced` + `purchaseInvoiceLineId`. Each lease is its own transaction; a failure is returned in `failures`, never thrown. Called daily by the Inngest `recurring-billing` job and by "Invoice Now" (`$id.invoice.tsx` → `generateLeaseInvoicesNow`, Active leases only). The drafts stay Draft: the buyer adds the supplier's invoice number and posts. Posting a Lease line with a payment row debits Lease Liabilities (Operating Lease Expense for Short-Term); a Lease line added by hand (no payment row) is a variable charge to Variable Lease Expense. VOID returns the rows to Pending and stamps `voidedPurchaseInvoiceId`.
- **Deleting an invoice releases its rows** — `deletePurchaseInvoiceReleasingLeases` / `deletePurchaseInvoiceLineReleasingLeases` (`purchasing.server.ts`) delete a Draft purchase invoice (or one line) and return the billed rows to Pending in the same transaction (`releaseLeasePayments`). The purchase invoice delete routes call them; the MCP `invoicing_deletePurchaseInvoice` / `invoicing_deletePurchaseInvoiceLine` tools are blocked (`mcp-blocked-tools.ts`).
- **Reminders and expiry** — the same daily job notifies the owner (`assignee ?? createdBy`) and the company's `invoiceNotificationGroup` once per date (`LeaseCriticalDate`, `packages/jobs/src/invoicing/lease-reminders.ts` `dueLeaseReminders` + `stampLeaseReminders`) when `noticeDate` or `endDate` is within `companySettings.leaseReminderDays`, and expires (`expireLeases`) every Active lease past its `endDate` with every run row Posted and no Pending payment.

### Leases safety

- Never write `lease.status`, the classification, the measurement columns, `leaseScheduleLine` or the lease's `revenueRecognitionSchedule` rows from app code. Every lifecycle change goes through `post-lease`.
- Never delete a purchase invoice (or a line) that may carry Lease lines with a plain delete. `leasePayment.purchaseInvoiceLineId` has no FK, so the row stays Invoiced and is never billed again. Use the `*ReleasingLeases` functions.
- Terms and payment rows are editable only while Draft. Change an Active lease with Modify, never by editing its rows.
- Every date of a change must fall on a lease-month boundary, and the months before it must already be posted by a lease run.
- Leases are base-currency only; activation refuses any other currency.
