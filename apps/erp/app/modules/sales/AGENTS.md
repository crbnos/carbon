# Sales Module

Quotes (with cost rollup and pricing), sales orders, sales RFQs, customer management, opportunity tracking, pricing rules/overrides, the customer portal, rental agreements for the fleet (see Rentals below), and AR contracts for services billed on a schedule (see Contracts below). Full quote-to-order-to-fulfillment lifecycle.

## Key Domain Concepts

- **Opportunity** — deal container linking RFQs, quotes, and sales orders for one customer engagement.
- **Quote** — detailed cost estimate with line items, each having a make method (BOM + routing) and quantity-break pricing. Statuses: Draft → Pending → Sent → Ordered / Lost / Cancelled.
- **Quote Revision** — `quote.revisionId`. Unlike a PO (amended in place), a quote revision is a **new `quote` row** created by `copyQuote` → the `get-method` server function (`quoteToQuote`, `asRevision: true`), keeping the same `quoteId` with `revisionId = max + 1`, sharing the source `opportunityId`. Each revision gets its **own `externalLink`** row, whose `documentId` is revision-qualified (`Q000001-1`) because `externalLink` is UNIQUE on `(documentId, documentType, companyId)` — an unqualified id collides with the original's link. `deleteQuote` does not remove the link row, so that insert uses `onConflict … doUpdateSet` to reuse the orphan a deleted revision left behind. Displayed as `Q000001-1` when > 0 via `getQuoteDisplayId` (`@carbon/documents/utils`) on the PDF, email, share page, and filenames; two-tone in-app rendering uses `<RevisionSuffix>` (`~/components`).
- **Quote Line Pricing** — per-quantity-break pricing. PK is `(quoteLineId, quantity)` — no `id` column. `discountPercent` is a **fraction 0–1** (not 0–100). Generated columns compute net/converted prices. **Lead time can be PREDICTED from the shop schedule** rather than typed: the calendar-clock button on the Lead Time row opens `QuoteLeadTimeModal`, which POSTs `$quoteId.$lineId.lead-time.tsx` → `runQuoteLeadTimeWhatIf` (`@carbon/planning`) and applies one constraint's value to every break at once. The write goes through the grid's `onUpdateLeadTimes` (`quoteLinePrice.leadTime`, one state update for every break — never a loop over `onUpdatePrice`, which snapshots state per call; a failed row is rolled back and the modal stays open) — no new persistence, so `resolvePreservedQuoteLinePriceFields` is untouched.
- **Price trace** — how a price was reached (base → overrides → rules → final), a snapshot stored WITH the price because rules are edited in place: `quoteLinePrice.priceTrace` per quantity break, `salesOrderLine.priceTrace` per order line (copied from the quote by `convert`). Typed (manual) prices store `null`. The calculator icon opens it in a modal; on a quote line `getQuoteLinePriceTraces` also returns today's `currentTrace`, and `repriceQuoteLineFromRules` stores it. See `.claude/rules/quote-discount-system.md`.
- **Pricing Rules** — company-scoped Discount/Markup/Configuration rules. Discounts are non-stacking (highest-priority wins); Markups stack and compound in priority order. A **Configuration** rule targets exactly ONE configurable item (`itemId` in the form → `itemIds: [id]`, amount 0, no item group — `normalizePricingRule` in `sales.service.ts`) and carries `configurationPrices` (JSONB `{ key, value, amount, label? }[]` — list option / `"true"` for a boolean / `null` = per unit of a numeric value; `label` is the parameter's label at save time, used by the price trace; validated by `pricingRuleConfigurationPriceValidator` in `sales.utils.ts`, which stays out of the `sales.models` import graph so the engine tests can load it). `toMatchedRule` parses a rule row for the engine; `applyPriceRules` (`sales.utils.ts`) adds those signed surcharges to the starting price before the discount, given the line's `configuration`. An override with `applyRulesOnTop = false` still takes them (`configurationOnly`) — they price the options, not the part. Every other rule type stores `configurationPrices` as null.
- **Line configuration** — `quoteLine.configuration` and `salesOrderLine.configuration` (keyed by `configurationParameter.key`; the `convert` server function copies it quote → order). Jobs made for an order line use `resolveJobConfiguration` (`sales.utils.ts`): the order line's configuration, else the quote line's; when the order line was configured differently from its quote the job is built with `itemToJob` + that configuration instead of copying the quote's method (an unset value — absent, null or blank — compares equal). A configured Make to Order quote line is priced from the part's unit sale price (not the cost rollup) when it has one, so it matches the order line — `configuredQuoteBasePrice`; a row with markups someone chose stays cost-plus. The sales order line form keeps its configurator in `useItemConfiguration` + `ItemConfigureButton` (`~/components/Configurator/ItemConfigurator`), which loads parameters through `getConfigurationParameters` and ignores a stale load for an item no longer selected.
- **Price Overrides** — customer-specific or type-specific price overrides with quantity breaks via `customerItemPriceOverride` / `customerItemPriceOverrideBreak`. Precedence: customer > customer-type > all-customers > base price.
- **Sales Order** — confirmed order from a quote. Lines carry `methodType` (Make to Order, Make to Stock, etc.) that determines production handling.
- **Sales RFQ** — inbound request from a customer, convertible to a quote via the `convert` server function.
- **Rental Agreement** — rents serialized fleet units (fixed assets) to a customer; billed in persisted periods, invoiced as `Rental` lines on Draft sales invoices. See "Rentals (sub-area)".
- **Contract** — bills a customer for Service items under an agreement: One-time and Recurring lines, an invoice schedule and a monthly revenue plan both editable while Draft (set up through a five-step wizard), amendments, cancellation with a credit memo, renewal. Drafted as `Service` lines (list price + `discountPercent`) on Draft sales invoices that post to Deferred Revenue / Contract Assets; the recognition run recognizes the plan. See "Contracts (sub-area)".

## Safety

### Always
- MUST use `convertQuoteToOrder` / `convertSalesRfqToQuote` for lifecycle conversions — they call the `convert` server function.
- MUST use `resolvePrice` + `applyPriceRules` for price calculation — never compute prices ad hoc.
- MUST store `discountPercent` as a fraction (0.10, not 10) — all downstream math assumes 0–1.
- MUST scope customer queries by `companyId` — customers are company-scoped.

### Ask First
- Closing sales orders — `closeSalesOrder` sets `closed`, `closedAt`, `closedBy` permanently.
- Deleting quotes linked to an opportunity — may orphan related orders.
- Modifying pricing rules — affects all future `resolvePrice` calls.

### Never
- Bypass the `convert` server function for quote→order or RFQ→quote conversions.
- Delete `quoteLinePrice` rows when *rewriting* a line's pricing — go through `upsertQuoteLinePrices`, which delete-and-reinserts inside one transaction and carries over any user-entered field (`discountPercent`, `leadTime`, `shippingCost`, `categoryMarkups`, `priceSource`) you **omit** (explicit-wins, omit-preserves via `resolvePreservedQuoteLinePriceFields`). Deleting rows for a quantity break the line no longer offers is different and required: see `reconcileQuantityBreaks` (`sales.utils.ts`) and its use in `x+/quote+/$quoteId.$lineId.details.tsx`. Orphaned rows render as selectable options on the customer share page.
- Store `discountPercent` as a whole number (e.g., 10 instead of 0.10).

## Sales Rules (sub-area)

Configurable if-condition-then-error/warn rules evaluated when an item is added to a **sales document** (quote line, sales order line, sales invoice line) — e.g. "if item type is X and the customer's ship-to country is Y → block". Lives **inside** this module: validators in `sales.models.ts`, UI in `ui/SalesRules/`; the admin CRUD is the family-parametrized implementation in `~/modules/shared` (see "Service functions" below). There is no `modules/sales-rules` directory — a rule feature is not its own domain.

Distinct from **storage rules** (`~/modules/inventory`, warehouse/MES surfaces) and **configurator rules** (`configurationRule`, `x+/part+/$itemId.rule*.tsx`) — storage and sales rules now share ONE table, `enforcementRule`, discriminated by `family` ('storage' | 'sales'); the configurator's `configurationRule` is unrelated. Every read/write in this module MUST filter `family = 'sales'`.

- **Rule** — `enforcementRule` row (`family = 'sales'`): `conditionAst` JSONB (`{kind: all|any|none, conditions:[{field,op,value}]}`), `severity` (`error` blocks; `warn` requires acknowledgment), `message` with `{token}` interpolation, `surfaces` (`enforcementRuleSurface` enum; the sales-legal subset `quoteLine` | `salesOrderLine` | `salesInvoiceLine` is enforced by the `enforcementRule_sales_surfaces` CHECK), item scoping via `filteredItemTypes`/`filteredItemGroupIds`/`filteredItemMatchAll` (empty = all items) or explicit `enforcementRuleItemAssignment` pins (shared with the storage family — always resolve pins against a family-filtered rule set, never a PostgREST embed).
- **Shared engine** — the AST compiler/evaluator lives in `@carbon/utils` (`rules.ts` + `field-registry.ts`, with the zod AST mirror in `rules-schema.ts`): `compileSalesRuleWithCache`, `evaluateRules`, `SALES_RULE_SURFACES`, `getFieldsForSalesRuleSurfaces`, `SALES_RULE_FIELD_REGISTRY` (customer type/status/country + synthesized `customer.customFields.*`). Countries are **alpha-2** codes.
- **Evaluator** — `@carbon/ee/rules.server` `evaluateSalesRuleLines` (service-role client; plan-gated on `SALES_RULES`). Missing ship-to → the engine's required-field semantics emit "Customer location is required" at the rule's severity.
- **Fail loud, never silently permissive.** A failed rule load, item load, or ship-to resolution THROWS. Each of those returns "nothing to enforce" if swallowed, which turns a compliance control off with no signal.
- **Drop-ship ship-to** — `resolveSalesOrderShipTo` returns the shipment's `customerLocationId`, never the header's, when `dropShipment` is set. If the drop-ship location is missing it returns null rather than falling back: the header is a DIFFERENT address, so a fallback would clear a country rule that should have blocked.
- **Invoice ship-to** — a sales invoice's customer ship-to is `salesInvoiceShipment.customerLocationId` (migration `20261006221401_sales-invoice-discount-and-ship-to.sql`; `invoiceCustomerLocationId` is the bill-to; the `locationId` columns are Carbon's own warehouses). Authored on the invoice's Shipping card ("Ship To", scoped to the invoice's customer; `update.tsx` clears it on a customer change); `convert` copies the order's delivery location (drop-ship location when `dropShipment`, else the header's `customerLocationId`), `create-contract-invoices` copies `shipToCustomerLocationId`, `create-rental-invoices` the agreement's Rental Site. An order-derived line (`salesInvoiceLine.salesOrderId`) resolves through `resolveSalesOrderShipTo`; a standalone line resolves through `resolveSalesInvoiceShipTo` (document gate, line create/edit, API gate) and, with no ship-to set, passes null and fails closed via required-field semantics. NEVER substitute the bill-to — pinned by `packages/ee/src/rules/sales/invoice-shipto.test.ts`. The `salesInvoiceLocations` view's `shipment*` address columns join this column (same migration; they joined the warehouse `locationId` before and were always null), feeding the PDF Ship To block and the Stripe shipping address.
- **One modal** — enforcement actions return `{ violations, ruleNames }`; forms submit via `useRuleViolations` and render the shared `RuleViolationModal` (`@carbon/ee/rules`). Do not add a second violation UI.
- **Acknowledgment log** — `enforcementRuleAcknowledgment` (append-only): one row per deduped violation on blocked attempts and acknowledged overrides.

### Sales Rules safety

- MUST evaluate with the **service role** client in route actions AFTER `requirePermissions` — the check must see full truth regardless of the acting user's read permissions.
- MUST gate write routes with `requireFeature({ feature: "SALES_RULES" })` (key in `packages/ee/src/plan.ts`) — community-blocked, not merely Cloud-paywalled. The ee write functions also embed `requireEntitlement("SALES_RULES")` as the un-strippable lock.
- The shared rule-builder components (`RuleBuilder`, `SurfacesField`, `MessageWithTokens`, `SeveritySelect`, `ItemFilterSelector`) live in `~/modules/inventory/ui/StorageRules/` and are imported by **deep path**. Keep any parameterization **additive** (defaults preserve storage behavior), and never import a module *barrel* from these components — keep the dependency a one-way deep import from `sales` into the inventory UI folder to avoid a barrel cycle. The shared zod AST schema lives in `@carbon/utils` for the same reason.
- Never widen the `enforcementRule_sales_surfaces` CHECK to admit storage surfaces — that CHECK is what replaced the old per-family enum typing.
- Never duplicate `isBlocked`/`dedupeViolations`/the violation modal — import from `@carbon/ee/rules(.server)`.

Enforcement: the quote, sales-order, and sales-invoice line create + edit actions, plus document gates (quote finalize/convert, RFQ convert, order confirm, shipment post, invoice post — the invoice-post gate runs in `x+/sales-invoice+/$invoiceId.post.tsx` BEFORE the optimistic `Pending` write). ### Rentals safety

- Never write `rentalBillingPeriod` / line status transitions from app code; no app code writes a line status. Activate / release / close / cancel go through `post-rental-agreement`, delivery and return through `post-shipment` / `post-receipt` (source `'Rental Agreement'`).
- Never delete a sales invoice (or line) that may carry Rental lines with a plain delete — use the `*ReleasingRentals` server functions.
- Terms and units are editable only while Draft; the line details route refuses a unit change after activation.
- Delivery (a posted rental shipment) puts the unit on rent (it starts accruals); billing periods run from the agreement's start date and cycle, whatever the delivery date.
- A `Sale` line (sales-type lease) is derecognized at ACTIVATION, not delivery. Never unwind it from app code: early termination is a manual journal (return before `endDate` and cancel both refuse "Ending a rental treated as a sale early is a manual journal").
- A stored classification is final once Active; thresholds changed in settings apply only to later activations.

- **Schedule math** — pure, `@carbon/database/contract-schedule` (`packages/database/src/contract-schedule.ts`, re-exported from `@carbon/utils`; in `@carbon/database` so the demo-dataset tier can plan a schedule). `billingGrid` (Anniversary anchors on `startDate`, Calendar on the Monday / 1st of month / quarter / 1 Jan; period k is always added FROM the anchor, so a 31 Jan anchor clamps to 28 Feb and returns to 31 Mar; first period clipped to the start, last to the end). `periodUnits` counts whole months from the period start, then the remaining days as a fraction of the next month (15 Mar–14 Apr = 1); `wholePeriodUnits` makes a whole unclipped month-based period exact (Month at a Year rate = 1/12). A Weekly grid at a Month / Quarter / Year rate prices every row with `averageDayUnits` instead — days at the yearly average day (rate × 12 ÷ 365 for a Month rate) — so every whole week is the same amount and a 365-day year is exactly 12 months (`periodUnits` made a week 7/28, 7/30 or 7/31 of a month). `rowPricing`: `unitPrice = round(rate × units)`, `amount = round(quantity × unitPrice × (1 − discountPercent))`. `planInvoiceSchedule`: One-time = one row on the first grid due date on or after its start; Recurring = one row per grid period, due on its first (Advance) or last (Arrears) day via `nextInvoiceDate` (a mid-period row lands on the NEXT regular invoice date); an invoice dated before `firstInvoiceDate` moves to it; a row ending on or before `billedThrough` is `Billed Externally`. `horizon`: fixed term → `endDate`; open-ended → the end of the period after today's. `validateScheduleEdit` is the conservation check (residual per line = computed − Σ non-adjustment rows). `reconcileContractSchedule` = reconcile, never rewrite: billed rows untouched; ONE adjustment per already-Invoiced recurring row whose line now ends earlier (−billed × daysAfter ÷ daysBilled); Planned invoices from the change date deleted and re-planned; split installments re-cut as a group. Also `amendmentEffectiveDate`, `recurringValuePerPeriod`, `suggestAmendmentType` (up Expansion, down Contraction, equal Existing), `suggestContractType` (Reactivation when every non-Draft contract of the customer Ended, else New Sales), `currentPeriodEnd`, `renewedEndDate`, `invoiceLinePricing`. Pinned by `contract-schedule.test.ts`.
- **Persist on first edit** — an unedited Draft has NO schedule rows: the `$id` loader plans them live. The first schedule edit (or Confirm) writes them (`isEdited = true` on touched invoices). The page names live rows by POSITION — `planned:<invoiceDate>` for an invoice, `planned:<invoiceDate>:<lineId>:<periodStart>[:adjustment]` for a row — and `edit-schedule` resolves them after writing (fix `56fa0f7b8e`, pinned by `contract-lifecycle.test.ts`). A line edited after a schedule edit leaves per-line residuals; the invoice grid shows them and offers Reset Schedule. The revenue plan follows the same model: an unedited Draft has no `customerContractRevenue` rows (the loader plans them live, `revenueIsStored: false`), and the first `edit-revenue` (or Confirm) writes them. Revenue rows are addressed by (line, month), so they need no position refs.
- **Revenue plan** — pure, `@carbon/database/contract-revenue-schedule` (re-exported by `@carbon/utils` `contract-revenue.ts`, which keeps `contractPositionPreview`; `revenue-schedule.ts` moved to `@carbon/database` too, `@carbon/utils` re-exports it). `planRevenueSchedule`: a line's revenue total = Σ its invoice-schedule rows (adjustments and memo credits included), spread over `lineRevenueDates` (go-live ?? revenue start ?? start → revenue end ?? end) by `revenuePreview` — Daily = `spreadStraightLine`; Even Period = equal per full calendar month, a partial month prorated by its days, residual placed by `distributeRoundingResidual`; no end → one row in the start month (an open-ended Recurring line runs to its last scheduled `periodEnd`). Months before `recognizeRevenueFrom`'s month are `Recognized Externally`. `validateRevenueEdit` is the conservation rule: residual per line = billed − Σ revenue rows. `reconcileRevenueSchedule` = reconcile, never rewrite (one line from a date): `Recognized` / `Recognized Externally` rows and `Planned` rows before the date's month are kept; the other months take the new plan; whatever keeps the line off the new plan's total (a recognized month now worth less) lands on the first non-kept month on or after the date, as a catch-up row when the plan has none. Pinned by `contract-revenue-schedule.test.ts`. Writers in `post-customer-contract/revenue-writes.ts` (shared with `create-contract-invoices`): `billedTotals`, `plannedRevenue`, `materializeRevenue`, `ensureRevenue` (writes the plan for an Active contract that has none — one confirmed before Phase B), `reconcileRevenue` (also keeps an **in-flight** Planned month — one a `revenueRecognitionSchedule` row references, held by a Draft run — and never deletes it), `changedRevenueLines` (only lines whose revenue dates, method, billed total or last billed period changed are reconciled), `writeOpeningEntries`.
- **Position** — pure, `@carbon/database/contract-position`. Position = invoiced − recognized, per line, in contract currency AND base: Deferred Revenue holds max(N, 0), Contract Assets max(−N, 0). Every movement goes through `applyContractMovement({ position, amount, rate, counterpart })`: a raising amount (an invoice) clears Contract Assets first, then adds to Deferred Revenue; a lowering amount (a recognition, a credit, a VOID) releases Deferred Revenue first, then adds to Contract Assets. Base is carried at a weighted-average rate per pool (drawing takes the pool's carried base, adding takes the movement's rate); against a `receivable` the difference to the receivable's base is realized FX (`fxBase`), against `revenue` it is 0. Also `positionFromEntries`, `normalizePosition` (the reclass that brings a negative pool back), `movementCredits`. Pinned by `contract-position.test.ts`. Ledger I/O in `packages/server-functions/src/lib/contract-ledger.ts`: `loadContractPositions` (one grouped read) and `lockContractPositions` — ONE transaction advisory lock `contract-position:<companyId>` that every writer takes (invoice posting and its VOID, `post-memo`, `synthesizeContractRevenue`). Confirm writes Opening entries without it.

- **Invoice generation** — server function `create-contract-invoices` (`{ asOf, customerContractId? }`, `update: sales` + `create: invoicing`; one transaction per contract, failures returned in `failures`): renew (`renewal = Renew` and `endDate <= asOf`, one term at a time; with an uplift every continuing Recurring line is ended and copied at `round(rate × (1 + uplift))`; revenue reconciled from the new term's first day), roll an open-ended schedule to the horizon (append only; revenue reconciled from the first appended period), both after `ensureRevenue`; draft every Planned invoice dated `<= asOf` as one Draft `salesInvoice` (with an opportunity, `customerContractId`, `customerReference` = PO number, location = the origin order's shipment location else the oldest location), then set Ended when `endDate < asOf` and nothing is Planned. - **Posting** (Phase B; all of it only when `accountingEnabled`):
  - *Invoice* — `post-sales-invoice` takes a line with `customerContractLineId` out of the Service deferral path: `planContractInvoiceLine` (`post-sales-invoice/contract-posting.ts`) applies the line's revenue (`salesRevenueBase × rate`, contract currency) to the line's position against the receivable and replaces the Sales leg with two revenue legs — Cr Contract Assets up to the asset pool, the rest Cr Deferred Revenue (a negative line: Dr Deferred Revenue first, then Contract Assets) — plus reclass lines for the pools' carried base and the realized FX difference (`realizedExchangeGain/LossAccount`, required only when it is non-zero). No schedule rows. Legs carry `documentType 'Contract'` / `documentId` = the contract; the line's `projectId` is the Project dimension on revenue-side legs only (AR, tax, shipping carry none). Deferred Revenue, Contract Assets and Sales must be mapped active leaves. One `Invoice` ledger entry per line, on the posting journal. Positions are read before the transaction and re-read under the lock; a moved position refuses ("A contract line's revenue position changed while this invoice was posting; post it again").
  - *VOID* — each `Invoice` entry is negated exactly (entry type `Void`, on the VOID journal, whose reversal of the original legs includes `documentType 'Contract'` lines); when the negation drives a pool below zero (the run already recognized part of what the invoice deferred), `normalizePosition` reclasses it to the other pool with one Deferred Revenue / Contract Assets pair on the same journal. The schedule rows still go back to Planned with `voidedSalesInvoiceId` (re-drafted held).
  - *Credit memo* — `post-memo` (`planContractCredit`): the memo-borne adjustment rows are summed per line and applied as a lowering movement against the receivable — Dr Deferred Revenue up to the deferred pool, the rest Dr Contract Assets, any part no credited line covers Dr Sales, and realized FX for the remainder; one `Credit Memo` entry per line. It no longer touches `revenueRecognitionSchedule`. Voiding it is still refused ("A contract cancellation credit cannot be voided").
  - *Recognition* — `synthesizeContractRevenue` (the `propose-revenue-recognition-run` server function, second of `RUN_ROW_SYNTHESIZERS`) turns each Planned non-zero revenue month starting on or before the run's period end, of a non-Draft contract (Ended included — a cancellation's catch-up rows), with no schedule row yet, into a Deferral row (Dr Deferred Revenue / Cr Sales) for what the deferred pool covers and an Accrual row (Dr Contract Assets / Cr Sales) for the rest, at `get_exchange_rate(…, periodEnd)`, one `Recognition` entry per row. `postRevenueRecognitionRun` posts them with `documentType 'Contract'` and Customer / Item / Project dimensions, flips the months to `Recognized`, stamps the entries' `journalId`, and refuses (`RunOutOfDateError`) while a due contract month is unsynthesized. See accounting AGENTS → Contract revenue.
  - Contract invoices posted before Phase B keep their Service Deferral rows (no restatement).

### Contracts safety

- Never write `customerContract.status`, schedule rows, revenue rows, ledger entries or amendments from app code — Confirm / schedule and revenue edits / Amend / Cancel / Revert go through `post-customer-contract`, drafting / renewal / ending through `create-contract-invoices`, ledger movements through posting and the recognition run.
- Never rewrite a `Recognized` revenue month or a month a Draft run holds — reconcile (`reconcileRevenue`), which books the difference on a later Planned month.
- Every writer of a contract position takes `lockContractPositions` and computes from `loadContractPositions`; never derive a movement's accounts outside `applyContractMovement`.
- Terms and lines are editable only while Draft; on an Active contract only `contractType`, `invoiceAutomation` and `notes` change directly.
- Never delete a sales invoice or line that may carry contract rows with a plain delete — use the `*ReleasingRentals` functions (they release contract stamps too). The MCP `invoicing_deleteSalesInvoice*` tools still use the plain deletes (open follow-up).
- A page that shows live-planned rows must send `planned:` position refs, never invented ids.
- `discountEndsOn` is acted on only at Confirm; an amendment or renewal copy keeps the date but never splits again.
