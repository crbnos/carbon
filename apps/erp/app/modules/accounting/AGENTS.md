# Accounting Module

Chart of accounts, journal entries, general ledger, fiscal periods, currencies, payment terms, cost centers, dimensions, financial reporting (trial balance, balance sheet, income statement), fixed assets with depreciation, intercompany transactions, and external accounting sync (Xero, QuickBooks Online, Rillet).

The reports hub lives inside the accounting module at `/x/accounting/reports` (with the module sidebar; single "Reports" sidebar item), while the report pages themselves are full-screen in their own namespace `apps/erp/app/routes/x+/reports+/` (`/x/reports/{balance-sheet,income-statement,executive-pnl,trial-balance,inventory-valuation,revenue-waterfall,rental-utilization,lease-net-investment}` — bare-outlet layout, no module sidebar; `/x/reports` redirects to the hub). Balance sheet and income statement are multi-period: a Columns filter (Monthly default / Quarterly / Yearly) buckets the selected range fiscal-aware via `computeReportPeriodBuckets` (`@carbon/utils`) and the `accountTreeBalancePeriodSeries` RPC returns per-bucket `balanceAtDate`/`netChange` in one snapshot-bounded journal scan. Trial balance stays single-period (Beginning/Debit/Credit/Ending derived from netChange by account class).

**Inventory Valuation** (`inventory-valuation.tsx`, gated on `view: "accounting"`) is an inventory-subledger report that lives here (not in the inventory module): it renders the `InventoryValuationWorkbench` from `~/modules/inventory` (on-hand value by location/item, as-of date, with a GL tie-out and a **Reconcile** action → `inventory-valuation.reconcile` posting via `createInventoryReconciliationJournal`, gated on `create: "accounting"`). Data/UI live in the inventory module; only the route + hub registration are here.

The **Executive P&L** (`executive-pnl.tsx`) shares the income statement's loader (same period series, consolidation, and translation) but renders a condensed summary instead of the account tree: `computeExecutivePnl` (`ui/Reports/executivePnl.ts`) rolls income-statement leaves up by `accountType` into Revenue / Cost of Sales / Operating Expenses / Other Income / Other Expense / Tax, then derives Gross Profit, Operating Income, and Net Income with margin-of-revenue percentages. A class-based catch-all keeps Net Income tied out to the income-statement root; `ExecutivePnlSummary` renders the fixed lines (no search, no drill-down).

## Key Domain Concepts

- **Chart of Accounts** — hierarchical account tree. Accounts have `class` (Asset/Liability/Equity/Revenue/Expense), `incomeBalance` (Balance Sheet/Income Statement), and `accountType`. Group accounts contain children; leaf accounts post transactions. Scoped by `companyGroupId`.
- **Journal Entries** — double-entry bookkeeping in the `journal` table. `amount` uses natural balances: positive Asset/Expense is debit; positive Liability/Equity/Revenue is credit. Convert by account class before summing debit-signed amounts. Lines carry dimensions and cost center allocations. Statuses (`journalEntryStatus`): a manual entry is Draft → Posted → Reversed; an automatic posting is born `Provisional` before the company's accounting cutover and `Posted` after it; the enable turns a Provisional journal into `Posted` (dated on or after the cutover) or `Superseded` (dated before it). `JournalEntryStatus` labels Superseded "Before cutover". `getJournalEntries` leaves Superseded journals out unless a status filter asks for them.
- **The accounting cutover** (`.ai/specs/implemented/2026-10-08-accounting-cutover.md`) — every posting path writes its journal and its sub-ledger rows (cost layers, finished-goods and asset cost, deferral schedules, contract entries, intercompany rows) for every company. `companySettings.accountingCutoverDate` decides only the journal status; `hasAccountingCutover(settings)` (`accounting.models.ts`) is the ERP's one test for it. `companySettings.accountingEnabled` still exists, but no code reads it. `accountingActivatedAt` / `accountingActivatedBy` record the enable; the `check_accounting_config_locked` trigger then refuses any change to the three cutover columns, to `company.baseCurrencyCode` and to `fiscalYearSettings.startMonth`. A new company gets a cutover from `seed-company` (the first day of the current month) and never sees the wizard. A company with no cutover sees the wizard instead of the gated pages: `AccountingBetaGate` overlays Reports, Intercompany, Journals, Periods, Fixed Assets and Depreciation Runs with a "Set up accounting" link, and `x+/accounting+/_index.tsx` redirects to the wizard. A Provisional journal has no accounting period, so it never locks the fiscal calendar (`getFiscalCalendarCommitted` counts Posted and Reversed only) and never blocks a period delete.
- **Journal status lists** (`@carbon/database/accounting-posting`) — every journal reader filters by one of three lists. `GL_JOURNAL_STATUSES` (Posted, Reversed): balances, trial balance, reports, period snapshots, tie-outs, provider sync. `DOCUMENT_JOURNAL_STATUSES` (Provisional, Posted, Reversed): a reader that follows one document's chain — void builders, GR/IR, WIP sums, intercompany lookups. `OPEN_ITEM_JOURNAL_STATUSES` (Provisional, Posted): payment control lookups and the memo, charge and reimbursement void checks. Superseded is in none. The `journal-status-filter` check (`@carbon/checks`) fails a `status <> 'Draft'` journal filter in TS and in migrations from `20261009005144`. The AR/AP readers (`get_ar_open_by_customer`, `get_ap_open_by_supplier`, `get_ar_tie_out`, `get_ap_tie_out`) keep `= 'Posted'` and also accept `sourceType 'Opening Balance'` (`20261009014620`).
- **Stand-in lines** — before the cutover, a posting that needs an empty nullable account default posts the line to `retainedEarningsAccount` and names the default it wanted in `journalLine.accountDefaultRole` (`resolveDefaultAccount`, `@carbon/database/journal-posting-status`). A Provisional journal counts nowhere, so the stand-in moves no balance. The enable re-points every stand-in line dated on or after the cutover to its default and clears the role. After the cutover an empty default fails the posting. See `packages/server-functions/AGENTS.md` → Journals and the accounting cutover.
- **Manual accounting work is refused before the cutover** with `ACCOUNTING_NOT_STARTED` ("Set up accounting before you post journals, runs or period closes."): `requireAccountingCutover` (`accounting.service.ts`) in `postJournalEntry`, `reverseJournalEntry`, `lockAccountingPeriod`, `closeAccountingPeriod` and `createDepreciationRun`; `requireGroupAccountingCutover` (every company of the group) in `runIntercompanyMatching` and `generateEliminations`; the server-only `assertAccountingCutover` (`accounting.server.ts`) in `postDepreciationRun`, `postDisposal` and `postRevenueRecognitionRun`; and the same check in the `propose-revenue-recognition-run` and `recalculate-revenue-recognition-run` server functions.
- **The enable wizard** — `x+/accounting+/activation.tsx` (layout, `view: accounting`, redirects to Periods once the company has a cutover; the cutover date rides the `?cutover=` search param (`ACTIVATION_CUTOVER_PARAM`), read by `getActivationCutover` in `accounting.server.ts`, which defaults to the first day of the current month) with five steps, each its own route: `activation.readiness.tsx` (the date picker — the first day of the current month or of one of the 3 before it, `CUTOVER_MAX_PERIODS_BACK` — and the six checks of `getActivationReadiness`: every `accountDefault` account column set to an active account, `migrationClearingAccount` included; fiscal year settings and base currency; a valid cutover date; no Draft or Pending receipt, shipment or invoice and no Draft payment or memo dated before the cutover; no open job created before the company's first Provisional or Superseded journal; no Posted `Opening Balance` journal), `activation.inventory.tsx` (`getCutoverInventory`: on-hand at the cutover per item and its unit cost — the replayed layer value for FIFO / LIFO, standard cost for Standard, `itemCost.unitCost` for Average, which is the only one the user edits), `activation.fixed-assets.tsx` (`getCutoverFixedAssets`: the assets on the books the day before the cutover — acquired before it, and not disposed or disposed on or after it, except an asset whose disposal leaves the books with no journal (`getAssetsLeavingWithoutJournal`: a sale, return to inventory or lease commencement posted before the reset) — with accumulated depreciation as of that day, the asset's own less what Posted runs booked for months on or after the cutover (`getDepreciationAfterCutover`), since the enable writes those runs' journals again; intent `save-asset` writes the accumulated depreciation as of the day before the cutover through `updateCutoverAccumulatedDepreciation`, which stores it plus that later depreciation), `activation.trial-balance.tsx` (the prior system's trial balance as of the day before the cutover, kept as ONE Draft `Opening Balance` journal with no period by `saveOpeningTrialBalance`; intents `save-tb` (the editor) and `import-tb` (CSV `accountNumber, debit, credit`, saves nothing when a row has an error); `getMigrationClearing` shows, per control account, the trial balance, Carbon's opening total and the difference) and `activation.enable.tsx` (the summary and the typed company name; it invokes the `activate-accounting` server function and redirects to Periods). The summary lists, under "Documents posted before Carbon kept journals", each family with legacy documents and how many (`getLegacyDocumentCounts`): documents posted on or after the cutover that have no journal, which the enable journals with today's accounts and costs (see `packages/server-functions/AGENTS.md` → Legacy documents). The reads live once, in Kysely, in `@carbon/database/accounting-cutover-reads` (server-only); the wizard loaders call them through `accounting.server.ts` with `getDatabaseClient()`, and `activate-accounting` calls the same functions with its transaction. The pure planners (`planInventoryReset`, `recostOutbound`, `buildOpeningJournalLines`) are `@carbon/database/accounting-cutover`. Settings → Accounting (`x+/settings+/accounting.tsx`) shows "Accounting since {date}" or a "Set up accounting" button; there is no switch.
- **Opening lines** — the enable posts one `Opening Balance` journal, dated the day before the cutover, against `accountDefault.migrationClearingAccount` (seeded as 3400 "Migration Clearing" for new companies). A control-account line copies the keys its chain reader matches (`documentType`, `documentId`, `documentLineReference`, description), so a payment, a purchase invoice's GR/IR walk or a job close after the cutover finds it as if the original posting had written it. A document partly settled before the cutover gets two lines: its original amount, and the amount settled before the cutover under "<description> (settled before cutover)", which the readers ignore. Every other account comes from the trial balance only. Deferred revenue opens from the Deferral rows dated on or after the cutover of invoices posted before it that were still deferred the day before (Planned, or Posted by a run whose journal the reset deleted, which the enable writes again), on each row's debit account. Lease net investment opens per rental agreement from the lease rows of each `Sale` line commenced before the cutover (the last `rentalLeaseScheduleLine.closingNetInvestment` before the cutover, else `initialNetInvestment`), not from a commencement journal, which a lease commenced before the reset does not have. Migration Clearing must total zero within 0.01 before the enable. A void of a document dated before the cutover is in `packages/server-functions/AGENTS.md`.
- **Fiscal Year Settings** — configurable start month for fiscal and tax years. Accounting periods auto-created via `getOrCreateAccountingPeriod`.
- **Dimensions** — analytical tags on journal lines (Location, Department, Project, etc.). Entity-type dimensions resolve values from their source table; Custom dimensions use `dimensionValue`.
- **Cost Centers** — hierarchical organizational units for cost allocation via `parentCostCenterId`.
- **Fixed Assets** — capital assets with depreciation. Supports straight-line, declining balance, MACRS, and units-of-production methods. Depreciation runs generate journal entries: one `depreciationRunLine` per asset per month, each month's journal in that month's period, and **Reverse Run** (`reverseDepreciationRun`) undoes the latest posted run — journals, accumulated depreciation and the run's status (see the rule). The **fleet bridge** links an asset to an `item` / `trackedEntity` / `workCenter`: a serialized unit is capitalized from stock or built by a Make to Asset job (`complete_job_to_inventory`), returned to stock at net book value, or accumulated as **Construction in Progress** (`fixedAssetClass.isConstructionInProgress`, status `Under Construction`, cost rows in `fixedAssetCipCost`) until capitalized into an in-service class. Construction in progress is built but **hidden** until it returns with projects: `CONSTRUCTION_IN_PROGRESS_ENABLED = false` (`accounting.models.ts`) filters CIP classes out of `getFixedAssetClasses` / `getFixedAssetClassesList` (every class list and picker), hides Attach Job / Capitalize and the CIP cost card (`isCipClass` in `x+/fixed-asset+/$fixedAssetId.tsx`), the Under Construction status filters (`visibleFixedAssetStatuses` / `visibleFleetStatuses`) and Complete To → Asset Under Construction (`JobForm`). Engines and schema are untouched; flip the constant to bring it back. Every inventory ↔ asset move is one Posted `fixedAssetTransfer` document written by the `post-asset-transfer` server function (journal `sourceType 'Asset Transfer'`, off by default in the sync policy). Fleet status is derived by the `fleetAssets` view, never stored. See `.claude/rules/fixed-asset-lifecycle.md`.
- **Revenue recognition** — `revenueRecognitionSchedule` is the one "what to post, when" table: `type` Deferral / Accrual / Interest, `status` Planned / Posted, each row carrying its own `debitAccountId` / `creditAccountId`, linked to a `salesInvoiceLineId`, a `rentalAgreementLineId` or a `customerContractLineId` (contract rows, see Contract revenue below). `post-sales-invoice` writes Deferral rows for every company (every **Service** line with service dates; every Rental rent line). There is no revenue recognition flag. Service dates belong to Service lines only: every other item type is a physical good, earned when it ships, so the sales order / invoice line forms show the date fields only on a Service line, the line validators refuse them on any other type (the invoice validator also admits `Rental`, whose lines carry their billing period), `upsertSalesOrderLine` / `upsertSalesInvoiceLine` null them on any other type, and posting ignores dates left on a non-Service line. A **run** (`revenueRecognitionRun` / `revenueRecognitionRunLine`, routes `x+/accounting+/revenue-recognition-runs*` + `x+/revenue-recognition-run+/`, nav Accounting → Revenue Recognition) claims every Planned row dated on or before its `periodEnd` and first runs the `RUN_ROW_SYNTHESIZERS` of the `propose-revenue-recognition-run` server function (`packages/server-functions/src/propose-revenue-recognition-run/`, `{ periodEnd }`, permission `create: accounting`; the routes and the monthly job call it through `serverFns`). `postRevenueRecognitionRun` (`accounting.server.ts`) posts the run's journals (`sourceType 'Revenue Recognition'`, `defaultEnabled: false` in the sync policy; one per month, below); deferral lines reference the invoice, rental Accrual/Interest lines `documentType 'Rental Agreement'` with Customer / Item / Location dimensions resolved from the agreement. Inngest `revenue-recognition-proposal` (cron `0 12 1 * *`) only proposes Draft runs. A period may hold more than one run (a later one picks up rows that fell due after the first posted) but one Draft at a time: the routes and the proposal refuse a second Draft, and the partial unique index `revenueRecognitionRun_one_draft_per_period` is the backstop. No run may end after the company's current month (`futureRunPeriodError`, `accounting.server.ts`; the proposal function repeats the check). Posting writes ONE journal per month the rows fall in, each in that month's period — the run's own period when the month is Closed (`resolveRunPostingPeriods` → `RunPostingPeriods`); `revenueRecognitionRun.journalId` names the journal of the run's own period, and the Documents panels read every journal through the schedule rows. **Reverse Run** (`reverseRevenueRecognitionRun`, route `$runId.reverse`) reverses those journals with their documents and dimensions (`reverseRunJournals`, each on its own date or today when Closed, `resolveReversalPeriods`), puts the rows back to Planned under the same run, clears what posting stamped (lease schedule lines, contract ledger entries, contract revenue months) and returns the run to Draft; `reverseJournalEntry` refuses a run's journal (`RUN_JOURNAL_SOURCES`, `accounting.models.ts`). A Draft is a snapshot: each run line copies its row's amount. **Recalculate** (`x+/revenue-recognition-run+/$runId.recalculate`, the `recalculate-revenue-recognition-run` server function, `update: accounting`) keeps the run's id and number, releases its rows BEFORE rerunning the synthesizers (a synthesizer that drops a held row would otherwise delete the run it emptied), then claims what is due by its `periodEnd` again; a run with nothing left due is deleted. The proposal's `periodEnd` must be a real month end (a 400 otherwise). `postRevenueRecognitionRun` refuses a run that is out of date — a held row's amount or status changed, or an unclaimed Planned row is due by its `periodEnd` — with `RunOutOfDateError`, whose message the post route shows. A write that deletes a held Planned row (an invoice void, or `synthesizeContractRevenue` dropping a contract row whose plan month was replaced) keeps Draft runs in step in its own transaction through `syncDraftRecognitionRuns` (`packages/server-functions/src/lib/draft-recognition-run.ts`), deleting a run it empties. Close task "Recognize revenue for the period" (`autoCheckKey 'unposted-revenue-schedules'`) asks the run what it would do instead of copying its rules: the `preview-revenue-recognition-run` server function (`{ periodEnd }`, `view: accounting`) runs the synthesizers and `selectDueScheduleRows` in a transaction that always rolls back and returns `{ count, amount }`. The check fails while that preview has rows, the preview failed, or a Draft run holds a Planned row due by the period end.
- **Rental accruals** — `synthesizeRentalAccruals` accrues earned-but-unposted rent of `Rental` (operating-lease) lines for the run's calendar month (Dr `contractAssetAccount` / Cr `rentalIncomeAccount`, both required or it throws "Set the Contract Assets and Rental Income account defaults before recognizing rental revenue"). It takes every non-adjustment `rentalBillingPeriod` of a `Rental` line (`On Rent` / `Returned`) that no POSTED invoice covers (`Pending`, or `Invoiced` onto a Draft/Pending invoice), clips it to the month and to `[deliveredAt, returnedAt]`, and writes one Accrual row per SLICE (`periodStart/End` = the slice, `scheduledDate` = the run's period end) with cumulative rounding from the period's first day. Any existing Accrual row overlapping a slice suppresses it (idempotent); a transaction advisory lock serializes concurrent proposals. Posting a Rental rent line credits Contract Assets for the unbilled Accrual rows of its period (Planned or Posted) and stamps `billedBySalesInvoiceLineId`. The close check counts un-accrued rent through the run preview (above), so it sees exactly what a run would accrue.
- **Contract revenue** (contracts Phase B, `.ai/plans/implemented/2026-09-22-revenue-recognition-rentals-and-contracts.md` Part IV D5) — `synthesizeContractRevenue` (second entry of `RUN_ROW_SYNTHESIZERS`) turns every Planned `customerContractRevenue` month starting on or before the period end, of a non-Draft contract, with no schedule row yet, into a Deferral row (Dr `deferredRevenueAccount` / Cr `salesAccount`) for the part the line's deferred pool covers and an Accrual row (Dr `contractAssetAccount` / Cr `salesAccount`) for the rest, at `get_exchange_rate(…, periodEnd)`; each row carries `customerContractLineId`, `customerContractRevenueId`, `contractAmount` and one `Recognition` entry in `customerContractLedgerEntry` (cascades with the row). A negative (catch-up) month yields negative rows. It first drops Planned contract rows whose plan month was replaced (`customerContractRevenueId` nulled). `postRevenueRecognitionRun` posts contract rows with `documentType 'Contract'` and Customer / Item / Project (line, else contract) dimensions, flips their plan months to `Recognized`, stamps the entries' `journalId`, and treats an unsynthesized due month or a held row with a nulled plan month as out of date. The close check counts unsynthesized due months through the run preview (above).
- **Sales-type leases** — a rental line classified `Sale` (a sales-type lease; `lessorClassification` values `Rental` / `Sale` / `Financing`) at activation (`post-rental-agreement`, see sales AGENTS → Rentals) posts its commencement and end-of-term residual return as journals of `sourceType 'Lease'` (`POSTING_POLICY` `Lease`, `defaultEnabled: false`; also in the hand-written `journalEntrySourceTypes` array with the `LuKeyRound` icon), lines `documentType 'Rental Agreement'` with Customer / Item / Location dimensions. Its effective-interest schedule is `rentalLeaseScheduleLine`; each line that `earnsInterest` (`lessor-lease` in `@carbon/utils`: not zero, not the one-unit drift an Advance lease closing on zero leaves on its last line) spawns one Planned `Interest` recognition row (Dr `netInvestmentInLeasesAccount` / Cr `leaseInterestIncomeAccount`) that the run posts under `'Revenue Recognition'`, and `postRevenueRecognitionRun` then stamps the schedule line's `journalId` / `postedAt` (no unpost path exists). Rent and Purchase Option invoice lines of a `Sale` line credit `netInvestmentInLeasesAccount`; a Purchase Option line also settles the rest of the line's NI against the schedule's closing balance (`purchaseOptionSettlement`, `post-sales-invoice/rental-posting.ts`: shortfall Dr `costOfGoodsSoldAccount` / Cr NI, excess Dr NI / Cr `leaseRevenueAccount`). A residual return moves the schedule's balance on the return date (`netInvestmentAt`) and keeps the Interest rows dated on or before it, so later runs still post them and NI closes to zero. A sales-type lease must run whole billing periods (`salesTypeRequirementError`, `lessor-lease` in `@carbon/utils`) so the billed rent equals the valued payment stream. Account defaults seeded 1160 Net Investment in Leases, 4070 Lease Revenue, 4150 Interest Income – Leases. Lease policy (the classification thresholds `companySettings.leaseMajorPartThresholdPercent` 75 / `leaseSubstantiallyAllThresholdPercent` 90 and `leaseDefaultDiscountRate` 6) is edited on `x+/settings+/accounting.tsx` ("Lease Classification" card, intent `leasePolicy`, `update: settings`) through `updateLeasePolicySettings` in the settings module; changes affect later activations only.
- **Net investment report** — `getLeaseNetInvestment(client, companyId, { asOf })`, report `x+/reports+/lease-net-investment.tsx` (`view: accounting`; hub card "Net Investment in Leases", category Close Reports; `path.to.leaseNetInvestment`). Per commenced `Sale` line live on `asOf` (Pending / On Rent, or Returned after `asOf`; Sold lines omitted; agreement `startDate` ≤ `asOf`): `initialNetInvestment`, posted principal (schedule lines with `periodDate` ≤ `asOf` whose Interest row has posted (`postedAt`) or that earn no interest, so have no row to post), current NI, next interest, undiscounted remaining payments by fiscal year (`fiscalYearSettings.startMonth`), and the last line's closing (option + residuals). Reads `rentalAgreementLine` and `rentalLeaseScheduleLine`, whose RLS is `sales_view` — an accountant without sales view sees an empty report. Principal counts once its Interest row is posted (a no-interest line: once its date passes), so it ties to 1160 only when the run and the rent invoices for the same months are both posted.
- **Rental utilization** — `getRentalUtilization(client, companyId, { from, to, fixedAssetClassId })`, report `x+/reports+/rental-utilization.tsx` (`view: accounting`; hub card "Rental Utilization", category Analytics). Per fleet asset: fleet days = `[acquisitionDate, disposalDate ?? to] ∩ [from, to]`; on-rent days = union of its lines' `[deliveredAt, returnedAt ?? to]` within that window; time utilization = on-rent ÷ fleet days; recognized income = Posted schedule rows dated in range crediting Rental Income or Lease Interest Income + posted Charge invoice lines; dollar utilization = income × (365 ÷ range days) ÷ acquisition cost. Class totals per `fixedAssetClass`. One read per table, joined in TS.
- **Intercompany** — transactions between companies in a group. `runIntercompanyMatching` pairs them; `generateEliminations` creates reversing entries on the lowest-common-parent elimination entity, classified by `journal.eliminationKind`: `'IC Balance'` (reverse IC Receivable/Payable) and `'IC Revenue'` (reverse an intragroup sale's revenue + COGS and write the buyer's capitalized asset down to group cost — removes intragroup profit from consolidated income). The engine is **capture-driven, not GL reconstruction**: the posting server functions (`post-sales-invoice`, `post-purchase-invoice`) record role-tagged references (`intercompanyEliminationLine`: `Control`/`Revenue`/`COGS`/`Capitalization`) when each side posts, and `generateEliminationEntries` reads them — so it writes down whatever account the BUYER capitalized (inventory OR a **fixed asset** — the latter is now in scope, was the negative-Finished-Goods bug). The writedown scales by the buyer's on-hand fraction (fixed assets: full until disposed); revenue/COGS reversal scale by the same fraction so the entry balances. `p_regenerate` reverses existing eliminations (reversing entries, never deletes) and re-derives — the workbench "Regenerate" button. Both halves of a trade record their matching amount in the trade's DOCUMENT currency rounded at internal `SCALE` — `calculateSalesIntercompanyAmount` (seller) and `round(intercompanyAmount)` (buyer). `generate_intercompany_matches` pairs them on exact NUMERIC equality with **no tolerance**, so rounding either half at settlement precision leaves every trade with sub-cent digits permanently `Unmatched` and eliminations never run. Investment/NCI and seller fixed-asset disposal (deferred gain) remain out of scope. See `.ai/specs/2026-08-17-intercompany-elimination-engine.md`.
- **Currency translation / CTA** — `translateCompanyBalances` validates the source trial balance using natural debit/credit signs and positive finite pair rates. Missing rates fail explicitly. `applyCtaToReportPeriodSeriesForReport` resolves only the root company's CTA mapping through a server-only permission and company-group/root check; operating-company ledger reads remain RLS-scoped. The existing `applyCtaToReportPeriodSeries` service adds the calculated CTA once to the reporting root company's configured `currencyTranslationAccount`, validates its active Equity posting leaf, then rerolls intermediate groups and roots before filtering/export. Never identify CTA by account number. Financial report chart reads include inactive historical accounts and their ancestors; chart and balance RPC rows are fully paginated before calculation. Active-only filters belong to posting/configuration pickers. Balance RPC trees and period-close snapshots retain inactive posting leaves and ancestors. Report loaders reject company selections outside the available company group (404) before balance reads.
- **Shipping revenue** — `accountDefault.salesShippingRevenueAccount` maps an active Revenue posting leaf distinct from Sales. New groups seed 4050 Shipping Revenue under Revenue; existing groups resolve a compatible leaf and backfill mappings. Nonzero invoice shipping requires a valid mapping; output tax posts separately to tax payable. The full defaults form validates once and saves both sections with one company-scoped `updateDefaultAccounts` UPDATE, so a failed mapping cannot half-save the form.
- **Payments have THREE payee kinds, not two.** `payment.employeeId` is a reimbursement
  payout: always a Disbursement, never AR, never a refund, and it targets
  `invoiceSettlement.targetReimbursementId` only — no invoice target, no discount, no
  write-off, no prior credit. Its control account is
  `accountDefault.employeeReimbursementsPayableAccount`, falling back to `payablesAccount`
  at runtime. `journalEntrySourceType` gained `Charge` and `Reimbursement` (the former
  replacing `Card Transaction`); a Reimbursement journal's payable leg is what a payout
  clears. Before the cutover a target with no control line (a document posted before
  every company wrote journals) books the default control account instead. After the
  cutover a target with no control line, in its own journal or in the opening journal, is
  refused ("Target is missing its original control account") rather than debiting a
  liability that was never credited.
- **Payments and refunds** — the customer/supplier determines AR/AP independently of cash direction. Customer Disbursements and supplier Receipts refund posted balance-reducing memos through `invoiceSettlement.targetMemoId`, using current cash only (no invoice targets, discounts, writeoffs, or prior credits). Ordinary payments retain invoice targets, memo-source funding, and prior cash credits. Memo availability subtracts effective source and target principal; an effective posted refund blocks memo voiding. Aging and tie-out RPCs sign unallocated refunds opposite ordinary payments and use the applying payment's cash direction for FX consumption. Target memos consume exact `sourceAmount` principal and `appliedAmount` carrying base. Unknown memo principal retains the existing exclusion contract; it is not reconstructed or raised as a report error. Payment/invoice application histories page all rows, including embedded parent statuses and refund labels, before totaling.
- **Customer deposits** — a customer payment with `payment.rentalAgreementId` or `payment.salesOrderId` (CHECK `payment_deposit_document_check`: at most one; `paymentValidator` refines the same and refuses it on a supplier payment) is a deposit. `post-payment` books its unapplied cash on `accountDefault.prepaymentAccount` (2110 Customer Prepayments, class Liability) with description `CUSTOMER_DEPOSIT_DESCRIPTION` = "Customer Deposit" (`@carbon/database/accounting-posting`) instead of on-account AR credit; a Disbursement carrying the reference refunds from the same account. Applying it later goes through the existing prior-credit path: the source-control lookup matches either the on-account description or "Customer Deposit", and the release posts `CUSTOMER_DEPOSIT_APPLIED_DESCRIPTION` ("Customer Deposit (applied)") as a debit on the prepayment account. **A deposit funds only its own document**: `allocatePaymentFunding` (`@carbon/utils` payment-funding) gives each `FundingSource` an optional `scope` (`fundingScopeOf(payment)` → `{ type: "rentalAgreement" | "salesOrder", id, readableId? }`) and each `FundingRequest` the `rentalAgreementIds` / `salesOrderIds` its invoice bills (from `salesInvoiceLine`, one read per call: `loadSalesInvoiceDocumentIds` in `@carbon/database/deposit-scope`); a scoped prior source funds only requests that list its id, an unscoped one funds anything. A payment that is itself a deposit is refused on any other invoice ("A deposit for RA000001 can only be applied to that agreement's invoices", readable id via `loadDepositScope`). Source priority is unchanged (current payment, then prior sources by `postingDate`, `paymentId`) but the split is decided over all requests at once (`prioritizedTransport`), so a deposit's invoice never spends the ordinary cash another invoice needed and the outcome does not depend on request order — with no scoped source it is byte-identical to the old walk. `replaceInvoiceSettlements` and `post-payment` both apply it (post re-derives, so a crafted Draft cannot bypass it). `getAvailableOnAccountCreditSources` returns deposits in `sources` with their scope but leaves them out of `availableDocumentAmount` / `availableBaseAmount` (and `getAvailableOnAccountCredit`); `getOpenSalesInvoicesForCustomer` returns each invoice's `rentalAgreementIds` / `salesOrderIds`; `PaymentApplyTable` lists each deposit apart ("Deposit for RA000001 (its invoices only)"), sizes rows with `fundableDocumentAmounts`, and for a deposit payment lists only its document's invoices. The payment form's "Deposit for" / "Refund deposit for" combobox (`PaymentForm`, customer payments only) is fed by `getDepositDocuments` (`invoicing/invoicing.server.ts`, server-only and not barrel-exported, called by the loaders of `x+/payments+/new.tsx` and `x+/payments+/$paymentId.tsx`). It loads every rental agreement, every open sales order, and every sales order a Posted deposit Receipt already references (plus ids the caller must keep), each flagged `open` (open order / Draft or Active agreement). The form narrows to the payment's customer; a Receipt offers only `open` documents (plus its current one), a Disbursement also offers documents already holding a posted deposit, so a Closed agreement's or a finished order's deposit can be refunded. Deposits never touch revenue or recognition schedules.
- **Net Income** — computed equity line on the balance sheet, never a posted account. Uses synthetic `NET_INCOME_ACCOUNT_ID` constant.

## Safety

### Always
- MUST ensure journal entries balance — `postJournalEntry` validates total debits = total credits before posting.
- MUST use `rootSignMultiplier` logic for root account aggregation — Assets/Revenue add, Liabilities/Equity/Expense subtract.
- MUST scope chart of accounts by `companyGroupId` (shared across group) and transactions by `companyId`.
- MUST use `getOrCreateAccountingPeriod` before posting a Posted journal — it checks for closed periods and auto-creates missing ones. A Provisional journal (no cutover yet) has no period and creates none.
- MUST filter journal status with `GL_JOURNAL_STATUSES`, `DOCUMENT_JOURNAL_STATUSES` or `OPEN_ITEM_JOURNAL_STATUSES` — never `<> 'Draft'`, which counts Provisional and Superseded journals.
- MUST use `toStoredAmount` / `toDisplayDebit` / `toDisplayCredit` for amount conversion — respects account class sign conventions.

### Ask First
- Modifying the chart of accounts structure — affects all financial reporting.
- Posting depreciation — `postDepreciationRun` writes a journal per asset per month; only the latest posted run can be undone (Reverse Run).
- Changing fiscal year settings — impacts period boundaries and reporting.
- Generating intercompany eliminations — creates adjustment entries on elimination entities.

### Never
- Delete posted journal entries — MUST use `reverseJournalEntry` instead.
- Manually create a "Net Income" account — it is computed via `NET_INCOME_ACCOUNT_ID`.
- Bypass double-entry balance validation when posting journal entries.
- Write the cutover columns, or change a journal to `Posted` or `Superseded` outside `activate-accounting`. The enable is one-way; journal UPDATE RLS admits Draft and Posted only, and `check_posted_record_immutable` refuses any change to a Superseded journal or its lines.
- Delete accounts that have posted journal lines — will violate referential integrity.

## Key Service Functions

- `getChartOfAccounts` / `getAccounts` / `upsertAccount` — account management
- `getTrialBalance` — trial balance via `trialBalance` RPC
- `getFinancialStatementBalances` — single-period statement balances with Net Income computation (trial balance report)
- `getFinancialStatementPeriodSeries` — multi-period balance sheet / income statement columns via the `accountTreeBalancePeriodSeries` RPC; per-bucket Net Income injection and optional per-bucket translation (`translate` arg)
- `getConsolidatedBalances` / `getConsolidatedPeriodSeries` — multi-company consolidation with currency translation (single-period / per-bucket)
- `translateCompanyPeriodSeries` — per-bucket currency translation (wraps `translateCompanyBalances` once per bucket)
- `getAccountPeriodSeries` — thin wrapper for the `accountTreeBalancePeriodSeries` RPC (period ends must come from `computeReportPeriodBuckets`)
- `getReportPins` / `upsertReportPin` — per-user pin overrides for the reports hub
- `createJournalEntry` / `saveJournalEntryWithLines` / `postJournalEntry` / `reverseJournalEntry` — journal lifecycle. `saveJournalEntryWithLines` diffs the submitted lines against the stored ones (`diffJournalLines` in `accounting.utils.ts`: a line whose `id` matches is kept or updated in place, anything else inserted, the rest deleted; dimensions rewritten only when they changed) and applies it through the `save_journal_entry_lines` RPC (SECURITY INVOKER, one transaction, refuses anything but a Draft journal of the company). A caller that sends no ids replaces every line. Keeps the Supabase-client signature because the MCP tool and the opening-balance / AR-AP adjust flows call it.
- `getJournalEntryRelatedItems` — the journal Documents panel: resolves each line's `documentType` + `documentId` to its document (sourceType settles sales vs purchase "Invoice") plus rows that store the journal's id (disposal, depreciation run line, revenue recognition run, CIP cost — each looked up only for its sourceType). `getFixedAssetRelatedItems` / `getPeriodRunRelatedItems` feed the fixed asset and run pages.
- `getActivationCutover` (`accounting.server.ts`) and the re-exports of `@carbon/database/accounting-cutover-reads` beside it (`getActivationReadiness`, `getCutoverInventory`, `getCutoverFixedAssets`, `getCutoverOpenItems`, `getLegacyDocumentCounts`, `getMigrationClearing`, `getOpeningTrialBalance`, `saveOpeningTrialBalance`, `updateCutoverAccumulatedDepreciation`) — the enable wizard's reads and writes (see The enable wizard). The Opening Balances mode of the Chart of Accounts page (`createOpeningBalanceJournal`, `OpeningBalancePostModal`) is gone: the wizard's opening journal replaces it. `'Opening Balance'` is `syncable:false` in `@carbon/ee` POSTING_POLICY — like `Manual`, it never syncs (the external ledger owns opening balances).
- `getOrCreateAccountingPeriod` / `getCurrentAccountingPeriod` — period management (lazy create on posting)
- `createFiscalYearPeriods` — generate the 12 monthly periods for a fiscal year (idempotent; from `fiscalYearSettings.startMonth`)
- `lockAccountingPeriod` / `unlockAccountingPeriod` / `closeAccountingPeriod` / `reopenAccountingPeriod` — Open↔Locked↔Closed transitions (sequential close/reopen)
- `getPeriodCloseChecklist` / `closePeriodWithChecklist` / `completeCloseTask` / `skipCloseTask` — the close checklist (instantiates tasks, evaluates auto-checks, gates the close). The two run checks read `getPeriodRunPreview` (what new revenue recognition and depreciation runs for the period end would hold, never throws) plus the Draft runs that wait; each `PeriodReadinessCheck` then carries `amount`, `due` and `draftRuns`, and the close page (`periods.$periodId.close.tsx`) shows them with a **Create Run** button (intents `create-revenue-run` / `create-depreciation-run`). `loadPeriodCloseChecklist` / `computePeriodReadiness` take the preview as an argument, so the scripted tests pass a value.
- `getAccountingPeriodDeletability` / `deleteAccountingPeriod` — delete an empty, open period (blocks Locked/Closed or periods with journals)
- `getFiscalCalendarCommitted` — is the fiscal calendar committed (any posting or Locked/Closed period)? Gates editing the fiscal start month
- `getCurrencies` / `getBaseCurrency` / `getCurrencyByCode` — currency config lookups (decimals/active; no rate — `currency.exchangeRate` was dropped)
- `getExchangeRate` / `getExchangeRates` — per-company rate resolution (RPC `get_exchange_rate(s)`: base=1, `exchangeRateOverride` wins, else global `exchangeRate` market-store ratio; missing = error, never 1)
- `upsertExchangeRateOverride` / `deleteExchangeRateOverride` — per-company user rate pins (always beat the daily feed)
- `translateCompanyBalances` — balance translation for multi-currency consolidation
- `getDimensions` / `getActiveDimensionsWithValues` / `saveJournalLineDimensions` — dimension management
- `getCostCenters` / `getCostCentersTree` — cost center hierarchy
- `getFixedAssets` / `insertFixedAsset` / `insertDepreciationRun` — fixed asset lifecycle. `buildDepreciationRunLines` is what a depreciation run for a period should hold; `createDepreciationRun` creates the Draft from it and refuses "Nothing to depreciate for this period" rather than leave an empty run, and refuses any period a later posted run already covers (`laterPostedRunId`). `postDepreciationRun` (`accounting.server.ts`) locks the run, refuses anything but a Draft whose lines are the ones the route checked, reads the lines and locks the assets inside its transaction, and adds to `accumulatedDepreciation` in SQL; a month with no book amount posts no journal
- `getFleetAssets` (the `fleetAssets` view, search + `fleetStatus` filter) / `getUnderConstructionAssets` / `getFixedAssetTransfers` / `getFixedAssetCipCosts` / `getWorkCenterCapitalCost` (non-Disposed assets of a work center with NBV and straight-line monthly depreciation) / `setFixedAssetOutOfService` / `returnFixedAssetToService` / `getCapitalizationCost` (the `preview-asset-capitalization` server function: the cost `capitalize` would book, rolled back) / `invokeAssetTransfer` (`serverFns.as(...).invoke("post-asset-transfer")`, run as the caller: `capitalize` (a unit carried at zero takes an entered cost from an offset account), `return`, `attachJob`, `capitalizeCip`, `adjustCost` — raise an Active / Fully Depreciated asset's cost from an offset account, and the next depreciation run catches a Straight Line asset up) — the fleet bridge (`// -- Fleet --` in `accounting.service.ts`); `postAssetRegistration` (`accounting.server.ts`) takes an optional `status` and writes a `fixedAssetCipCost` row for a registration into a CIP class; the journal is Provisional before the cutover and Posted after it, in the same one transaction as the asset rows
