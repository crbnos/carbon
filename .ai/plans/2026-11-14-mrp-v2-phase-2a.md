# MRP v2 Phase 2a (planned orders) — implementation plan

**Spec:** .ai/specs/2026-08-22-mrp-v2-planned-order-generation.md (Phase 2a)
**Research:** .ai/research/mrp-v2-phase-2-planned-orders.md
**Closest sibling:** `planningAction` (Phase 1). `plannedOrder` copies its table shape,
authz entry, backup registration and diff-write.
**Branch:** naveenkash/mrp-v2-research

## Scope of this plan (agreed 2026-11-14)

Phase 2a ships with 4 parts moved to 2b. The spec records them.

1. No `projectPeg` change. The drawer shows the existing demand lineage.
2. The `supplyForecast` bridge stays. The `planning.update` routes keep writing it,
   and MRP keeps deleting it.
3. The grid SQL functions do not change. The grids already total the Order and Make
   actions, and those come from planned orders now.
4. Dates stay in calendar days, as in Phase 1. The fence counts calendar days too.

Design rules that every task follows:

- **One sizing function.** Task 3 moves the new-supply sizing out of `deriveRowActions`
  into a pure `sizeRowSupply`. The engine and the worklist both call it.
- **Planned orders exist only in the common segment** (`planningSegmentId = ''`) and only
  for items with no supersession mode. Project segments, planning groups and superseded
  items keep the Phase 1 path, unchanged. They are lot-for-lot already.
- **`explodeBom` without the new hook behaves exactly as today.** `getMethod` uses it.
- **Fence 0 behaves exactly as Phase 1.** The default is 0.
- **An Order or Make action covers every planned order of its week**, as Phase 1 sums new
  supply per week. Only change actions on a planned order carry `plannedOrderId`.
