# Carbon Extensibility Architecture

**Status:** Draft for review
**Date:** 2026-07-12
**Scope:** Platform-level architecture for third-party and first-party extensions to Carbon (ERP/MES/QMS)

---

## 1. Vision

Carbon should be the first open-source ERP where **extending the system and upgrading the system are not in tension**. Every mature open-source ERP today forces a choice: customize deeply and dread every upgrade (Odoo, ERPNext), or stay vanilla and lose the reason you chose open source. We reject that trade.

The core bet:

> **The platform owns schema and data integrity. Extensions own behavior.**
> An extension never touches a core table, never patches a core function, and never imports another module's internals. In exchange, the platform guarantees that a green contract-test suite today means a green suite after `carbon upgrade` tomorrow.

This is a deliberately **strict** model. It is harder to write an extension for Carbon than to drop a monkey-patch into ERPNext's `hooks.py`. That is the point: the cost is paid once, at build time, by the extension author — instead of on every upgrade, forever, by every customer. Upgrades must be a `pnpm` command, not a three-week consulting project.

### Principles

1. **Stable contracts, not stable internals.** Core modules publish versioned service interfaces, event schemas, and read models. Everything else is private and may change without notice.
2. **No EAV, no metadata soup.** Extension data lives in real Postgres tables with real types, real constraints, real indexes, and real RLS — generated and versioned by the platform.
3. **Hooks, not patches.** Extensions react to `before:`/`after:` extension points with declared, schema-validated payloads. There is no mechanism to override or replace core behavior in place.
4. **Isolation enforced by tooling, not convention.** Cross-module imports of internals fail lint and CI, for core modules and extensions alike. If it compiles, it composes.
5. **Workflows are infrastructure.** Long-running, multi-step, failure-prone business processes are declared as workflows and executed by the platform (persistence, retries, compensation) — not hand-rolled in extension code.
6. **Upgrades are proven, not hoped.** Every core release runs the contract suite against the published extension corpus. Breaking a contract requires a major version, a deprecation window, and a migration note — mechanically enforced.
7. **Multi-tenant by construction.** Every extension table carries `companyId`, composite PK `("id", "companyId")`, and RLS — generated by the platform, not left to the author.

### Non-goals

- **Arbitrary UI theming/patching.** Extensions contribute UI at declared slots and routes; they do not restyle or rewrite core screens.
- **Replacing core behavior.** If core logic is wrong or insufficient, the fix belongs upstream (it's open source). Extensions augment; they do not fork-in-place.
- **Runtime plugin loading.** Extensions are workspace packages resolved at build time. Dynamic hot-loading is out of scope for v1; the manifest system is designed so it could be added later without contract changes.

## 2. Core Extension Model

Three surfaces, in order of preference. An extension author should reach for the highest one that solves the problem:

| Surface | Use when | Guarantee |
|---|---|---|
| **Workflows** | Multi-step business process reacting to system events | Durable, retried, compensable |
| **Hooks** | Single-step reaction or validation at a lifecycle point | Schema-validated payload, ordered execution |
| **Service interfaces** | Extension code needs to read/act on core data | Typed, versioned, semver-guaranteed API |

### 2.1 Events and hooks

Carbon already routes side effects through an event system (Inngest via `@carbon/jobs`). The extension model formalizes this into **named extension points** with two phases:

- **`before:` hooks** — synchronous, in-transaction, ordered. Run inside the core service call *before* the write commits. A `before:` hook can:
  - **validate** — throw a typed `HookVeto` to abort the operation with a user-facing message;
  - **augment** — return a patch to the *extension-owned* side-table data for the entity (never to core columns).
  - Hard budget: 250ms per hook, no external I/O (enforced by the SDK runtime — no `fetch`, no `functions.invoke`). Anything slower belongs in an `after:` hook or workflow.
- **`after:` hooks** — asynchronous, at-least-once, delivered via the event system after commit. Free to do I/O, call services, start workflows. Must be idempotent; the payload carries a stable `eventId` for dedup.

Extension points are **declared by core modules**, not discovered. Each has a stable name and a versioned zod payload schema:

```
{module}.{entity}.{transition}          e.g.  quality.nonConformance.opened
                                              inventory.receipt.posted
                                              sales.salesOrder.released
```

```ts
// packages/extension-sdk/src/hooks.ts (SDK surface)
export interface HookRegistration<E extends ExtensionPointName> {
  point: E;                       // "inventory.receipt.posted"
  phase: "before" | "after";
  version: 1;                     // payload schema major version the handler targets
  handler: (ctx: HookContext, payload: PayloadOf<E, 1>) => Promise<HookResult>;
}
```

Rules that make this upgrade-safe:

- Payload schemas are **additive within a major version**. Removing/renaming a field or changing a type requires a new major version of that extension point; the platform delivers both versions during the deprecation window (adapter maintained in core).
- Hooks are registered in the extension **manifest** (§8), so the platform knows statically which extension consumes which point at which version. This is what makes upgrade impact reports possible (§6.3).
- `before:` hook ordering is deterministic: manifest-declared `priority`, then extension name. No extension can depend on another extension's hook having run unless it declares a dependency (§4.3).

### 2.2 Service interfaces

Every core module publishes a **contract package**: the only importable surface.

```
@carbon/contracts/quality      → QualityService interface + entity read models + event payloads
@carbon/contracts/inventory    → InventoryService, ...
```

- Contracts contain: a typed service interface (the operations core supports being called from outside the module), read-model types, extension-point payload schemas, and error types. **No implementation, no DB types, no Kysely.**
- Implementations are bound by the platform's service registry at startup. Extension code receives services through `HookContext`/`WorkflowContext` — never by importing `apps/erp/app/modules/...`:

```ts
async handler(ctx, payload) {
  const quality = ctx.services.quality;          // QualityService, tenant-scoped
  await quality.createInspection({ ... });       // companyId injected from ctx, not passed by caller
}
```

- Service methods are **tenant-scoped by construction**: the context carries `companyId` and the registry wraps every call. An extension physically cannot make a cross-tenant call through a service interface.
- Contracts are **semver'd independently of the app**. `carbon-ext-x` declares `"@carbon/contracts": "^3"` and the compatibility checker (§6) enforces it.

### 2.3 Reading core data

Extensions never query core tables. Two sanctioned read paths:

1. **Read models via service interfaces** — `ctx.services.sales.getSalesOrder(id)` returns the published `SalesOrderReadModel`, a stable projection (not the raw row — core can refactor columns freely as long as the projection holds).
2. **Published SQL views** for reporting/bulk access — core modules expose `contract."salesOrders_v1"` views with RLS. Extension migrations may reference these views (e.g., for their own materialized reports) but never `public."salesOrder"` directly. The migration generator rejects references to non-contract relations (§3.4).

## 3. Schema Extension Strategy — No EAV

### 3.1 Why not EAV / JSON blobs

ERPNext's Custom Fields and generic `field/value` patterns trade write-time convenience for permanent costs: no type safety, no FK integrity, no useful indexes, unqueryable reports, and a schema that exists only in application metadata. Odoo's inheritance approach mutates core tables directly, which is precisely what makes its upgrades hell. We do neither.

**Every piece of extension data lives in a real, typed, platform-generated Postgres table.**

### 3.2 The two shapes

**A. Entity augmentation — side tables.** When an extension adds fields to a core entity, the platform generates a 1:1 side table keyed to the core row:

```sql
-- generated from manifest of extension "coating-inspection"
CREATE TABLE "ext_coatingInspection_receiptLine" (
  "id"           TEXT NOT NULL,          -- = receiptLine.id
  "companyId"    TEXT NOT NULL,
  "coatingSpec"  TEXT,
  "cureTempC"    NUMERIC,
  "batchPhotoId" TEXT REFERENCES "document"("id"),
  "createdAt"    TIMESTAMPTZ NOT NULL DEFAULT now(),
  "updatedAt"    TIMESTAMPTZ,
  PRIMARY KEY ("id", "companyId"),
  FOREIGN KEY ("id", "companyId")
    REFERENCES "receiptLine"("id", "companyId") ON DELETE CASCADE
);
-- + RLS policies, updatedAt trigger — all generated, not hand-written
```

- Core tables are never ALTERed by extensions. Core deletes cascade; orphaned extension data is impossible.
- The SDK exposes augmentation transparently: `ctx.ext.receiptLine.get(id)` / `.set(id, patch)`, fully typed from the manifest.
- The forms system renders declared augmentation fields at the entity's declared form slot (§8), so simple "add a field to the receipt screen" needs zero UI code.

**B. New entities — extension-owned tables.** Full tables in the extension's namespace (`ext_{extension}_{table}`), same generated conventions: `id('prefix')` IDs, `companyId`, composite PK, RLS, audit columns. Extensions get a scoped, typed Kysely client for **their own namespace only** — the client's DB type includes only `ext_{extension}_*` tables plus contract views, so cross-namespace queries don't typecheck, and the DB role backing extension execution has no grants outside the namespace, so they don't run either.

### 3.3 Declared, not migrated by hand

Extension authors do not write SQL. They declare schema in the manifest:

```ts
// extensions/coating-inspection/manifest.ts
schema: {
  version: 3,                                  // monotonically increasing schema version
  augments: {
    receiptLine: {
      coatingSpec:  { type: "text" },
      cureTempC:    { type: "numeric" },
      batchPhotoId: { type: "ref", to: "document" },   // refs limited to contract-published entities
    },
  },
  tables: {
    coatingInspection: {
      columns: {
        receiptLineId: { type: "ref", to: "receiptLine", required: true },
        status:  { type: "enum", values: ["pending", "passed", "failed"], required: true },
        notes:   { type: "text" },
      },
      indexes: [["receiptLineId"]],
    },
  },
}
```

`carbon ext generate` diffs the manifest against the last generated version and emits a **numbered, immutable migration** into the extension package (`migrations/0003_*.sql`). Authors review and commit it; they never edit it. The generator enforces the platform's SQL conventions (naming, RLS, bare `NUMERIC`, no destructive changes without an explicit `lossy: true` acknowledgment that surfaces in the install/upgrade UI).

### 3.4 Versioned application

- Applied migrations are recorded per extension in `extensionMigration (extensionId, version, checksum, appliedAt)`.
- Install/upgrade applies pending migrations **in order, transactionally**; checksums detect tampering.
- Downgrade is explicitly unsupported; uninstall offers **archive** (rename namespace to `ext_removed_*`, revoke access) or **drop** (destructive, double-confirmed). Archive is the default.
- The generator statically rejects: references to non-contract core relations, triggers on core tables, functions in `public`, and any `ALTER` targeting a table outside the extension namespace. The generated SQL is the *only* SQL an extension can ship — there is no escape hatch, by design.

## 4. Module System Design

### 4.1 One rule

> A module (core or extension) may import another module **only** through its contract package.

Concretely, for a package `carbon-ext-coating-inspection`:

- ✅ `import type { ReceiptPostedPayload } from "@carbon/contracts/inventory"`
- ✅ `ctx.services.quality.createInspection(...)`
- ❌ `import { upsertReceipt } from "~/modules/inventory/inventory.service"` — lint error, CI failure
- ❌ `import { Database } from "@carbon/database"` — extensions get their scoped client, never the global DB types
- ❌ any import from another extension's package internals

### 4.2 Enforcement

Convention does not survive contact with deadlines, so the boundary is enforced three times:

1. **Lint** — Biome/ESLint boundary rules: extension packages may import only `@carbon/extension-sdk`, `@carbon/contracts/*`, their own files, and their declared npm deps. Core modules get the mirror-image rule (no importing `extensions/*`, no cross-module service imports).
2. **Typecheck** — contracts are the only packages that export types usable by extensions; internal types are not exported from module barrels. The scoped Kysely client makes out-of-namespace table access a type error.
3. **Runtime** — the DB role and the tenant-scoped service registry make the first two non-bypassable even by generated or dynamic code.

### 4.3 Dependencies between extensions

Extensions may depend on other extensions **only if the dependency publishes its own contract** (`extensions/x/contract.ts`, exported as `carbon-ext-x/contract`). The manifest declares it:

```ts
requires: { extensions: { "carbon-ext-lot-genealogy": "^2" } }
```

The platform topologically orders installation, migration, and hook execution by this graph, and refuses to disable/uninstall an extension with active dependents. Circular dependencies are a manifest validation error.

### 4.4 What an extension may contribute

Everything an extension can do is enumerable from its manifest — this is what makes upgrade analysis static:

| Contribution | Mechanism |
|---|---|
| React to lifecycle points | `hooks[]` |
| Multi-step processes | `workflows[]` |
| Schema | `schema` (side tables + owned tables) |
| UI | `ui.routes[]` (new pages under `/x/{extension}/...`), `ui.slots[]` (declared core slots: entity detail panels, table columns, action menus) |
| Permissions | `permissions[]` — new `{extension}_{action}` permissions, managed by core RBAC |
| Settings | `settings` schema — rendered by core settings UI, stored platform-side per company |
| Scheduled work | `crons[]` — platform-scheduled, delivered as events |

Notably absent: middleware on core routes, patching core components, raw SQL, service overrides. If a real use case can't be expressed, the answer is a new extension point in core — a PR, not a workaround.

## 5. Workflow Engine as Extension Primitive

Hooks handle single steps. Real extensions are usually *processes*: "when a receipt posts for a coated part, create an inspection, notify the quality team, wait for disposition, and if it fails, quarantine the lot and open an NCR." Hand-rolling that with hooks means hand-rolling persistence, retries, timeouts, and cleanup — the graveyard of every plugin ecosystem.

Carbon makes the workflow engine a **first-class platform service** (n8n-like in shape, but bound to system events and typed contracts, and executed on the existing durable-execution backbone — Inngest — rather than a bespoke runner).

### 5.1 Declaration

Workflows are TypeScript definitions registered in the manifest:

```ts
// extensions/coating-inspection/workflows/inspect-on-receipt.ts
export const inspectOnReceipt = defineWorkflow({
  id: "coating-inspection/inspect-on-receipt",
  version: 2,
  trigger: on("inventory.receipt.posted", {
    filter: (p) => p.lines.some((l) => l.itemTags.includes("coated")),
  }),

  steps: {
    createInspection: step(async (ctx, p) => {
      return ctx.services.quality.createInspection({
        sourceType: "receipt",
        sourceId: p.receiptId,
        procedure: "coating-visual",
      });
    }),

    notify: step(async (ctx, _p, { createInspection }) => {
      await ctx.services.notifications.send({
        group: "quality",
        template: "coating-inspection/pending",
        entity: { type: "inspection", id: createInspection.id },
      });
    }),

    disposition: waitForEvent("quality.inspection.dispositioned", {
      match: (p, { createInspection }) => p.inspectionId === createInspection.id,
      timeout: "72h",
      onTimeout: "escalate",
    }),

    quarantineIfFailed: step(async (ctx, _p, { disposition }) => {
      if (disposition.result === "fail") {
        await ctx.services.inventory.moveToQuarantine({ ... });
        await ctx.services.quality.openIssue({ type: "nonConformance", ... });
      }
    }),
  },

  compensate: {
    // runs if a later step permanently fails after createInspection succeeded
    createInspection: (ctx, _p, r) =>
      ctx.services.quality.cancelInspection(r.id, { reason: "workflow-aborted" }),
  },
});
```

### 5.2 Platform guarantees

- **Durability** — every step result is persisted; a deploy or crash mid-workflow resumes, never restarts from scratch.
- **Retries** — per-step retry policy with backoff; steps are required to be idempotent (the SDK provides idempotency keys derived from `runId + stepId`).
- **Waits** — `waitForEvent` / `sleep` park the run with zero held resources; timeouts route to declared handlers.
- **Compensation** — saga-style: on permanent failure, completed steps' compensators run in reverse order. Compensators are declared per step, not global.
- **Versioning** — in-flight runs finish on the version they started; new triggers use the new version. A workflow version is immutable once published.
- **Observability** — every run, step, retry, and compensation is visible in a core admin surface (per company, per extension), with payloads redacted per the manifest's data classification.
- **Tenancy** — runs are companyId-scoped like everything else; a workflow trigger fires per company that has the extension enabled.

### 5.3 Why this is the centerpiece

Most "extensibility" needs in a manufacturing ERP are exactly this shape — approval chains, inspection flows, replenishment logic, customer-specific compliance steps. Making the durable process the *primary* extension primitive (rather than a pile of hooks that each author wires together differently) is the single biggest lever for extension quality, and it is also the most upgrade-safe surface: a workflow touches core only through events in and service calls out, both of which are versioned contracts.

## 6. Upgrade Safety Guarantees

### 6.1 What is versioned

| Surface | Versioning | Breaking change requires |
|---|---|---|
| Extension-point payloads | Major version per point | New point version + adapter for old version through deprecation window |
| Contract packages (`@carbon/contracts/*`) | Semver | Major bump + codemod/migration note |
| Extension SDK | Semver | Major bump, N-1 supported |
| Contract SQL views | Suffixed (`_v1`, `_v2`) | New view; old view maintained through window |
| Workflow definitions | Per-workflow integer | In-flight runs pinned to their version |
| Extension schema | Per-extension integer | Forward-only migrations |

**Deprecation policy:** a deprecated surface keeps working for **one major core release** after deprecation, emits structured runtime warnings (surfaced in the admin UI, attributed to the consuming extension), and is listed in release notes with its replacement.

### 6.2 Contract tests

Contracts are only guarantees if they're executable. Two suites, both required:

1. **Platform-side (core CI):** every core module ships contract tests asserting its published surface — extension-point payloads match their schemas at the moment of emission (golden fixtures per version), service interfaces behave per contract (including error contracts), views return the published shape. A core PR that changes behavior behind a contract fails CI unless it also bumps the version and adds the adapter.
2. **Extension-side (`carbon ext test`):** the SDK ships a harness that runs an extension against a **real ephemeral Postgres + platform runtime** (not mocks): applies its migrations from zero and from each historical version, fires golden fixture events at its hooks and workflows, executes workflow paths including timeout and compensation branches, and lints the manifest against the target core version.

### 6.3 The corpus gate

The decisive mechanism: core CI maintains a **registry corpus** — manifests + contract tests of all published extensions (first-party always; community extensions opt in via the registry). On every core release candidate:

1. Static pass: diff every corpus manifest against the RC's contract versions → machine-generated impact report ("`carbon-ext-x@2.1` consumes `inventory.receipt.posted@1`, deprecated in this RC, removed in next major").
2. Dynamic pass: run each corpus extension's contract-test suite against the RC.

A red corpus doesn't necessarily block the release — but it *must* produce either a fix, an adapter, or an explicit entry in the breaking-changes report with remediation. Silent breakage is the failure mode this entire architecture exists to eliminate.

### 6.4 The upgrade experience

```
$ carbon upgrade
  Checking 4 installed extensions against carbon@5.0.0…
  ✓ carbon-ext-lot-genealogy@2.3.1        compatible
  ✓ carbon-ext-coating-inspection@1.8.0   compatible (1 deprecation warning)
  ✗ carbon-ext-edi-940@0.9.2              requires @carbon/contracts/sales ^3, core provides ^4
      → carbon-ext-edi-940@1.0.0 is available and compatible. Include it? [Y/n]
```

Pre-flight is static (manifests + lockfile), so it runs before anything is touched. Extension schema migrations run after core migrations, in dependency order, transactionally. In-flight workflow runs continue on their pinned versions.

## 7. How This Improves on ERPNext / Odoo / open-mercato

| Dimension | ERPNext | Odoo | open-mercato | **Carbon (this spec)** |
|---|---|---|---|---|
| Extension mechanism | `hooks.py` + monkey-patching + server scripts | ORM class inheritance (`_inherit`) — patch core in place | Clean DI module contracts | Declared hooks + versioned contracts; **no override mechanism at all** |
| Custom fields | DocType metadata (EAV-flavored, app-level schema) | ALTERs core tables via ORM inheritance | Limited | Platform-generated typed side tables; core tables never touched |
| Schema migrations for extensions | Fixtures + patches, hand-maintained | Module migration scripts, hand-maintained, breaks across versions | Basic | Generated from manifest, numbered, checksummed, platform-applied |
| Module isolation | Convention only — any app imports any app | Effectively none — inheritance couples everything to core internals | Good (package boundaries) | Enforced at lint + type + DB-role level; contracts are the only door |
| Upgrade safety | Manual; customizations routinely break | The famous 3-week consulting project; paid migration service exists for a reason | Better, but young | Semver'd surfaces + deprecation windows + **corpus contract tests on every core release** |
| Workflow/process automation | Server scripts + basic workflow states | Automated actions / server actions (imperative, untracked) | — | First-class durable workflow engine: persistence, retries, `waitForEvent`, compensation |
| Multi-tenancy in extensions | Site-per-tenant | DB-per-tenant or none | Row-level | Row-level, generated into every extension table + tenant-scoped service calls, non-optional |
| ERP domain depth | Deep | Deep | Shallow | Deep (existing Carbon modules) — the gap open-mercato leaves |
| Static upgrade impact analysis | No | No | Partial | Yes — manifests make every dependency of every extension machine-readable |

The one-line summary: **open-mercato's contract discipline, applied to a real ERP, with schema extension solved structurally instead of via EAV, and upgrade safety made an executable guarantee instead of a hope.**

The honest cost: writing a Carbon extension requires learning the manifest, the contract packages, and the workflow SDK — more upfront than dropping a patch into Odoo. We accept this. The extensions that get written will survive upgrades, compose with each other, and be reviewable by the registry. "Easy to hack" and "easy to operate for a decade" are different products; we are building the second.

## 8. File / Folder Conventions

Extensions are pnpm workspace packages under `extensions/`:

```
extensions/
  coating-inspection/                      # package: carbon-ext-coating-inspection
    manifest.ts                            # the single source of truth (validated by SDK zod schema)
    contract.ts                            # OPTIONAL: surface published to dependent extensions
    package.json                           # deps: @carbon/extension-sdk, @carbon/contracts/* only
    migrations/                            # generated by `carbon ext generate`, immutable, committed
      0001_init.sql
      0002_add_cure_temp.sql
      0003_inspection_table.sql
    hooks/
      validate-coating-spec.ts             # one hook per file
    workflows/
      inspect-on-receipt.ts                # one workflow per file
    ui/
      routes/
        inspections.tsx                    # mounted at /x/coating-inspection/inspections
        inspections.$id.tsx
      slots/
        receipt-line-panel.tsx             # rendered at declared slot ui.slot.receiptLine.detail
    services/
      coating.service.ts                   # extension-internal logic (scoped Kysely client)
    tests/
      contract.test.ts                     # runs under `carbon ext test`
      workflows.test.ts
    locales/                               # Lingui catalogs, merged by platform i18n
    AGENTS.md
```

Conventions:

- **Package name:** `carbon-ext-{slug}`. **DB namespace:** `ext_{camelSlug}_*`. **Routes:** `/x/{slug}/...`. **Permissions:** `{slug}_{action}`. All derived from the manifest `slug`; collisions are an install-time error.
- **`manifest.ts` is exhaustive.** If a capability isn't declared there, the platform won't wire it — a hook file not listed in the manifest is dead code, flagged by lint.
- **`migrations/` is append-only.** Editing a committed migration fails the checksum at install time.
- **`contract.ts` is optional and binding.** Publishing it means accepting the same semver obligations core carries.
- Core-side, the extension SDK and shared machinery live in `packages/extension-sdk/`, contracts in `packages/contracts/{module}/`, and the registry/loader in `packages/extension-host/`.

## 9. End-to-End Example: Custom Inspection Workflow

**Scenario:** an aerospace shop applies a protective coating to certain purchased parts. Every receipt of a coated part needs a visual inspection with a photo, a 72-hour disposition SLA, and automatic quarantine + NCR on failure. Coating spec and cure temperature must appear on the receipt line.

Everything below is the complete extension — no core changes.

### 9.1 Manifest

```ts
// extensions/coating-inspection/manifest.ts
import { defineExtension } from "@carbon/extension-sdk";

export default defineExtension({
  slug: "coating-inspection",
  name: "Coating Inspection",
  version: "1.8.0",
  requires: {
    core: "^4.2",
    contracts: { inventory: "^3", quality: "^3", notifications: "^1" },
  },

  schema: {
    version: 3,
    augments: {
      receiptLine: {
        coatingSpec:  { type: "text", label: "Coating spec" },
        cureTempC:    { type: "numeric", label: "Cure temp (°C)" },
      },
    },
    tables: {
      coatingInspection: {
        columns: {
          receiptLineId: { type: "ref", to: "receiptLine", required: true },
          status: { type: "enum", values: ["pending", "passed", "failed"], required: true },
          photoDocumentId: { type: "ref", to: "document" },
          notes: { type: "text" },
        },
        indexes: [["receiptLineId"]],
      },
    },
  },

  hooks: [{ point: "inventory.receipt.posted", phase: "before", version: 1,
            handler: "./hooks/validate-coating-spec" }],

  workflows: ["./workflows/inspect-on-receipt"],

  ui: {
    routes: [{ path: "inspections", file: "./ui/routes/inspections.tsx" }],
    slots: [{ slot: "receiptLine.detail", file: "./ui/slots/receipt-line-panel.tsx" }],
  },

  permissions: [{ action: "inspect", label: "Perform coating inspections" }],

  settings: {
    dispositionSlaHours: { type: "number", default: 72 },
    notifyGroup: { type: "text", default: "quality" },
  },
});
```

### 9.2 Schema

`carbon ext generate` emits `migrations/0003_inspection_table.sql`: the `ext_coatingInspection_receiptLine` side table (§3.2) and `ext_coatingInspection_coatingInspection`, each with `companyId`, composite PK, RLS, audit columns — reviewed, committed, applied on install in order 0001→0003.

### 9.3 The `before:` hook — validation

```ts
// hooks/validate-coating-spec.ts
import { defineHook, HookVeto } from "@carbon/extension-sdk";

export default defineHook("inventory.receipt.posted", "before", 1,
  async (ctx, payload) => {
    for (const line of payload.lines) {
      if (!line.itemTags.includes("coated")) continue;
      const aug = await ctx.ext.receiptLine.get(line.id);   // typed from manifest
      if (!aug?.coatingSpec) {
        throw new HookVeto(
          `Line ${line.lineNumber}: coating spec is required before posting a coated part.`
        );
      }
    }
  });
```

Posting a receipt with a coated part and no spec now fails with that message, inside the core transaction — nothing to clean up.

### 9.4 The workflow

The `inspectOnReceipt` workflow from §5.1, with the SLA read from settings: `timeout: ctx.settings.dispositionSlaHours * HOUR`. The platform persists the run at `createInspection`, parks it at `disposition` for up to 72h, resumes when quality dispositions the inspection (a core event — the extension didn't build the disposition UI, core Quality owns it), and on `fail` quarantines stock and opens an NCR **through the contract services**. If `moveToQuarantine` permanently fails after retries, the declared compensator cancels the inspection so no orphaned pending record survives.

### 9.5 UI

- `ui/slots/receipt-line-panel.tsx` renders coating fields + inspection status on the receipt line detail; the two augment fields also auto-render in the receipt line form via the manifest (no code).
- `ui/routes/inspections.tsx` is a queue page at `/x/coating-inspection/inspections`, built from `@carbon/react` components, gated by the `coating-inspection_inspect` permission.

### 9.6 Lifecycle

```
carbon ext test          # migrations from 0 and from v2; golden receipt.posted@1 fixtures;
                         # workflow happy path, timeout path, compensation path — real Postgres
carbon ext publish       # manifest + contract tests enter the registry corpus
# customer:

```

Six months later core ships 5.0 and reshapes receipt internals. The corpus gate ran this extension's suite against the RC; `inventory.receipt.posted@1` still delivers (via the core-maintained adapter, flagged deprecated). `carbon upgrade` reports "compatible, 1 deprecation warning." The shop upgrades over lunch. **That is the entire product.**
