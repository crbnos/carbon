# Grill: multi-jurisdiction tax spec refresh (2026-10-16)

Target: the refreshed spec that replaces `.ai/specs/2026-07-03-multi-jurisdiction-tax.md`.
Scope set by the user: deliver the full spec, including the Xero integration.
Research: `.ai/research/2026-10-16-purchase-tax-recovery-and-xero-tax-mapping.md`.

Each resolution below moves into the spec's Open Questions section when the spec is written.

## Resolutions

- [x] **1. How does a tax code mark recoverability?** — **Answer:** A recoverable percentage on each tax code component, from 0% to 100%, default 0%. One code covers partial recovery (the 50% car lease). Business Central, Acumatica and Odoo use this model. The receipt keeps the recoverable share of the purchase order tax out of the received unit cost. The purchase invoice posts the recoverable share to the Tax Paid account (see 2). The non-recoverable share stays in cost, as today. A 0% code posts exactly what Carbon posts today.
- [x] **2. Which account holds recoverable tax, and do the tax defaults get new names?** — **Answer:** Adopt Odoo's four names. Rename `accountDefault.salesTaxPayableAccount` to `taxReceivedAccount` ("Tax Received", current liability). Rename `accountDefault.purchaseTaxPayableAccount` to `taxPaidAccount` ("Tax Paid", current asset). The Phase 2 settlement uses two new defaults, `taxPayableAccount` (net owed) and `taxReceivableAccount` (net refund due), in place of one `taxSettlementAccount`. `reverseChargeSalesTaxPayableAccount` keeps its name. New companies get seeded accounts with these names and classes. The migration renames the columns only. It does not rename or reclassify an existing company's accounts, because it would have to find them by number or name. Each column rename adds a `LIVE_COLUMN_RENAMES` entry (`packages/jobs/src/backups/renames.ts`) and updates the glossary entries. The user rejected "input tax" / "output tax" as unclear. Source: Odoo 17 `account.account-generic_coa.csv` (1310 Tax Paid, 1320 Tax Receivable, 2510 Tax Received, 2520 Tax Payable).
- [x] **3. Which documents get tax codes?** — **Answer:** Every sales and purchase document except card charges and reimbursements. In scope on the sales side: quotes, sales orders, sales invoices, rental agreements and their charges, customer contract lines and fixed asset sales. In scope on the purchase side: supplier quotes, purchase orders, purchase invoices, lessee lease invoices (from the supplier's code) and fixed asset purchases. Memos are in scope too (question 5). Out of scope: `chargeLine` (Ramp card charges) and `reimbursementLine`. They keep tax inside the amount, and the providers keep sending "No VAT". Reason: Ramp sends no tax data, so each card line needs manual coding, and the expense posting paths all change. That work gets its own follow-up spec.
- [x] **4. Is header shipping taxed?** — **Answer:** A `taxesShipping` flag on `taxCode`, default off. Posting already allocates header shipping across lines by weight (`allocatedHeaderShipping`, `packages/database/src/sales-posting-amounts.ts`). If a line's code has `taxesShipping` on, the line's share of header shipping joins the line's tax base. With the flag off, header shipping stays untaxed, as today. This replaces the July company setting `shippingIsTaxable`, because one company can sell into a state that taxes shipping (Texas) and a state that does not (California). The posting-corrections spec's "no header-shipping tax switch" kept tax stable during that fix only. That spec leaves tax determination to this spec.
- [x] **5. How does a memo carry tax?** — **Answer:** The user enters a net amount and a tax code. Carbon computes the tax forward with `applyRate` at the currency's decimals. `memo` stores `taxCodeId` and `taxAmount`. `memo.amount` stays the gross that hits AR or AP (net + tax), so the AR/AP views and tie-outs do not change. Posting: debit the reason account with the net, debit Tax Received with the tax, credit AR with the gross. The other direction and party combinations mirror it. A memo made from a source takes the source line's code and rate: RMA credits, rental early-return credits and contract credits. This also fixes the rental early-return credit, which today replays the negative Rent line with no tax unwind (`rental-credit.ts:5-14`). A credit that spans two rates is two memos. The July back-computation (`amount × r/(1+r)`) is dropped, because the posting-corrections spec forbids inferring tax from a memo's gross amount.
- [x] **6. Which accounting providers get tax-rate mapping?** — **Answer:** Xero and QuickBooks Online. Each tax code has one mapping per provider and per direction (sales, purchase), in `externalIntegrationMapping`. Xero maps to a `TaxType` from GET `/TaxRates`. QuickBooks Online maps to a `TaxCode`. Both providers start to send tax on bills and credit notes. Rillet does not change: invoices keep the header `tax_amount`, and bills send no tax. Reason: Xero and QuickBooks Online serve VAT companies, and both build the return from line tax. Rillet is US-only and has no VAT return.
- [x] **7. When does the provider mapping ship?** — **Answer:** In Phase 1, with tax codes and recoverable posting. Tax returns stay in Phase 2. Avalara stays in Phase 3. Reason: if Phase 1 posts recoverable VAT but bills still go to Xero as "No VAT", the Xero VAT return is wrong for every company that uses the feature.
- [x] **8. Does Carbon send its own tax amount?** — **Answer:** Yes. Each line sends Carbon's tax amount and the mapped rate. Before the push, the syncer checks that the amount is within one minor unit of the net × the provider rate's own percentage, as `quickbooks-online/entities/invoice-tax.ts` does. Reason: the provider then agrees with the posted journal, and the check catches a code mapped to a rate with a different percentage.
- [x] **9. What happens with an unmapped code or a line with no code?** — **Answer:** If a line's code has no mapping, the document stops with the retryable Warning `UNMAPPED_TAX_CODES`, which names the code. If a legacy line has only `taxPercent`, the syncer matches the percentage to exactly one active provider rate for that direction (the QuickBooks Online approach today). No match, or more than one match, gives the same Warning. The hard-coded Xero `OUTPUT` and `INPUT` go away. Sync cannot be turned on while an active tax code has no mapping, the same rule as required accounts. This reverses the July rule that unmapped codes fall back to `OUTPUT` / `NONE`. Reason: Katana and Unleashed block on an unmapped rate, and a default rate puts VAT in the wrong return box.
- [x] **10. How does a partly recoverable bill line reach Xero?** — **Answer:** Two lines. The recoverable part (net × recoverable percent) goes at the mapped purchase rate with the recoverable tax. The rest (remaining net + non-recoverable tax) goes at `NONE` on the same account. A UK accountant checks a demo return before release, because no source states the HMRC box 7 treatment for blocked VAT.
- [x] **11. Do Carbon tax returns run when Xero or QuickBooks Online files the return?** — **Answer:** No. With Xero or QuickBooks Online connected and sync on, Carbon keeps `taxLedger` and the liability report but turns off Finalize. The provider files the return and books the settlement once. The MTD spec now states the same rule: the HMRC connector submits only returns that Carbon finalizes.
