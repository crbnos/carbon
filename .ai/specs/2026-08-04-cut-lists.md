## TLDR

Shops that cut bar, tube, plate, or sheet run on **cut lists**: which pieces to
cut, at what dimensions, from which stock, for which jobs. Carbon has no length
or size field anywhere in the schema — it cannot distinguish one 20 ft bar from
three drops totaling the same footage, cannot tell a saw operator what to cut,
and loses heat-number traceability at the first cut.

This spec adds: structured stock dimensions on material items, cut lengths on
BOM lines, a stateful `cutList` document (Draft → Released → In Progress →
Completed), remnant return as dimensioned lots via the existing batch-split
mechanism, a native 1D optimizer (`optimize-cuts` edge function), cross-job
cutting runs, an MES cut-run screen, and per-job cost allocation. 1D is built
in-house; true-shape 2D (DXF) nesting stays external behind a CSV export —
the same line SAP draws.

Neither Odoo nor ERPNext has this (documented unmet demand); Epicor and Global
Shop sell it as paid add-ons; Fulcrum built it natively as its headline fab
feature. Combined with Carbon's QMS story (heat chain from mill cert to finished
part), this is a defensible wedge for metal-fab and woodworking job shops.

## Problem Statement

1. **No dimensioned inventory.** `material.sizes[]` is free-text mapped to
   `item.revision`; there is no numeric length/width/thickness column anywhere.
   144" of bar on hand could be one bar or three drops — `itemLedger` quantity
   can't say, so remnants live in spreadsheets and rack labels.
2. **No cut semantics on the BOM.** `methodMaterial.quantity` is "quantity per
   parent"; a cut length can only be smeared into quantity-in-inches or encoded
   as a separate item revision per length.
3. **Cross-job cutting has no home.** One saw/laser run serves many jobs. Today
   the only trace is the read-only `get_radan_v1` export RPC (Radan integration
   is disabled) and the unbuilt job-operation-batching spec.
4. **Traceability dies at the saw.** The lot-split mechanism in the `issue` edge
   function creates a child `trackedEntity` with genealogy, but the remnant has
   no dimensions, no remnant marker, and heat numbers have no first-class or
   even conventional home.

## Proposed Solution

### Data model (Phase 1 unless noted)

New tables (all with `companyId` composite PKs, audit fields, RLS per convention):

```
itemStockDimension          -- 1:1 with item (the size-variant item, D1)
  itemId, companyId, stockLength, stockWidth, stockThickness,
  unitOfDimension, isMetric

cutList                     -- the stateful document
  id ('CL' prefix), companyId, locationId, processId, workCenterId?,
  status: Draft|Released|InProgress|Completed|Cancelled,
  kerf, endTrim, gripMargin, minRemnantLength, unitOfDimension,
  notes, assignee

cutListLine                 -- one demand line = piece length × qty for a job
  id, companyId, cutListId, jobId, jobMaterialId, itemId (material),
  pieceLength, pieceWidth?, quantity, quantityCut, status

cutPattern                  -- Phase 2; one stock unit's cut sequence
  id, companyId, cutListId, stockItemId, trackedEntityId?,
  sequence, pattern (jsonb: ordered cuts -> cutListLine refs),
  expectedRemnant, actualRemnant
```

Changes to existing tables:

- `methodMaterial` / `quoteMaterial` / `jobMaterial`: add `cutLength`,
  `cutWidth`, `grainLocked` (nullable; only meaningful for dimensioned
  materials). Flows through `get-method` copies.
- `process`: add `isCuttingProcess` + `defaultKerf`, `defaultEndTrim`,
  `defaultGripMargin`, `defaultMinRemnantLength` (D3).
- `materialForm`: add `dimensionality` (`1D` | `2D`) — drives which cut fields
  and which optimizer apply (bar vs sheet).
- `trackedEntity`: no schema change; remnants use reserved attribute keys
  `remnant: true`, `length`, `width`, `heatNumber` via `batchProperty` (D2).
- `itemLedger`: new `itemLedgerDocumentType` value `Cut List Consumption`.

### Lifecycle

```
Draft ──release──▶ Released ──start──▶ InProgress ──confirm──▶ Completed
  │                   │                                (consume stock lots,
  └──cancel──▶ Cancelled ◀──cancel─────┘                create remnant lots,
                    (unreserve stock)                   allocate cost per job)
```

Postings happen once, at confirmation — the SAP trim-sheet-order pattern.
Confirmation extends the `issue` edge function's existing split machinery:
consume the source lot per-job (`Cut List Consumption` ledger rows), split the
remainder into a child `trackedEntity` stamped with `remnant/length/heatNumber`
attributes. Remnants below `minRemnantLength` post as scrap with a reason.

### Cross-job cutting runs (Phase 2)

A planning surface pools open cut demand across released jobs, grouped by
**material item + machine (process) + date window**, and builds one `cutList`
serving N jobs. Every `cutListLine` keeps `jobId` + `jobMaterialId`, so
completion, costing, and traceability fan back per job.

### Optimizer (Phase 2)

New `optimize-cuts` Supabase edge function (module-scope pool, zod payload,
`requirePermissions` — the `schedule`/`mrp` template). Engine in
`functions/lib/cutting/`: pure, deterministic, unit-tested first-fit-decreasing /
best-fit-decreasing over individual stock records (remnants sort first), with
kerf / end trim / grip margin / min-remnant parameters. Column generation is a
later upgrade, only if measured yield justifies it. Rectangular guillotine 2D
for sheets is Phase 3. True-shape DXF nesting: never in-house; CSV export
(generalizing `get_radan_v1`) is the contract.

### MES execution (Phase 2)

One cut-run screen per `cutList` in `apps/mes`: pull list (scan lot to verify),
pattern sequence, mark cuts done per pattern, record actual drop dimensions
(pre-filled from plan), scrap with reason, print piece/remnant labels (ZPL via
existing print queue). Completing the run fans out quantity completion and
material consumption to every served job.

### Documents & labels (Phase 1)

- `CutListPDF` via the block-registry pattern (`packages/documents`), like
  `JobTravelerPDF`.
- Cut-list block on the job traveler (gated by a company setting, like
  `includeMaterialsOnTraveler`).
- Piece + remnant ZPL labels with QR (part, job, heat / dims, material, heat,
  parent lot).

## Phases

| Phase | Ships | Gate |
|---|---|---|
| 1 — Foundation | `itemStockDimension`, cut fields on BOM lines, manual `cutList` + `cutListLine`, confirmation with remnant return + labels, `CutListPDF` + traveler block, heat-number batch property | Ungated |
| 2 — Optimization & execution | `cutPattern`, `optimize-cuts` engine + edge fn, cutting-run builder (cross-job), MES cut-run screen, per-job cost allocation + yield variance, length-aware shortfall | `CUT_LISTS` (Business/Partner) |
| 3 — Commercial loop | Quoting pieces-per-stock math, purchasing requisitions from shortfall + stock-length yield comparison, rectangular 2D, CSV export/import contract | `CUT_LISTS` |

## Non-Goals

True-shape DXF nesting engines; saw/machine control (TigerStop-class); coil
processing; glass-style mid-run re-optimization.

## Interaction with Job Operation Batching

The batching spec (2026-07-03, in-progress) groups job operations on a batchable
process; a cutting run groups *cut demand* and produces patterns + remnants.
Resolution: **cutting processes are excluded from generic operation batching**
(`isCuttingProcess` processes don't show on the batch planning board); the
cutting-run builder is their dedicated surface. Shared UI ideas (material-property
filters, drag grouping) may be reused, but the data models stay separate —
`jobOperationBatch` has no dimensions, patterns, or remnants.

## Success Criteria

- Yield per run computed and stored; trending visible per material class.
- Remnant lots carry dims + heat and are consumable by scan; reuse rate queryable.
- Zero unallocated cut-run cost after confirmation.
- Lot→heat chain unbroken through splits, including remnant-sourced parts.
- Phase 1 usable with zero optimizer: manual cut list in, labeled remnants out.
