Client query cache and realtime broadcast

Cached lists never go stale, pages miss changes, and each cold load fetches five whole tables. The ERP and the MES get one client cache and one realtime system that Postgres drives by broadcast. Operational pages update live in both apps, and a cold load with no change fetches no table.

The picture

The problem

The 27 cached api+ routes read with getQueryData, which ignores staleTime and invalidateQueries. So a cached list never goes stale. 78 route files each export a clientAction that names the keys to invalidate.

A page can miss the changes of a table it shows. RealtimeDataProvider reads five whole tables from the browser on each cold load, about 950 ms each.

postgres_changes does one permission check for each subscriber for each change, on one thread for all tenants.

Example

Jane Doe completes an operation for job J-001 in the MES. The ERP job page has no subscription on jobOperation or job. So the planner sees the old status until a reload.

How it works

Part 1 — Query cache

  1. A cached api+ route exports cachedClientLoader<typeof loader>().
  2. The loader reads with fetchQuery, so staleTime and in-flight dedupe apply.
  3. One root middleware runs after each request.
  4. If the method is GET or the path is /refresh-session, the middleware does nothing.
  5. Otherwise the middleware marks every LOADER entry stale.

Part 2 — Realtime by broadcast

  1. A statement trigger calls broadcast_table_changes.
  2. The function sends { table, op, ids } to the private topic company:<companyId>:<table>.
  3. A policy on realtime.messages lets only an employee of that company join the topic.
  4. A route declares its tables in handle.realtime.
  5. useRouteRealtime() in the shell subscribes to one channel for each declared table.
  6. On a message, the hook starts a 300 ms debounce timer.
  7. If a fetcher is submitting when the timer ends, the hook waits for it.
  8. The hook marks the LOADER entries stale. Then it revalidates the page.
Reference lists and notifications

The tables behind the cached reference lists use broadcast_reference_changes. It sends { table, op } to one shared topic, company:<companyId>:reference. The shell marks the LOADER entries stale on each message.

useNotifications subscribes to user:<userId>:notification. On an INSERT or UPDATE, the hook reads the rows with those ids through PostgREST. On a DELETE, the hook removes the rows with those ids.

useRealtime(table, filter?) stays for a component that is not a route. If the filter names id, the hook compares the message ids with the filter ids. If the filter names another column, the hook wakes on any change to the table.

Part 3 — Live lists, cold load

  1. useLiveList reads the list and its checksum from IndexedDB.
  2. The hook puts the list in the query cache.
  3. The hook calls the list_checksums function.
  4. If the checksum matches, the app fetches nothing.
  5. If the checksum differs, the hook fetches the list in full.
  6. The hook writes the list and the new checksum to IndexedDB.
What a broadcast message does to a list

If ids is null, the hook runs the checksum steps again. If op is DELETE, the hook removes those rows from the cache. Otherwise the hook reads those rows through PostgREST, merges them, sorts, and writes the list to IndexedDB. A reconnect runs the checksum steps again.

Part 4 — Component hooks

  1. useLoaderQuery(url) reads an api+ URL through useQuery, on the same key as the loader.
  2. useAction({ onSuccess, onError }) wraps useFetcher. It returns submit, isPending, data and pending.

Before and after

  1. Reference lists: a cached route keeps its first result for the whole session.
  2. Mutations: each of 78 routes names the keys to invalidate. A route that forgets one leaves a stale dropdown.
  3. Page updates: the ERP job page does not show an operation that the MES completed, until a reload.
  4. Realtime lists: each cold load reads item, supplier, customer, employees and itemSupersession in full.
  5. Components: 137 call sites load with a fetcher in a mount effect. 435 submit call sites use useFetcher.
  1. Reference lists: an entry goes stale after staleTime, after a mutation, and after a change by another user.
  2. Mutations: one root middleware marks every loader entry stale. No route names a key.
  3. Page updates: the ERP job page shows the completed operation within 3 seconds, with no reload.
  4. Realtime lists: a cold load with a matching checksum sends 1 list_checksums request and reads no table.
  5. Components: five pickers on one page share one request. useAction gives the pending state with no effect.

Decisions

How does the cache name an entry? By URL: [LOADER, companyId, pathname, search].

Why: React Router's own client-cache guide keys by URL. A route author writes no key.

What goes stale after a mutation? Every LOADER entry.

Why: It costs one extra fetch when a list is next used. It removes 78 hand-written invalidations and the key registry.

Does the cache hold page data? No.

Why: A route with a clientLoader leaves the combined .data request. dataStrategy is closed in framework mode.

Which realtime transport? Broadcast from the database.

Why: Realtime checks permission one time at join. postgres_changes checks each change for each subscriber on one thread.

What does a message hold? { table, op, ids }, with ids null above 100 rows.

Why: The client reads rows through PostgREST, so table RLS still decides what a user sees.

How fine is a topic? One topic for each company for each table.human

Why: A caller with a parent-column filter wakes on any change to the table. The debounce bounds the cost.

Which tables get a trigger? Only tables that a route or a live list declares.human

Why: A table that no page watches gets no write overhead and stores no messages.

Which pages update live? Operational pages in the ERP, all of the MES, and the cached reference lists.human

Why: Settings and admin pages change rarely. They reload on navigation as today.

How do reference lists hear a change? One shared topic, company:<companyId>:reference.

Why: One channel for each client covers every reference table. A topic for each table would hold about 30 channels open.

Where does a trigger attach to a table? In event-system/attachments.ts, applied by set_event_triggers.human

Why: Each attach call replaces the whole list of a table. One typed manifest removes the clobber risk. No migration attaches a trigger.

Where do the interceptor bodies live? In managed files under event-system/handlers/.human

Why: The 63 interceptors and apply_item_stock_quantities leave the migrations. authz sync and authz migration own them.

How does a missed declaration show? The new realtime-table-has-trigger check fails the build.

Why: postgres_changes fails silently for an unpublished table.

When do tables leave the publication? In this PR.human

Why: A tab on the old build goes quiet until a reload. It shows no error.

What stays on postgres_changes? Nothing.human

Why: The publication ends empty. No second realtime system stays in the code.

How do notifications travel? A private topic for each user: user:<userId>:notification.human

Why: A company topic would wake every employee for each notification of each other employee.

How does a cold load avoid the table fetches? A change log names the rows that changed.human

Why: The client reads only the rows that changed since its stored copy. A checksum refetches a whole list when one row changes.

Who may the checksum function read for? SECURITY INVOKER: the calling user.

Why: The hash must cover the rows that this user can read. The same RLS applies to the list fetch.

Where do the lists live? The query cache, key ["live", companyId, <list>].

Why: One store holds the server data. nanostores has no other user after this change.

How far does useAction go? Pending state and callbacks only.human

Why: Mutations stay plain router actions. Optimistic cache writes are out of scope.

Where does the shared code live? @carbon/react.

Why: Both apps need the hooks. The no-duplicated-app-file check forbids a copy in each app.

What breaks for existing users? One thing: the publication drop.

Why: The API, the MCP tools and the webhooks do not change.

Data model

The change adds no table and no column. It adds four functions, two policies on realtime.messages, and one statement trigger set for each watched table.

  • itemSupersession and itemStockQuantities have no id column. Their messages carry ids: null.
  • implementationHub has no companyId column. The function reads the company from id for this table.
  • itemLedger keeps its existing handler, apply_item_stock_quantities, beside the new one.
  • The 3 broadcast functions are managed files. They ship through authz migration.
  • The authz manifest owns the 2 policies on realtime.messages, under the key "realtime.messages".
  • The migration drops each moved table from the supabase_realtime publication.

Done when

  • An operator completes an operation in the MES. The ERP job page shows it as complete within 3 seconds, with no reload.
  • A user adds a customer type. The picker on another open form shows it after the save, with no reload.
  • A second user in the same company adds a customer type. The first user's picker shows it within 3 seconds.
  • A cold load with a matching checksum sends 1 list_checksums request and 0 requests to the five list tables.
  • A cold load after another user renames a customer refetches customer only.
  • A user deletes an item while a second user's tab is closed. The second user's list lacks that item after the next load.
  • A notification for user A shows in user A's bell within 3 seconds. User B cannot join user:<A>:notification.
  • The supabase_realtime publication holds 0 tables.
  • A user in company A cannot join company:<B>:item. The subscribe call returns an error.
  • A user switches company. No list and no cached loader entry from the first company appears.
  • An update that changes only updatedAt on item sends no message.
  • A bulk update of 10,000 item rows sends 1 message for each company, with ids null.
  • A realtime message during a fetcher submit does not cancel that fetcher's redirect (MES "Complete Batch").
  • No file under apps or packages imports nanostores.
  • No file under apps or packages contains postgres_changes.
  • No route exports a clientAction that only invalidates.
  • The realtime-table-has-trigger check fails when a route declares a table that REALTIME_TABLES lacks.
  • event-dispatch.test.ts fails when the ignored-column list in broadcast_table_changes.sql differs from auditConfig.skipFields.
  • The local stack and the self-hosted compose stack (Realtime v2.89.0) both deliver a broadcast on a private channel.
  • The typechecks for erp, mes, @carbon/react, @carbon/database and @carbon/checks pass, one at a time.
  • pnpm run lint and pnpm run test pass.

Terms

Reference list
A list that a cached api+ loader returns, for example customer types.
Realtime list
One of four lists that the app keeps current: items, customers, suppliers, people.
LOADER entry
A query cache entry with the key [LOADER, companyId, pathname, search].
Topic
The name of a private channel that a client joins to get broadcast messages.
Publication
supabase_realtime, the list of tables that postgres_changes can deliver.
Checksum
A hash of the ids and list columns of one list, for the rows this user can read.
Cold load
The first load of the app in a tab.
handle.realtime
The list of tables that a route shows, declared on the route.
