Page-Level Permissions

Today an admin grants access to whole modules, and each person gets a copy of their role that never updates. The change grants one level on each of 158 pages, lets a person's override add or remove access, and computes access at every check. Every module switches in one deploy, and a role edit reaches everyone with that role at once.

The picture

Scope

In scopeOut of scope
  • The page registry and typed page keys
  • Levels per module, with exceptions per page
  • Role grants, person overrides and API key grants
  • One resolver in SQL and TS, with shared test cases
  • The role grid, the person's Access tab and the API key grid
  • The access view and role audit events
  • All 14 modules with a sidebar: 158 pages, switched in one deploy
  • Pages that share a table, enforced by the column that tells them apart
  • Named actions on a page, such as post or approve
  • Planned, not built: API keys that take a role, portal roles, access scoped to a location, starter roles

The problem

A permission attaches to one of 17 modules, so an admin cannot grant one page of a module. At invite, Carbon copies the employee type's permissions into the person. A later edit of the type reaches nobody who already has it. Five separate pieces of code decide access, and nothing proves that they agree.

Example

Jane Doe is a receiving clerk. The admin wants her to post receipts and nothing else in Inventory. Today the admin must give her Inventory, which also opens Shipments and Inventory Count. Later the admin edits the "Receiving" type, and Jane's access does not change.

How it works

  1. The registry in code lists each module's pages, their highest level and their tables.
  2. An admin gives a role one level per module: None, View, Create, Edit or Full.
  3. The admin can set a different level on single pages of the module.
  4. A person can have overrides on a module or a page. An override can add or remove access.
  5. At a check, the resolver takes the first grant that exists: person page, person module, role page, role module.
  6. The level expands to actions: Edit holds view, create and update; Full adds delete.
  7. The top-level nav shows a module when the person has View on any of its pages.
  8. Reference data that every employee may read needs only the "employee" permission.
  9. Pages that share a table, such as the five item types, are told apart by a column RLS checks.
  10. A gate names a page and its lowest level, such as { "inventory.receipts": "Edit" }. The database keeps action keys such as inventory.receipts_update.
  11. Every app authenticates with one function, authorize(request, gate?) from @carbon/auth/auth.server. It returns the caller and api, the service functions bound to that caller.
  12. Every module moves to page keys in one deploy; after it, no check names a module key.

Before and after

The admin edits the "Receiving" type to remove Shipments. Jane Doe and 13 other clerks keep Shipments, because each holds a copy made at invite. The admin bulk-edits the 14 people one by one. Jane still cannot hold Receipts without the rest of Inventory.

The admin sets the "Receiving" role: Inventory at None, Receipts at Edit. On the next request all 14 clerks see only Receipts in Inventory. One audit event records the role, the page, the old and new level, and 14 people affected. Jane needs Shipments for one week, so the admin gives her a Shipments override at View.

Decisions

How is access worked out? At every check, from the grants. No stored copy.human

Why: RLS runs the helper once per statement, so the cost is small. With no copy, nothing can go stale and nothing needs a backfill.

Ladder or checkboxes? Levels: None, View, Create, Edit, Full.human

Why: one choice per page, and no create-without-view state. The order is NetSuite's. A page can cap its highest level.

Can an override remove access? Yes. It adds or removes, and it wins over the role.human

Why: the admin can make a one-person change without a one-person role, as with NetSuite Global Permissions and Infisical folder grants.

What is a page? One page per distinct sidebar path: 158 pages in 14 modules.human

Why: the grid matches what the admin clicks. Documents has five entries on one path, so it is one page.

Which modules? All 14, in one deploy.human

Why: the user chose it. No time exists when a page key and a module key decide the same access.

Is each item type its own page? Yes, and RLS checks item.type.human

Why: a split the database does not enforce is a promise the API breaks. Child tables check the type of their parent item. The same rule covers memo.direction.

How do today's checkboxes convert? Round up to the lowest level that covers every flag, with a report.human

Why: nobody loses access on deploy day. An admin lowers anything the report marks "grew".

Do API keys get page levels now? Yes, the same grid and grants as roles.human

Why: one model, and a key can be limited to one page. accounting_delete stays opt-in: "Select all" never sets Full on Accounting pages.

What is in the first version? Six items; four extensions planned; named actions out.human

Why: module level with page exceptions, one resolver, typed keys, the sidebar, the access view and role audit events make the rest smaller.

Do module keys survive? No. A conformance check fails one after the switch.

Why: before the switch a module's one page has the module's name. The nav uses holdsAny instead.

What does a gate look like? A page and its lowest level: { "inventory.receipts": "Edit" }.human

Why: admins set levels, so code asks for levels too. { create: "parts", update: "parts" } meant { parts: "Edit" }. The database keeps action keys, and each action maps to one level.

How does a route authenticate? With one authorize; the Onshape panel with authorizePanel.human

Why: carbon, carbonFor and requirePermissions did one job. The panel keeps its own cps_ token, so a leaked panel token reaches only the panel routes.

Where do module settings pages go? They stay in Settings, such as settings.inventory.

Why: they need settings today, and page grain already lets an admin grant one of them.

How many tables hold permissions? One: permission, with three subject columns.human

Why: exactly one subject column is set, and each is a real foreign key, so deletes cascade and backup restores rewrite the ids.

Does the database hold a copy of the registry? No.

Why: a page key carries its module, so the resolver needs nothing else. Grant writers clamp a level to the page's maxLevel.

When do the grants and the editors ship? Together, in one release.

Why: once the resolver reads grants, the old editors would write tables that nothing reads.

How does an Admin type resolve? Full on every page, with no grant rows.

Why: a page or module added later is covered with no migration.

How do pages read reference data? "employee" for tables every employee may read.

Why: it matches RLS, and Odoo and Business Central do the same. A restricted table uses anyOf the views of the pages that read it.

Do postings change? No.

Why: the gate checks the source document, then the posting writes ledgers as the system — Business Central's "indirect" permission.

Where does the code live? Registry and resolver in packages/database/src/access/; authoring in @carbon/ee.

Why: RLS, @carbon/auth and @carbon/api all import @carbon/database. Authoring stays behind requireEntitlement.

How do routes name their page? Explicitly, in requirePermissions, typed.

Why: explicit and greppable, the same pattern as today.

Rejected: a gate derived from the URL.

Who edits grants? Edit on users.employeeTypes, users.accounts or settings.apiKeys.

Why: these are the pages where an admin edits each subject today. The resolver is SECURITY DEFINER.

Which public contracts change? MCP ToolPermission gains page; apiKey.scopes becomes grants.

Why: a tool gated on a page must say so to describe_tool. Both go in the changelog.

Data model

One table, permission, holds every grant: a role's, a person's override and an API key's. The migration converts today's checkboxes into rows and keeps the old checkboxes in convertedFrom, so the access view can list every row that grew.

Done when

  • A role with Inventory at View and Receipts at Edit lets a person create and edit a receipt; shipment writes refuse.
  • A Receipts override of None shows "Access Denied" on Receipts, and the receipt service functions refuse.
  • A role edit from Edit to View reaches every person with the role on the next request.
  • Tools at Edit with Parts at View lets a person change a tool's cost but not a part's, in the app, the API or PostgREST.
  • Credit Memos at Edit with Supplier Credits at View: a supplier credit update fails everywhere.
  • An MES operator with Production Jobs at Edit only starts and completes a job operation in MES.
  • A page added after the migration goes to every role whose Inventory level covers it.
  • The Admin type has Full on every page, including a page added after the migration.
  • A person with View on Receipts only sees Inventory in the nav and only Receipts in its sidebar.
  • A role with view and update but no create becomes Edit, and the report lists it as "grew".
  • An API key with Receipts View reads receipts and gets 403 on a receipt create.
  • "Select all" on the API key grid leaves every Accounting page below Full.
  • A buyer with no level on Payment Terms selects payment terms on a purchase order.
  • A customer portal account gets forbidden from an "employee"-gated service function.
  • Every row of cases.json passes against holds and the SQL resolver.
  • { "inventory.receiptz": "Edit" } fails typecheck, and a module in a gate fails the module-key check.
  • Every app route authenticates with authorize; requirePermissions is not exported from @carbon/auth.
  • The access view shows each page's level and source, and lists everyone with Edit on Receipts.
  • A role edit writes one audit event with the affected count.
  • The SQL helper adds less than 1 ms to a receipts list query.
  • The item-type check adds less than 5 ms to an update of 1,000 item cost rows.

Terms

Page
One sidebar entry of a module, such as Receipts; access attaches to it.
Level
One of None, View, Create, Edit and Full; each level holds every action of the levels below it.
Role
An employee type; it holds a level per module and exceptions per page.
Grant
One row of the permission table: it gives a role, a person or an API key one level on a module or a page.
Override
A person's own grant; it wins over the role and can add or remove access.
Page registry
The list of modules and pages in packages/database/src/access/registry.ts.
Resolver
The function that answers "does this person hold this action here", in SQL and in TS.
Gate
The access a route or service function needs: each page it names and the lowest level there.
Page key
An action key of the form inventory.receipts_update, as RLS and the claims use it.
Module key
A permission key of the form inventory_update; no check names one after the switch.
"employee"
A service function permission that admits any employee or API key of the company and refuses portal accounts.
RLS
Row-level security: the Postgres policies that decide which rows a caller reads and writes.
Indirect permission
A posting writes ledgers as the system after the gate checks the source document.
