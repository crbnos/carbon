## Reading of the request (autonomous mode)

**What:** after applying any of the four demo datasets, every ERP and MES screen a user can open shows meaningful, editable data — not just "every status appears somewhere". **Why:** the user opened the app and found whole screens empty (customer portals, sales rules, MES schedule, Production › Forecast / Priorities, resource and material planning) and only 8 jobs; the previous pass verified status coverage, never screens. **Where:** the dataset engine + data packs, the dataset wipe, a post-commit planning step (MRP + scheduler) for the two callers that commit (template job, dev CLI), and the commit gate. **Who:** anyone applying a demo template (onboarding, Settings › Demo Data, `pnpm db:seed:dev`). Constraints carried over: files excluded, FK integrity, no regressions, invalid demo data blocks the commit, autonomous mode, never commit without asking, never rebuild the DB.

## Goals

1. Every screen classified EMPTY or FILTERED-EMPTY in the five research audits renders rows after a real apply of each dataset, except the documented exclusions (Non-goals).
2. Planning screens are populated by the **real engines**: MRP (`runMrp`) and the scheduler (`runLocationSchedule`) run once, post-commit, after every template apply and every dev-CLI seed.
3. The shop floor looks alive: ≥ 18 jobs per dataset with open work due within −3…+21 days of today, spread over every work center, with priorities, assignees, running production events and recent completions.
4. Three pre-existing apply failures on used companies are fixed (intercompany partners, posted card transactions, model-only step slides); the accounting-period fix stays.
5. Every new shape is pinned by `validateDataset`, `REQUIRED_*` sets and `COVERAGE_FLOORS`, so a regression blocks the commit.

## Non-goals

- **Files** (user-excluded): documents, logos, backups, attachments, inspection-plan drawings/balloons, step-slide images.
- **New global `user` rows** (synthetic employees / console operators / portal accounts) — see Autonomous Decision H3.
- **Audit log** — needs a per-company DDL table (`create_audit_log_table`) the wipe cannot manage.
- **API keys** — a fake hash would be a non-working credential in a security screen.
- Integrations, SSO, billing, subsidiaries/ITAR (env- or credential-gated); home "recents" (browser localStorage).
- Real intercompany / card-transaction data (integration-coupled) — the wipe now refuses such companies instead.
- Changing app code to make empty-by-design defaults nicer (e.g. maintenance lists defaulting to the first location) — seed around it.

## Design

### A. Wipe (applies to all callers)

| Case | Behaviour |
|---|---|
| `accountingPeriod` (done, uncommitted) | preserved; tier 09 adopts a month's existing period by `(fiscalYear, periodNumber)`, else by `startDate` |
| model-only step slides | `assemblyInstructionStepSlide`, `methodOperationStepSlide`, `jobOperationStepSlide`, `quoteOperationStepSlide` deleted before the FK-nulling pass (their content CHECK cannot survive it), like `TRANSIENT_MRP_TABLES` |
| intercompany customers/suppliers (`intercompanyCompanyId` set) | refuse up front, before any write: "This company trades with other companies in its group … demo data can only be applied to a company without intercompany partners." |
| Posted/Voided `cardTransaction` | refuse up front: "This company has posted card transactions, which cannot be deleted …" |

Refusals are thrown as a named `Seed:` error from a `preflight` inside `wipeCompanyBusinessData`, so the template job's marker gets `failed` + the message and nothing is written.

### B. Seed data + tier extensions (all four datasets)

Grouped by screen. "Tier" = engine shape to add; everything else is data in `data/<key>/`.

**B1 Production floor (tier 06, production.ts)**
- Open jobs re-dated to due −3…+21 (existing open jobs moved; validator chronology kept).
- ≥ 10 additional released jobs (Ready/In Progress) of short-routing items per dataset, touching every work center; 1 released job with no due date (Priorities › Unscheduled); 2 make-to-stock jobs (`salesOrderId` NULL).
- Distinct `job.priority`; `job.assignee` / `jobOperation.assignee` = applying user on ~6 open items.
- 3 jobs Completed within the last 3–25 days with Setup/Labor/Machine `productionEvent`s (completion-time + estimates-vs-actuals KPIs); open events (`endTime` NULL) today on 3–4 work centers.
- `jobOperationStepRecord` for done ops; `jobOperationParameter` / `jobOperationTool` on a few ops; one Final Inspection op `operationType='Inspection'` + `inspectionDocumentId`; ROB-style assembly op linked to the seeded assembly instruction (`methodOperation`/`jobOperation.assemblyInstructionId`).
- One batchable process; an Active `jobOperationBatch` with ≥ 2 members from different jobs.
- Procedures: one Active, one Archived, rest Draft (versions); make methods of seeded items Active; assembly instruction published state.
- `pickMethod` default shelf per stocked item at the plant.

**B2 Planning (tier 12 + post-commit step)**
- Engines run post-commit (Section C) → `demandActual/Forecast/supplyActual/Forecast`, `capacityReservation`, op start/due dates, dependencies.
- `peopleAssignment` for the current week and a `peopleAbsence`; shifts created at the **plant** (not HQ) + `workCenterShift` links; the applying user's `employeeJob` upserted (it is a silent no-op today when missing) with location = plant, title, department, shift, start date.

**B3 Sales & purchasing (tiers 02, 04, 05)**
- `enforcementRule` family `sales` (item-targeted, warn + error) with item assignments; family `storage` and a work-center rule with assignments.
- Customer portals: `externalLink` documentType `Customer` for 2 customers.
- `approvalRule` (PO tiers + supplier) and Pending `approvalRequest`s for the Needs-Approval PO and the Pending supplier.
- Quote methods: each Make-to-Order quote line gets its item's method copied (`quoteMakeMethod`/`quoteMaterial`/`quoteOperation`) — reverses 2026-09-22 Decision 9.
- Configurator: one configurable item `requiresConfiguration=true`, a `configurationRule`, one configured quote line.
- `assignee` on a few open quotes/SOs/POs/RFQs; supplier `status` on every supplier; `createdAt` spread over past offsets for quotes/RFQs/supplier quotes; 2 more pricing rules; customer/supplier bank accounts if the table is tenant data.
- Return orders: memos linked (`salesReturnOrderId`/`purchaseReturnOrderId`) with credit lines; `nonConformance{Sales,Purchase}ReturnOrderLine`.

**B4 Invoicing & accounting (tiers 04, 05, 09)**
- `postingDate` = `dateIssued` on every non-Draft invoice (fills Receivables/Payables/aging).
- Posted journals shaped like the posting paths: `Sales Invoice` (AR/Revenue), `Purchase Invoice` (Inventory|Expense/AP), `Payment` (Cash vs AR/AP, `payment.journalId` set), plus one `Opening Balance`, with `accountingPeriodId` set (periods now survive the wipe). Aging spread over Current / 1–30 / 31–60 / 61–90.
- Draft Receipt + Draft Disbursement payments (apply UI).
- `costLedger` rows paired with posted receipt/shipment ledger rows; `itemCost.unitCost` non-zero.
- AR/AP billing-address rows.

**B5 Quality, maintenance, resources (tiers 07, 10)**
- `nonConformanceWorkflow` ×3 linked from NCRs; `nonConformanceItem` on every NCR; NCR `assignee`; `nonConformanceSupplier` on a supplier NCR; `nonConformanceActionProcess`; `procedureParameter`.
- `QualityData.inspection` becomes a list: Passed receipt lot, Pending lot, Job Operation lot.
- Maintenance: `maintenanceDispatchItem.unitCost`; a Reactive dispatch on a production-event day; 2 back-dated Completed dispatches; a Scheduled dispatch due today; an In Progress + Down dispatch; `workCenterReplacementPart`; one HQ work center with a dispatch + schedule.
- `partner` rows.

**B6 Settings & people (tiers 01, 10)**
- `companySettings.timeCardEnabled = true` + one open time-card entry today.
- `userAttributeCategory` → `userAttribute` → `userAttributeValue` for the applying user.
- `itemSerialSequence` per serial-tracked item; 3 `customField`s; `printJob` history. ~~one `active=false` webhook~~ — dropped (D66).

### C. Post-commit planning step

`planDemoCompany({ companyId, userId })` in `@carbon/jobs` (which already depends on `@carbon/planning`): `runMrp(serviceRole, db, { type: "company", … })`, then `runLocationSchedule` for every location with Ready/In Progress/Paused jobs — the same calls the cron and `api+/schedule.ts` make. Callers:
- `companyTemplateFunction`: a new `step.run("plan-template")` after `apply-template`, **non-fatal** (logs + `metadata.planningError`; the 3-hourly MRP cron is the backstop). Revert/finalize unchanged.
- Dev CLI: `seed-dev.ts` (in `@carbon/database`, which cannot import `@carbon/planning` — cycle) spawns `pnpm --filter @carbon/jobs plan:company -- --company <id> --user <id>` after its commit; failure prints a warning and exits 0. `--skip-plan` opts out.

### D. Checks

- `validate.ts`: refs for every new slice field; `REQUIRED_*` for procedure (Draft/Active/Archived), approval request, enforcement-rule family, inspection status list, dispatch shapes; floor rules for "open job due within window", "every work center has open ops", "≥ 18 jobs".
- `coverage.ts`: re-measured floors for every newly written table. Engine outputs (MRP tables, `capacityReservation`) stay OUT of floors (verify.ts rolls back before engines run) and are covered by the screen matrix instead.
- Screen matrix: a script (scratchpad; evidence in `.ai/runs/`) that, against a real seeded + planned company, runs one count query per screen data source with the screen's own filters (from the audits) and asserts non-zero for every in-scope screen, for all four datasets.

## Design Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Engines run post-commit, in-process, non-fatal | real engine output, zero drift; in-transaction run impossible (PostgREST reads + own transactions — research §3a) |
| 2 | Wipe refuses IC partners and posted card transactions | both are immutable by trigger and FK-linked to rows the wipe must delete; preserving them cannot satisfy the trigger |
| 3 | Slides deleted before FK nulling | CHECK `imagePath OR modelUploadId` cannot survive nulling; the slide is business data the wipe deletes anyway |
| 4 | No new global `user` rows | tenancy + identity safety (H3) |
| 5 | Journals authored for posted docs | Revenue/AR/AP would otherwise read $0 on every financial report |
| 6 | Dates stay `DayOffset`; engine output uses the engine's own clock | engines run "now"; seed anchor is "today" — same day |
| 7 | Shifts move to the plant | every work center is at the plant; scheduler + resource planning read plant shifts |

## Acceptance criteria

1. For each dataset, after `pnpm db:seed:dev -- --email demo-audit@carbon.local --dataset <key>` (engines included), the screen matrix reports 0 in-scope screens with 0 rows; evidence `.ai/runs/2026-09-2x-screen-matrix-<key>.txt`.
2. MES operations board for the applying user shows ops on every plant work center, with start dates within ±3 weeks and ≥ 1 running op on 3+ work centers.
3. Production › Priorities shows jobs in the current week and ≥ 1 Unscheduled job; Scheduling › Forecast and Resource Planning show reservations/assignments; both Material Planning screens show week columns with demand.
4. Sales rules, storage rules, customer portals, approval rules, procedures (Active + Archived), configurator all list rows.
5. Income statement revenue ≠ 0; receivables aging has rows in ≥ 3 buckets.
6. The four wipe cases in §A behave as specified in a rolled-back apply against a company constructed in each state.
7. `pnpm --filter @carbon/database typecheck`, `test`, `pnpm db:check:datasets` (all four), `turbo typecheck` for `@carbon/jobs` pass; a real re-apply over a seeded company exits 0.
8. A deliberately broken new ref / removed required status blocks `sh .husky/pre-commit`.

## Autonomous Decisions (high-stakes first)

- **H1 — Reverses 2026-09-22 non-goals.** Approval rules, enforcement rules, demand/supply forecasts, `printJob` and a webhook were out of scope; the user's report puts them in. — **Autonomous:** in scope — rung 1 (user's stated intent: "every feature visible").
- **H2 — Engines outside the all-or-nothing apply (public behaviour of the template job).** Options: (a) run in-transaction (impossible, research §3a), (b) hand-author MRP/scheduler output (drift from the real engine), (c) run post-commit non-fatal. — **Autonomous:** (c) — rung 2 (the cron and `api+/schedule.ts` already run the same functions after commit) + rung 5 (real numbers beat plausible ones).
