# Per-User Notification Preference Settings — Competitor Conventions

Date: 2026-07-14. Scope: UX/data-model conventions for user-level notification settings, to inform Carbon's design. Surveyed: Odoo, NetSuite, ERPNext/Frappe, GitHub, Slack, Linear, Notion, Asana. Grounded in official docs (URLs at bottom).

## Notable Structural Details

- **Linear is the reference UX**: Settings → Notifications lists delivery channels; each channel has a master on/off and, expanded beneath it, per-event-type toggles (with related events bundled into categories like "status changes"). Email adds an immediate-vs-digest frequency choice.
- **ERPNext is the reference ERP data model**: one lazily-created `Notification Settings` doc per user; boolean per event type; two master booleans (`enabled` for bell, `enable_email_notifications`); per-event email fields are `depends_on` the master — hidden/inert while off but values preserved (a true override, not a bulk edit). New event types ship as new default-on fields.
- **Two orthogonal axes everywhere**: (1) *what* — event/category subscription, often with a scoped-override hierarchy (global default → project/repo/record → thread); (2) *where* — delivery channel matrix. Products that conflate them (Odoo's email-vs-inbox router) get the most user complaints.
- **Auto-subscribe on participation** is universal (creator, assignee, @mention → follower), with unfollow as the per-record escape hatch.
- **Slack's pause semantics**: DND/schedule is a temporal overlay that suppresses delivery without touching stored preferences — the only surveyed product with a documented preserving mute-all.
- **NetSuite is the anti-pattern**: admin-authored workflow emails with zero user-side surface; users resort to mail-client filters (same complaint appears on Asana forums).

## Takeaway Conventions (industry consensus)

1. **Two-axis model: event type x delivery channel.** Store a per-user preference matrix (event/category rows, channel columns). Linear and ERPNext do this explicitly; channel-only models (Notion, Asana) are the weaker pattern. Group related events into a small set of categories rather than exposing dozens of raw event types.
2. **The in-app inbox/bell is (almost) never disableable.** Consensus: preferences govern *outbound* channels (email, push, Slack); every notification still lands in the in-app feed. ERPNext and GitHub are the exceptions, but Linear/Notion/Asana/Slack all keep in-app mandatory — safe default for an ERP where notifications carry work (approvals, assignments).
3. **Opt-out defaults + auto-subscribe on participation.** Everything on for new users; creating, being assigned, or being @mentioned auto-subscribes to the record; unfollow is the per-record escape. Opt-in (NetSuite saved searches) leads to missed work.
4. **Master toggles should be preserving overrides, not bulk edits.** ERPNext (master boolean gates per-event booleans, values kept) and Slack DND (temporal overlay) are the clean patterns. Asana's "uncheck everything" destroys user intent. Model as: `emailEnabled` master + per-event settings evaluated only when master is on.
5. **New notification types default ON, gated only by masters.** ERPNext ships new event fields default-on; a user's specific mutes don't suppress new types, but a master-off does. Nobody re-prompts users. Store preferences sparsely (only deviations from default) so new types inherit the default automatically.
6. **A non-suppressible core is standard and expected.** Security/account emails, admin-mandated workflow notifications (NetSuite, ERPNext admin alerts), direct assignments/mentions (Linear, Notion, Asana → inbox). Design an explicit `mandatory` flag on notification types: user preferences apply to channels, never to whether the in-app record exists.
7. **Transactional-notification emails use a signed-in "manage preferences" link, not one-click unsubscribe.** GitHub, Slack, ERPNext all link to settings; one-click List-Unsubscribe is reserved for marketing/digest mail (Odoo marketing, Frappe newsletters). A footer link to the user's notification settings page is sufficient; add List-Unsubscribe only to digest-class mail.
8. **Scoped overrides beat global-only.** GitHub (account → repo → thread) and Slack (account → conversation) layer record/scope-level overrides on the global default. For Carbon, per-record follow/unfollow (Odoo/ERPNext "document follow") is the ERP-native form of this — worth designing the schema so a later per-record override table is additive, not a refactor.
