# How Manufacturing ERPs Model RMAs (Customer Returns)

**Date:** 2026-08-07
**Question:** How do manufacturing ERPs model RMAs / customer returns — document model, lifecycle, reasons/dispositions, receiving, costing, credit, replacements, serial/lot — to inform the design of a Carbon RMA module?

Sources are official vendor documentation unless flagged. Epicor's Kinetic help is behind a customer login (EpicWeb/doc.epicor.com); for Epicor, claims come from Epicor-authored pages plus Epicor "Contextual Help" text republished verbatim by a licensee, flagged below. Anything that couldn't be verified against a primary page is marked **unverified**.

---

## Microsoft Dynamics 365 Business Central

**Two tiers of return processing.** A plain **Sales Credit Memo** handles a return/cancellation with no receipt tracking. A **Sales Return Order** is the heavier document, used "if you need more control of the sales return process, such as warehouse documents for the item handling, or a better overview when receiving items from multiple sales documents with one sales return" — and it "automatically issues the related sales credit memo and other return-related documents, such as a replacement sales order, if needed" ([Process sales returns or cancellations](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-cancellations)).

**Document model & linking.** Header + lines. Lines can be entered manually (blind return — linking is optional) or pulled from history two ways ([Process sales return orders](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-orders)):
- **Get Posted Document Lines to Reverse** — copies lines from one or *more* posted documents (shipments, invoices, return receipts, credit memos); "always exactly reverses the costs from the posted document line". A **Show Reversible Lines Only** filter shows only quantities not yet returned (works for posted shipment/invoice lines only). If part of a line's quantity was already returned/sold/consumed, only the remaining quantity is copied; fully-reversed lines aren't copied at all.
- **Copy Document** — copies one whole document; exact cost reversing only if **Exact Cost Reversing Mandatory** is enabled on **Sales & Receivables Setup**.

**Exact cost reversing (the flag that matters).** "To preserve correct inventory valuation, you typically want to put returned items back in inventory at the unit cost that they were sold at, not at their current unit cost." Mechanically, the return line's **Appl.-from Item Entry** field points at the original item ledger entry; the copy functions fill it automatically, or a user sets it manually on any return line ([inventory costing section](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-cancellations#inventory-costing)).

**Serial/lot.** When copied lines carry item tracking, "the **Appl.-from Item Entry** field on the item tracking lines is filled with the appropriate item ledger entry numbers from the posted item tracking lines" — i.e. the same serial/lot identity re-enters, cost-linked to its original outbound entry ([Process sales return orders](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-orders)).

**Return reasons.** A per-line **Return Reason Code** (user-defined table, shared by sales and purchase return orders). Each code carries two behavior hooks, documented in the (archived but still-accurate NAV) [Return Reasons window reference](https://learn.microsoft.com/en-us/previous-versions/dynamicsnav-2015/hh173680(v=nav.80)): a **Default Location Code** ("specify that the returned items belong to the customer and should not affect the availability and value of your inventory") and **Inventory Value Zero** — checked, "the item can then enter into inventory to be repaired, but its value will be set to zero"; cleared, "return the item to inventory at its original cost". Current BC docs reference the field but no longer enumerate these hooks on a dedicated page.

**Lifecycle / order of operations.** Return order → post **Receive** (creates **Posted Return Receipts**; warehouse receive/put-away documents can drive it) → post **Invoice** (creates the posted **Sales Credit Memo**, applied to customer ledger entries). Receipt and credit are separable: **Get Return Receipt Lines** on a credit memo, or the **Combine Return Receipts** batch job, credit many return orders' receipts in one memo; **Quantity Invoiced** flows back to the originating return order, which survives until deleted (manually or via **Delete Invoiced Sales Return Orders**) ([combine return receipts](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-cancellations#to-combine-return-receipts)).

**Restock charge & allowances.** A restock fee is just another line: "in the **Type** field, select **Charge (Item)**", fill amount, and assign the charge to the posted shipment; "when you post the sales return order, the restock charge is added to the relevant sales entry amount" (keeps valuation right). Sales allowances (price reductions) use the same Charge (Item) mechanism ([Process sales return orders](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-orders#to-create-a-restock-charge)).

**Replacements.** Enter the replacement as a *negative-quantity* line on the return order, then **Move Negative Lines** deletes it and creates a new **Sales Order**. **Create Return-Related Documents** goes further: for one vendor number it can auto-create a replacement **Sales Order**, a **Purchase Return Order**, and/or a replacement **Purchase Order** — the documented use case is vendor-warranty items ([Process sales return orders](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-orders#to-create-return-related-documents-from-a-sales-return-order)).

**Financials.** Credit memo must be applied to customer ledger entries (**Apply Entries**, partial **Amount to Apply** allowed); refund is a separate payables/receivables step. Posting a credit memo also reverts item charges assigned to the posted document. Unpaid invoices get the lighter **Correct**/**Cancel** actions, which "don't support partial returns or cancellations" ([Process sales returns or cancellations](https://learn.microsoft.com/en-us/dynamics365/business-central/sales-how-process-sales-returns-cancellations)).

**Supplier side is a mirror image.** **Purchase Return Order** → post Ship (creates **Posted Return Shipments**) → **Purchase Credit Memo**; same **Get Posted Document Lines to Reverse**, its own **Exact Cost Reversing Mandatory** flag on **Purchases & Payables Setup**, **Combine Return Shipments**, **Move Negative Lines** → replacement purchase order, same **Return Reason Code** field ([Process purchase returns or cancellations](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-process-purchase-returns-cancellations)).

## Oracle NetSuite

**Document model.** A **Return Authorization (RA/RMA)** is "a record of expected customer returns" and — key semantic — "a non-posting transaction": nothing hits inventory or GL until receipt/credit. It records item, quantity, and price, which "determine amounts to be credited or refunded" ([RA Forms](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1304530.html), [Return Authorization record](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N3688557.html)). Two entry modes: **standalone** (not linked to a sale) and **linked** (created from a cash sale or invoice, lines pre-populated); the record API can also initialize from a sales order. For serialized items on a standalone RA, the UI lets you "select the serial number sold to this customer" ([Entering a Standalone Return Authorization](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1305354.html)).

**Lifecycle.** The documented process order: enter RA → **approve** ("approves the customer to be credited or refunded upon receipt of the item") → **receive** (item receipt) → **issue credit memo** → **refund** → **close line items** for quantities no longer expected ([Customer Returns Process](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1303799.html)). Statuses are quantity-derived and differ by feature set ([Customer Return Authorization Status](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1310133.html)):
- With Advanced Receiving: **Pending Approval → Pending Receipt → Partially Received → Pending Refund → Refunded**, plus **Canceled** and **Closed** ("all lines on the return have been closed").
- Without Advanced Receiving: **Pending Approval → Pending Refund → Partially Refunded → Refunded / Canceled / Closed** (receipt and refund collapse into one step).
A preference sets the default status of new RAs: "Select **Pending Approval** if your company uses the approval process… Select **Pending Fulfillment** if your company doesn't" (sic — the RA lifecycle page then shows approved RAs as Pending Receipt) ([Preferences for Customer Returns](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1305008.html)).

**Receiving & the restock decision.** Receiving reuses the standard **Item Receipt** transaction, opened from the RA (**Receive**) or from *Transactions > Customers > Receive Returned Order*. Per line: **Receive** checkbox, **Quantity**, mandatory **Location** under Multi-Location Inventory, and the pivotal **Restock** checkbox — checked, "inventory count increases… inventory value increases"; cleared, the item is "logged as an expense" and the "income loss posted as a loss" (scrap/write-off at receipt, no disposition document). Posting updates RA received quantities, inventory records, and inventory asset accounts. **Save & Refund** jumps straight to a cash refund, and "you credit customers only for what was received" ([Receiving a Customer Return](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1307628.html), [Handling Returned Items](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1308274.html)). What *cost* a restocked item re-enters at is not stated on these pages (**unverified** here; NetSuite has costing-preference docs this research did not reach).

**Financials.** Which money document comes out is form-driven: "**Standard Return Authorization - Credit**" generates a **credit memo** (apply to balance or refund later); "**Standard Return Authorization - Cash**" generates a direct **refund** and "cannot later be processed as a credit memo". With Advanced Receiving you "must credit a return before refunding" (credit memo from RA, then refund from the credit); without it, refund can come straight from the RA. A **Refund in Advance of Return** preference allows crediting before goods arrive; otherwise "the company waits until the return is received back into stock before crediting or refunding" ([RA Forms](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1304530.html), [Preferences](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1305008.html)).

**Return reasons.** No dedicated return-reason code table appears in the core RA docs (memo fields and customization cover it) — an explicit gap versus BC/Infor.

**Replacements.** From the RA, after an item receipt exists, a **Create Replacement Sales Order** button spawns a new sales order pre-populated from the RA lines ([Returning and Replacing Fulfillable Items](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_40150958866.html)). RAs can also be generated from **warranty claims**, with serial/lot entered via the **Inventory Details** subrecord ([Creating Return Authorizations for Warranty Claims](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4391869751.html)).

**Quality tie-in (supplier side).** NetSuite Quality Management's "Enhanced Receipt Return Authorization Workflow" auto-creates vendor returns from inspection: quality inspection evaluates each lot/serial on a PO receipt, and with Action = **Return to Vendor** and **Return Only Failed Inventory** checked, "the system generates the vendor return for the failed lot or serial number" ([Enhanced Receipt Return Authorization Workflow](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/article_0222101726.html)).

**Supplier side.** **Vendor Return Authorization** is the mirror: "a non-posting purchase transaction record", carrying both NetSuite's return number and the vendor's own RMA number, with a four-step flow — enter → approve → **ship** authorized return → **credit** (log vendor credit/refund) ([Vendor Return Authorization Overview](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N2386202.html)). Note the symmetry: customer side *receives*, vendor side *ships*.

## Odoo (v18)

**No RMA document at all.** A return is an inventory operation: on a validated delivery order, click **Return** → a **Reverse Transfer** pop-up pre-fills products/quantities from the delivery → edit quantities / delete lines → **Return** "generates a new warehouse operation for the incoming returned product(s)" which the warehouse validates like any receipt. The reverse transfer is inherently linked to (and quantity-bounded by) the originating delivery; on validation "the **Delivered** quantity on the sales order updates" so a later invoice only bills kept goods ([Returns and refunds](https://www.odoo.com/documentation/18.0/applications/sales/sales/products_prices/returns.html)).

**After invoicing: reverse transfer + credit note.** "Validated… invoices cannot be changed", so the physical return (reverse transfer) is paired with a **Credit Note** created from the invoice. The credit-note dialog takes a **Reason**, **Journal**, **Reversal Date** and two modes: **Reverse** (draft credit note, editable — this is how partial credits happen) and **Reverse and Create Invoice** (validated credit note auto-reconciled against the invoice, plus a new draft invoice). Credit notes are "a reverse entry that cancels out the journal items from the original invoice", numbered `R` + invoice number ([Credit notes and refunds](https://www.odoo.com/documentation/18.0/applications/finance/accounting/customer_invoices/credit_notes.html)).

**Lifecycle & semantics.** There is no authorize/approve stage, no return-reason code on the transfer (the only "Reason" lives on the credit note), and no restock-vs-scrap decision at receipt — returned stock lands in inventory and scrapping is a separate inventory operation. Statuses are just transfer states (draft/waiting/done).

**Repairs.** The Repair app links to returns: a repair order has a **Return** field to "select the return order from which the product to be repaired comes from"; parts lines carry **Add / Remove / Recycle** types; states run **Confirmed → Under Repair → Repaired**; for billable repairs, **Create Quotation** generates a sales order carrying the parts/costs, and the fixed product ships back on a delivery created by reversing the return receipt ([Process repair orders](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/repairs/repair_orders.html)).

**Costing / serials.** Returned goods re-enter through the standard incoming-move valuation; no exact-cost-reversal flag is documented. Lot/serial selection on a reverse transfer follows normal transfer lot entry (no special return doc); Odoo 18 documents a separate [reassign lot/serial](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/inventory/product_management/product_tracking/reassign.html) tool. **Not documented / unverified:** any original-cost reversing behavior.

## Epicor Kinetic

*(Primary Kinetic help is login-gated. Claims below cite Epicor-authored contextual help republished verbatim by licensee WCI, plus epicor.com pages; community sources flagged.)*

**Document model.** **RMA Processing** (Sales Management > Order Management > General Operations) has four areas: the **RMA** header (number/search), **Details** — "indicate what invoice and line of invoice an RMA is being created for along with the qty to be returned and reason for return", **Receipts** — "when returned goods arrive at the facility the receipt must be recorded here", and **Credits** — "after receipt of goods credits can be created directly from the credits area" ([RMA Processing, Epicor contextual help mirror](https://wcibags.atlassian.net/wiki/spaces/ECH/pages/843743245/RMA+Processing)). So: line-level link to invoice + invoice line, reason captured at authorization, credit only after receipt. Kinetic 2024.1 added "the ability to create an RMA from an order, invoice, or shipment pack" ([Epicor: What's New in 2024.1](https://www.epicor.com/en-us/blog/industries/whats-new-in-release-2024-of-kinetic/)). Epicor's product page confirms org-wide "returns and disposition processes… using unique returned materials authorization (RMA) numbers" ([Kinetic Service Management](https://www.epicor.com/en/products/enterprise-resource-planning-erp/kinetic/service-management/)).

**Receive → inspect → disposition (the distinctive part).** "After RMA receipt is performed… the material enters an inspection state awaiting disposition handling." Disposition happens in **RMA Disposition** with four options ([Disposing of RMA Product, Epicor contextual help mirror](https://wcibags.atlassian.net/wiki/spaces/ECH/pages/843481202/), [RMA Dispositions](https://wcibags.atlassian.net/wiki/spaces/ECH/pages/843481174/RMA+Dispositions)):
- **Stock** — back to inventory; prompts for warehouse and bin; creates an **INS-STK** (inspection-to-stock) part transaction.
- **Job** — issue the returned material to a job (rework/repair on a work order).
- **Fail** — reject from the system, reason required; failed material flows to **DMR Processing** (Discrepant Material Report), the same non-conformance machinery used for failed purchases, from which supplier return/scrap follow ([community corroboration](https://www.epiusers.help/t/how-do-i-process-a-supplier-return-dmr-via-rma-disposition-without-the-qa-module/67390) — flagged community).
- **Return Shipment** — send back to the customer; "automatically creates a Miscellaneous Shipment Pack ID" and an **INS-CUS** transaction.
Partial dispositions are allowed — one RMA quantity can split across Stock and Fail, each its own disposition record.

**Financials.** Credit memos are generated from the RMA's Credits area post-receipt; "if an Apply To Invoice number was assigned to the original RMA, the credit memo created will be applied to the invoice; if no number is entered, an open credit memo will be created" ([epiusers, describing Epicor help text](https://www.epiusers.help/t/rma-generated-credit-memo-does-not-grab-product-group-from-invoice-right/120093) — community). Costing: when the RMA line specifies invoice and line, Epicor walks back to the original shipment's **PartFIFOTran** FIFO layers, and layers returned via disposition to Job or Fail "will be processed as individual or distinct FIFO layers" — i.e. exact original-cost layers follow the return ([epiusers](https://www.epiusers.help/t/rma-disposition-costs-table/115190) — community; **not verified against gated official docs**).

**Serial/lot.** Not covered by the accessible mirrored pages (**unverified**; community threads indicate serial selection at RMA receipt).

## Infor CloudSuite Industrial (SyteLine)

**Document model.** An RMA "creates the document that authorizes a customer to reject material" with an **RMA header** (customer, problem info; its **Status** field "tracks this authorization through its life cycle… serving as the historical record after all material has been returned and the customer has been credited") and **RMA Line Items** (material, expected return, compensation, disposition) ([Return Material Authorization Overview](https://docs.infor.com/csi/9.01.x/en-us/csbiolh/mergedprojects/sl_custvend/other/overview/return_material_authorization_overview.htm)).

**Reasons and dispositions as separate code tables.** A **Problem Code** "best describes the problem that led to the return" (reporting on why customers reject material); a three-character **Disposition Code** "identifies what action should be taken with the material when it is returned", trackable via the RMA Status Report (same overview page — values are user-defined, not enumerated by the docs).

**Lifecycle.** Documented [RMA Steps](https://docs.infor.com/csi/9.01.x/en-us/csbiolh/lsm1454144038357.html): create RMA header → create RMA line items → receive via the **RMA Return Transaction** form → optional rework (**Creating a Rework Order** — repair the returned item on a rework order) → **Issuing a Credit** / **Sending a Replacement** / **Generating Replacement Orders**. Replacements can be "new items from inventory or… the same items after a repair step" ([About Returns](https://docs.infor.com/csi/9.01.x/en-us/csbiolh/mergedprojects/sl_custvend/other/overview/about_returns.htm)).

**Financials.** The **RMA Credit Memo** form generates credits; "if an item is to be returned by the customer, the return must take place before the credit memo can be created." Line selection is rule-driven: lines qualify when "the Return flag is selected and the quantity returned is greater than the quantity credited thus far", or "the Return flag is cleared and an amount remains to be credited" (credit-without-physical-return is a first-class case), for lines with **Open**/**Filled** status under an **Open** RMA header. **Apply To Invoice number** applies the credit to a specific invoice, else an open credit memo; a **Reversing an RMA Credit Memo** procedure exists ([Processing an RMA Credit Memo](https://docs.infor.com/csi/10.x/en-us/csbiolh/customer_svc_user_cl_sl/qxm1529518824289.html)).

## SAP Business One

**Three-document chain.** ([SAP Learning: Solving Issues in Sales](https://learning.sap.com/courses/managing-logistics-in-sap-business-one/solving-issues-in-sales))
- **Return Request** — optional authorization document (issuable as an RMA number), created from a **Delivery** or **A/R Invoice**; non-posting. Its advantage: "the system will automatically determine the appropriate correction document to follow" on Copy To.
- **Return** — the goods-movement correction *before invoicing*: "reverses the effects of a delivery, either partially or fully"; increases warehouse stock, posting to a **Sales Returns** account separate from the original stock account.
- **A/R Credit Memo** — the correction *after invoicing*: "reverses an A/R invoice's journal entry either partially or fully" and "increases the stocks of the credited items" (inventory + GL in one document). A **Without Qty Posting** row option credits money without any inventory movement (price adjustments, goods not coming back).
Exchanges are handled with **negative rows** directly on sales documents rather than a replacement document. Paid/closed invoices require reopening before the chain applies. Supplier mirror: **Goods Returns** and **A/P Credit Memo** in purchasing ([SAP TB1000 courseware on help.sap.com](https://help.sap.com/doc/saphelpiis_hc_b1_image_repository_consultant_training_basic_b1_90_tb1000_02_06_pdf/9.0/en-US/B1_90_TB1000_02_06.pdf)).

## Katana MRP (light pass)

**Return orders** are created from *completed* sales orders (Sell > Sales orders > Done); "each return connected to its original sales order to ensure traceability". Three statuses: **Not Returned** ("customer initiated a return… inventory levels remain unaffected") → **Returned** (received, "may be in quality control or awaiting assessment", still not in stock) → **Restocked** (inventory adjusted, "stock is now available again"). Item-level add/remove/edit with **reasons for return**; restocking is per-item with a **Restock location** column and a batch-info pop-up for batch-tracked products; a return's status change can "automatically trigger credit notes in QuickBooks Online"; Shopify-initiated returns sync in ([Returns overview](https://support.katanamrp.com/en/articles/11094886-returns-overview), [How to restock return orders](https://support.katanamrp.com/en/articles/11130510-how-to-restock-return-orders)). Costing basis on restock is **not documented**. Notable: even a lightweight MRP separates *received* from *restocked* — the two-phase receipt is table stakes.

## Fulcrum (light pass)

Public docs are thin: the returns workflow is initiated from the refund flow — "when you are refunding an item, you can also indicate a return, which will create a receiving record for the item being returned" ([Fulcrum product update: Returns workflow](https://fulcrumpro.com/product-update/returns-workflow)). Inspection/disposition and costing behavior are **not publicly documented**.

## Synthesis

### The common core (table stakes)

1. **An authorization document distinct from money and inventory documents.** Every document-first system (BC, NetSuite, Epicor, Infor, SAP B1's Return Request, Katana) has an RMA header + lines that is *non-posting*: it records intent (what's expected back, at what price/qty) and accumulates state, while inventory moves on a receipt document and money moves on a credit memo/refund. NetSuite states the non-posting semantic outright.
2. **Optional line-level linkage to the original transaction.** Lines link to the original invoice line / shipment / order (BC `Appl.-from Item Entry`, Epicor invoice+line, NetSuite linked RA, SAP Copy To). Linking is always *optional* — standalone/blind returns are supported everywhere — but when present it drives three things: reversible-quantity validation (BC "Show Reversible Lines Only"), credit pricing (copied prices/discounts), and cost reversal (below).
3. **Lifecycle = authorize → (approve) → receive → disposition → credit/refund/replace → close**, with statuses derived from quantities (NetSuite: Pending Receipt / Partially Received / Pending Refund / Refunded; Infor: Open/Filled per line; Katana: Not Returned / Returned / Restocked). Cancel/close-line escape hatches exist at every stage (NetSuite "Closing Line Items", BC delete-invoiced-return-orders).
4. **Receiving reuses the normal receiving machinery.** NetSuite opens a standard Item Receipt; BC posts return receipts through the same warehouse receive/put-away documents; Odoo literally creates an incoming transfer; Epicor records receipts on the RMA; Infor has an RMA Return Transaction form. No system invents a parallel receiving stack.
5. **A restock-vs-not decision after physical receipt.** Modeled either as a binary flag at receipt (NetSuite **Restock**: unchecked = write-off as expense/loss) or as an explicit inspect-then-disposition stage (Epicor: receipt lands in inspection, then **Stock / Job / Fail(DMR) / Return Shipment**; Infor disposition codes; Katana's Returned→Restocked gate).
6. **Credit memo generated from the return, applied to the original invoice or left on account.** Epicor/Infor: "Apply To Invoice… else an open credit memo". Default order is receive-then-credit (NetSuite "credit customers only for what was received"; Infor "the return must take place before the credit memo can be created"), with an explicit override (NetSuite **Refund in Advance of Return**; Infor's no-return credit lines). Credit ≠ refund: credit-on-account first, refund as a follow-on payment document (NetSuite makes the ordering configurable; BC handles refund in payables).
7. **Cost: returned goods re-enter at their original outbound cost, not current cost.** BC's exact cost reversing (item-ledger-entry application, `Exact Cost Reversing Mandatory`), Epicor's FIFO-layer walk-back from the original shipment. With a documented degrade path for damaged goods: BC **Inventory Value Zero** per return reason; NetSuite's no-restock write-off.
8. **Replacements spawn a linked sales order.** NetSuite **Create Replacement Sales Order** (post-receipt), Infor replacement orders (from stock or after repair), BC **Move Negative Lines** / **Create Return-Related Documents** (which also spawns the vendor-warranty purchase return + replacement PO). Repair is a distinct flow: Odoo repair orders and Infor rework orders link the returned unit to a work/rework order; Epicor's **Job** disposition issues returned material to a job.
9. **Return reasons are a small user-defined code table on the line.** BC Return Reason Code (with behavior hooks: default location, zero value), Epicor reason on the RMA detail + reason on Fail, Infor Problem Code (why) *separate from* Disposition Code (what to do), Katana free-form reasons. NetSuite and Odoo are the outliers (reason only on the credit note in Odoo; none native in NetSuite).
10. **The supplier side mirrors the customer side** with direction flipped (customer RMA *receives*, vendor return *ships*): BC purchase return orders/posted return shipments, NetSuite Vendor RA (enter→approve→ship→credit), SAP B1 Goods Returns/A-P Credit Memo. Epicor and NetSuite additionally *bridge* the two: a failed customer return (Epicor Fail→DMR; NetSuite quality-inspection workflow) becomes a return-to-vendor.

### Divergences worth noting

- **Document-first vs operation-first.** Odoo has no RMA object — return = reverse transfer + credit note, linkage via the delivery. Cheap to build, but there is no place to hang authorization state, reasons, dispositions, or expected-vs-received tracking; Katana (similar market) added a return-order object anyway.
- **Approval as a first-class stage** (NetSuite, Infor status; Epicor via workflow) vs absent (BC, Odoo, SAP B1 — the Return Request itself is the authorization).
- **Where the damaged-goods decision lives:** at receipt (NetSuite flag), at disposition after inspection (Epicor/Infor — manufacturing-grade), or encoded in the reason code (BC's location + zero-value hooks — clever, low-ceremony).
- **Restock fee:** only BC documents a concrete mechanism (a Charge (Item) line assigned to the posted shipment, folded into the sales entry amount); others handle it as manual credit-memo line edits.
- **One credit document per RMA vs many:** BC can combine many return orders' receipts into one credit memo (statement-style), and conversely partially credit; NetSuite/Epicor generate credits per-RMA (multiple credits per RMA allowed in Epicor).
- **Exchange semantics:** linked replacement SO (NetSuite/Infor) vs negative lines moved off the return (BC, SAP B1). The negative-line approach is documented but clunky.

### Implications for Carbon

Carbon already has: sales order → shipment → sales invoice; a receipts system whose `receiptSourceDocument` enum already contains an unused **"Sales Return Order"** value; an AR credit-memo table (header-level amount, Draft/Posted/Voided, direction Credit|Debit, posts to a journal); a quality Issues module with dispositions (Use As Is, Rework, Scrap, Return to Supplier, Quarantine…) and MRB approvals; `trackedEntity` lot/serial rows (Available/Reserved/On Hold/Consumed/Rejected); item/cost ledger posting via edge functions.

1. **Build the RMA as a non-posting header+lines document** (`salesRma` or `salesReturnOrder`), separate from receipt and credit memo. Statuses quantity-derived, NetSuite-style: `Draft → Authorized → Partially Received → Received → Dispositioned → Credited/Closed`, plus `Voided`; per-line close for never-coming-back quantities.
2. **Line linkage optional but rich:** nullable FKs to `salesOrderLine` / shipment line / `salesInvoiceLine` (+ itemId, qty, uom). When linked: validate against already-returned quantity (BC's reversible-lines check), copy pricing for the credit, and resolve the original cost. Blind returns (no link) are table stakes.
3. **Receive through the existing receipts system** — this is exactly what the unused `"Sales Return Order"` `receiptSourceDocument` value is for. One receipt per arrival, partial receipts natural, item ledger posting through the existing edge functions. Default the receiving location to a quarantine/inspection location (BC's per-reason **Default Location Code** is the pattern to steal).
4. **Disposition via the quality Issues module, not a new subsystem.** Epicor's receive→inspect→disposition is the manufacturing-grade model, and Carbon already owns the vocabulary: map RMA disposition to the existing enum — restock (Use As Is), Rework (→ job/rework), Scrap (write-off posting), Return to Supplier (spawns purchase-return flow — Epicor's Fail→DMR bridge), Quarantine (hold). Support partial, per-quantity dispositions (one RMA line splitting Stock/Scrap), optionally gated by MRB approval for high-value returns.
5. **Costing policy per line, decided at receipt/disposition:** (a) original cost via the linked outbound ledger entry (BC exact cost reversing — requires resolving the shipment's cost-ledger entry), (b) zero value (BC Inventory Value Zero: unit exists for rework, worth nothing), or (c) no restock = expense write-off (NetSuite). Scrap disposition posts the write-off through the existing cost-ledger edge functions.
6. **Credit memo:** generate from the RMA on demand (not auto), defaulting to received-and-dispositioned quantities × original invoice pricing, minus restocking fee. Carbon's AR credit memo is header-amount-only — either add credit-memo lines or store the line-level credit breakdown (qty credited per RMA line, fee) on the RMA and post the total; the per-line `quantityCredited` is needed regardless for status derivation and partial credits. Keep credit (posted memo on account) separate from refund (payment-side, out of scope initially). Restock fee as an explicit signed component, BC-style.
7. **Replacements: spawn a linked sales order** from the RMA (NetSuite's post-receipt `Create Replacement Sales Order`), carrying `rmaId` provenance — not BC's negative-line dance. Repair-and-return can start as a disposition note + manual job, later formalized (Odoo repair orders / Infor rework orders show the shape: link returned unit → work order → outbound shipment).
8. **Serial/lot: same entity re-enters.** On RMA lines for tracked items, let users pick from trackedEntities actually shipped to that customer (NetSuite's "serial number sold to this customer"; BC's item-tracking application). On receipt, reactivate the same `trackedEntity` in **On Hold** (or Quarantine) until disposition flips it to Available/Rejected/Consumed — this preserves genealogy across the round trip, which none of the lightweight systems manage.
9. **Return reasons: company-scoped code table** referenced per RMA line (why), kept separate from disposition (what we did) — Infor's Problem Code vs Disposition Code split. Optional per-reason behavior hooks (default location, zero-value) are cheap and proven in BC.
10. **Design for symmetry now, build supplier side later.** Keep naming/shape such that a purchase-return document can mirror (direction flipped: ship instead of receive), and let the Return-to-Supplier disposition be the bridge between the two — the Epicor/NetSuite pattern.

**Verification gaps:** Epicor official Kinetic docs are gated — disposition/credit details rest on Epicor-authored mirrored help + community corroboration as flagged. NetSuite's restocked-item cost basis and Katana's costing basis are not documented on the pages reached. Fulcrum's public documentation is minimal.
