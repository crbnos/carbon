# Paperless Parts Integration

Inbound only: Paperless Parts (an estimating and quoting platform) sends webhooks, and
Carbon turns a sent quote into a Draft `quote` and an order into a `salesOrder`, creating
the customers, contacts, items, make methods and routings they need. Carbon never pushes
anything back, except a Paperless account it creates for a contact that has none.
User docs: `docs/content/docs/integrations/estimating.mdx`.

## Key files

- `packages/ee/src/paperless-parts/config.tsx` — the `PaperlessParts` descriptor
  (`defineIntegration`, id `"paperless-parts"`, category "Estimating & Quoting",
  `active: true`). Registered in `packages/ee/src/index.ts` `integrations[]`.
  `SetupInstructions` shows the webhook URL `/api/webhook/paperless-parts/{companyId}`.
  No `providerRole`, no OAuth, no server hooks (`hooks.server.ts` has no entry).
- `packages/ee/src/paperless-parts/lib/client.ts` — `PaperlessPartsClient`, GENERATED by
  `swagger-typescript-api` from the Paperless OpenAPI file (header comment). Do not
  hand-edit it; regenerate it. Base URL `https://api.paperlessparts.com`, header
  `Authorization: API-Token <apiKey>`. The integration calls `quotes.quoteDetails`,
  `orders.orderDetails`, `accounts.listAccounts` and `accounts.createAccount`.
- `packages/ee/src/paperless-parts/lib/lib.ts` — the import logic (about 3,500 lines).
  Exported through `lib/index.ts`: `getCustomerIdAndContactId`, `getCustomerLocationIds`,
  `getEmployeeAndSalesPersonId`, `getOrderLocationId`, `getCarbonOrderStatus`,
  `getPaperlessPart`, `getOrCreatePart`, `createPartFromComponent`, `insertQuoteLines`,
  `insertOrderLines`.
- `packages/ee/src/paperless-parts/lib/schemas.ts` — zod schemas of the Paperless payloads
  (`OrderSchema`, `OrderItemSchema`, `ComponentSchema`, `ContactSchema`, `FacilitySchema`, …).
- `packages/ee/src/paperless-parts/lib/utils.ts` — `calculatePromisedDate` (business days
  after a lead time, skipping weekends and `holiday` rows). Tested in `utils.test.ts`.
- Export paths: `@carbon/ee/paperless-parts` → `lib/index.ts` (`packages/ee/package.json`);
  the root barrel also exports `PaperlessPartsClient` (`index.ts`, "TODO: export as
  @carbon/ee/paperless").
- `apps/erp/app/routes/api+/webhook.paperless-parts.$companyId.ts` — the webhook.
  Tests: `webhook.paperless-parts.$companyId.test.ts`.
- `packages/jobs/src/inngest/functions/integrations/paperless-parts.ts` —
  `paperlessPartsFunction`, registered in `packages/jobs/src/inngest/index.ts`.

## Data flow

1. Paperless POSTs to `webhook.paperless-parts.$companyId.ts`. The route reads the
   `companyIntegration` row (`getIntegration`, service role) and resolves `apiKey` and
   `secretKey` from Vault with `resolveIntegrationSecrets`.
2. The route verifies the signature (next section). On success it calls
   `trigger("paperless-parts", { apiKey, companyId, payload })`, which sends
   `carbon/paperless-parts` (`packages/lib/src/trigger.ts`).
3. `paperlessPartsFunction` (Inngest id `paperless-parts`, `retries: 1`) parses the payload
   with a discriminated union on `type`, reads `company` and the integration row, and reads
   the import settings from `companyIntegration.metadata`.
4. It branches on the event type:

| Event | What the job does |
|---|---|
| `quote.sent` | Re-reads the quote (`quotes.quoteDetails`, with `revision`). Skips it when a `quote` mapping exists. Else inserts `opportunity`, `quote` (status `Draft`, `revisionId` = the Paperless revision), the mapping, `quoteShipment`, `quotePayment`, an `externalLink`, then `insertQuoteLines`. |
| `order.created`, `order.status_changed` | Same code path. Re-reads the order (`orders.orderDetails`). If a `salesOrder` mapping exists, it only updates `salesOrder.status` (`getCarbonOrderStatus`). Else inserts `opportunity`, `salesOrder`, the mapping, `salesOrderShipment`, `salesOrderPayment`, then `insertOrderLines`. |
| `quote.created`, `quote.status_changed`, `integration_action.requested`, `integration.turned_on`, `integration.turned_off` | Logged and acknowledged. Nothing is written. |

### What the line inserts do

- `insertQuoteLines` skips a quote item of `type === "manual"` and an item with no
  components. It makes one `quoteLine` per ROOT component, plus `quoteLinePrice` per
  quantity break with `priceSource: "manual"` (so no Carbon recalculation overwrites the
  Paperless price, see `sales.utils.ts`), `quoteMakeMethod`, `quoteMaterial` and
  `quoteOperation` rows.
- `insertOrderLines` makes `salesOrderLine` rows, sets the item's lead time
  (`itemReplenishment`), and computes a promised date with `calculatePromisedDate`.
- `getOrCreatePart` / `createPartFromComponent` find an item by its `item` mapping, then by
  `readableId` + `revision` + `name` (`getPaperlessPart`). Else they create the `item`,
  `part`, `itemCost`, the thumbnail (`downloadAndUploadThumbnail`) and the make method
  lines (`methodMaterial`, `methodOperation`).
- Both line inserts call `processSupportingFiles`: a CAD file becomes a `modelUpload` on
  the item (`uploadModelFile`), any other file an item document (`uploadFileToItem`).
- Materials: `getOrCreateMaterial` picks a `materialSubstance` with an LLM call
  (`generateText`, `openAiCategorizationModel`). The material properties cache for 30
  minutes in process memory (`CACHE_TTL`).
- Notes (`private_notes`, `public_notes`, operation `notes`) become Tiptap documents through
  `TiptapText(text, { format: "text" }).toDocument()` (`@carbon/files/markdown`).

### Customers, contacts, people and location

- Customer (`getCustomerIdAndContactId`): the `customer` mapping by Paperless account id,
  then a customer with the same `name`, else an upsert on `(name, companyId)`. A contact
  with no account: Carbon searches Paperless accounts by the contact's full name and
  creates one (`accounts.createAccount`) when none matches.
- Contact: the `contact` mapping by Paperless contact id. Else a `contact` with the same
  email and `isCustomer`: Carbon reuses the one already linked to this customer, else the
  only match. With several matches and none on the customer, it creates a new contact.
- Creator and sales person: `getEmployeeAndSalesPersonId` matches the estimator and the
  sales person to `employees` by email. `createdBy` is the estimator, else `"system"`.
- Location: `getOrderLocationId` matches the Paperless `send_from_facility` to a
  `location.name` (case-insensitive), else the company's first location by `createdAt`.
  Both the quote and the sales order get it. Customer ship-to and bill-to locations come
  from `getCustomerLocationIds` (`customerLocation` + `address`, mapped).

## Webhook signing (required)

The header `Paperless-Parts-Signature` holds `t=<unix seconds>,v1=<hex>`. The route
computes HMAC-SHA256 over `` `${t}.${body}` ``, keyed by the signing secret decoded as HEX
bytes (`Buffer.from(secretKey, "hex")`). It accepts two body forms: the raw request text,
and a legacy normalized `JSON.stringify` form for older deliveries. The compare is
constant-time (`signaturesMatch`). A missing header, a malformed header and a mismatch each
log `"Paperless Parts webhook rejected"` with a `reason`
(`missing_signature_header`, `malformed_signature_header`, `signature_mismatch`) and
answer 401. Any other throw answers 500.

This scheme differs from `verifyHmacSha256Signature`
(`packages/ee/src/integrations/webhook-signature.ts`), which signs the body alone, and
from `signWebhookBody` (`packages/jobs/src/inngest/functions/events/webhook-body.ts`),
which keys by the whole secret string.

## Settings

| Setting | Type | Default | Read by |
|---|---|---|---|
| `apiKey` | secret | — | the route, passed to the job in the event |
| `secretKey` ("Webhook Signing Secret") | secret | — | the route |
| `methodType` | Purchase to Order / Pull from Inventory | Pull from Inventory | the job, for material lines |
| `trackingType` | Inventory / Non-Inventory / Batch | Inventory | the job, for new materials |
| `billOfProcessBlackList` | string array | `[]` | operation names to skip |
| `usePaperlessOrderNumber` | switch | `false` | `quoteId` / `salesOrderId` = the Paperless number, else `get_next_sequence` |

- Both secrets live in Vault: `SECRET_KEYS["paperless-parts"] = ["apiKey", "secretKey"]`
  (`packages/ee/src/integrations/secrets.ts`). An empty field keeps the stored value; the
  install action in `x+/settings+/integrations.$id.tsx` (`FORM_SECRET_INTEGRATIONS`)
  requires one on first install.
- `usePaperlessOrderNumber` is preprocessed from the `"true"`/`"false"` string that
  `SwitchField` posts. `zfd.checkbox()` rejected every save.
- The blacklist match is a case-insensitive SUBSTRING match on
  `operation_definition_name ?? name`, in both `createPartFromComponent` and
  `insertQuoteLines`.

## Storage of the link (`externalIntegrationMapping`)

Two different `integration` values. Use the right one.

| `integration` | `entityType` values | Written by |
|---|---|---|
| `"paperlessId"` | `quote`, `salesOrder` (`externalId` = Paperless `uuid`) | the job |
| `"paperlessPartsId"` | `customer`, `contact`, `customerLocation`, `item`, `part` | `lib.ts` (`createPaperlessMapping`) |

`createPaperlessMapping` deletes the entity's old mapping with the service role, then
inserts the new one. The table has no UPDATE or DELETE RLS policy.

## Gotchas

- Every write is a chained Supabase-client call, never a transaction. On a failure the job
  calls `deleteQuote` / `deleteSalesOrder`, which delete only the header row. The quote or
  sales order mapping was already inserted, and the table has no FK to the entity. So a
  redelivered webhook reads "Quote already exists" and imports nothing.
- The job inserts the `opportunity` before it checks the quote's shipment and payment
  results, so a failed import can leave an orphan `opportunity`.
- `order.status_changed` for an order Carbon does not have yet CREATES the sales order.
- Reusing a contact by email overwrites its `firstName` and `lastName` with the Paperless
  values.
- The route and the job never check `companyIntegration.active`. Uninstall
  (`deactivateIntegration`) only sets `active = false`, so a signed webhook still imports
  after an uninstall.
- No timestamp window: the route does not reject an old `t`, so a captured delivery can
  replay. The mapping checks make most replays a no-op.
- `calculatePromisedDate` uses JavaScript `Date` and `getLocalTimeZone()` on the server,
  with a 10:00 cutoff in the SERVER's zone. `.claude/rules/date-handling.md` bans both in
  `packages/ee` server code. It is existing debt, not a pattern to copy.
- Quotes imported before 2026-10-13 have no `quote.locationId`. Quote-to-order conversion
  falls back to the quote shipment's location, then the company's first location
  (`apps/erp/app/modules/shared/shared.service.ts`).
- The route logs the webhook payload at info (`logger.info("payload", payload)`). The
  job's first log line (`"Paperless Parts webhook received: …"`) logs the whole event
  data, which includes the `apiKey`.

## Never

- Never hand-edit `lib/client.ts`. Regenerate it from the OpenAPI file.
- Never verify the signature against re-serialized JSON only. The HMAC covers the raw
  bytes; the normalized form is a fallback for old deliveries.
- Never mix up `"paperlessId"` and `"paperlessPartsId"` in a mapping lookup. A lookup with
  the wrong one finds nothing and imports a duplicate.
- Never let a Carbon price recalculation touch a Paperless quote line price. Keep
  `priceSource: "manual"`.
- Never read `apiKey` or `secretKey` from `metadata` directly. Resolve them through
  `resolveIntegrationSecrets`.
