---
title: Planning (MRP)
description: How demand turns into suggested jobs and purchase orders — and where that ends and scheduling begins.
---

Planning determines what to make or buy and in what quantity. Carbon's <Term>MRP</Term> nets demand against supply across the complete <Term id="bom">bill of materials</Term>. It converts shortages into suggested orders and offsets component demand by <Term>lead time</Term>.

## Two stages

Planning has two distinct stages:

1. **MRP, explode and net.** The engine explodes demand through bills of material, nets it against on-hand plus open jobs and purchase orders, and writes period-bucketed demand forecasts (plus the demand and supply *actuals* it read). It then sizes each shortage with the item's <Term id="reordering-policy">reorder policy</Term> and writes a <Term id="planning-action">planning action</Term> for it, and one for every open order whose date or quantity no longer fits.
2. **Planning views, show and apply.** The production and purchasing planning pages project running stock week by week, show the actions on each row, and let you apply them.

<Callout type="note">
MRP **suggests, it never auto-orders.** The engine writes forecasts and suggestions; turning a suggestion into a real job or PO, or moving an existing one, is an explicit action you take on the planning page.
</Callout>

## When it runs

MRP recalculates on its own every 3 hours. To run it once a day instead, go to **Settings → Planning → MRP Schedule**, choose **Once a day**, and pick the hour; the hour is on your company's time zone. You can also run it yourself at any moment with **Recalculate** on the planning pages, whichever schedule is set.

## What feeds it

| Input | Source |
| --- | --- |
| Customer demand | Open sales-order lines, by promised date. |
| Production demand | Job material still to issue, offset by lead time. |
| Forecast demand | Manually entered demand projections. |
| Open supply | Open jobs and open purchase-order lines. |
| On hand | The item ledger balance. |

## Reorder policy

Each item, per location, carries a **reordering policy** that decides how a suggestion is sized: *Manual Reorder* (suggests nothing), *Demand-Based Reorder* (the default), *Fixed Reorder Quantity*, or *Maximum Quantity*. Each is tuned by reorder point, order quantity, accumulation period, and min/max/multiple rounding. See [Reordering](/docs/reference/reordering) for the parameters in full.

## From suggestion to order

An item's **<Term>replenishment system</Term>** determines where its shortage appears. *Make* items produce suggested <Term id="job">jobs</Term> on the production planning page; *Buy* items produce suggested POs on the purchasing page. Choosing **Order** creates a saved job or purchase order with status **"Planned"**, pending release into its normal lifecycle.

<Callout type="info">
**"Planned"** is a real, saved job or PO that came from a planning suggestion and is waiting to be released — distinct from a hand-started **"Draft"**.
</Callout>

## Planning actions

Every MRP run leaves a worklist on the planning pages. Each row's **Actions** column shows one chip per open action type; expand the row to see each action with its target order, quantity, date and reason.

| Action | Target | What applying it does |
| --- | --- | --- |
| **Order** / **Make** | none yet | Opens the order drawer; the existing **Order** button creates the PO or job. |
| **Expedite** / **Defer** | an open PO line or job | Moves the required date (PO line) or the due date (job) to the suggested date. |
| **Increase** / **Decrease** | an open PO line or job | Sets the line's purchase quantity, or the job's quantity, to the suggested quantity. |
| **Cancel** | an open PO line or job | Deletes the PO line, or cancels the job, when nothing needs it. |

**Apply** is offered only while the target can still change from planning: a PO at **"Draft"** or **"Planned"**, a job at **"Draft"** or **"Planned"**. A PO that has been sent or is in approval, a job on the floor, or a PO line whose date the supplier has promised shows **Review** instead, and you make the change on the order itself. Select several rows and choose **Apply Suggested Changes** to apply every open action on them at once.

<Callout type="info" title="A dismissed action stays dismissed until the need changes">
**Dismiss** hides an action you have decided not to take. The next MRP runs keep it hidden while the suggested quantity and date stay the same; a material change reopens it. **Reopen** brings it back by hand. **Assign to Me** sets the owner, and MRP keeps a hand-set owner on later runs.
</Callout>

An applied action is finished: the next run re-evaluates the changed order and writes a fresh action only if something still does not fit.

## Planning horizon

The **Planning Horizon** column is a date per row: today plus the item's horizon in days. A row shows only the actions and suggested orders due on or before that date, so a long planning window does not bury next week's work. Set the company default in **Settings → Planning → Planning Horizon**, and override it per item on the item's planning tab (**Planning Horizon (Days)**). An item set to 0 shows everything MRP plans, whatever the company default.

Moving the date in the column widens or narrows that one row for this page view only; it never changes the item.

## Reschedule tolerance

MRP suggests **Expedite** or **Defer** only when an open order lands more than the tolerance away from the date it is needed. The default is 7 days. Set it in **Settings → Planning → Reschedule Tolerance**; 0 suggests a move for any date difference.

## Planning ownership

Each action gets a <Term id="responsible-employee">responsible employee</Term>, resolved from the most specific setting that names one: the item at that location, then the item group at that location, then the location, then the company default. Set the rungs in **Settings → Planning → Planning Ownership** and on the item's planning tab (**Responsible Employee**). Filter the grid by assignee to see your own worklist.

## Planning vs scheduling

Planning determines quantities; **scheduling** determines timing and work-center allocation. After a job exists, scheduling places its <Term id="operation">operations</Term> on <Term id="work-center">work centers</Term> and calculates dates without changing quantities.

## Troubleshooting

### "Manufacturing is blocked for item …"
Ordering a suggested job was stopped because that item's planning settings have manufacturing blocked. Clear the flag on the item, then order again from planning.

### "Manufacturing requires configuration for item …"
The item is configurable, and planning can't supply a configuration. Create the job from a context that sets the configuration (for example the sales order line) instead of from the planning page.

### "Failed to create job method for item …"
The job was created but copying the item's method into it failed — usually the item has no **Active** make method. Activate a method on the item, then delete and re-order the job (or run Get Method on it).

### "Failed to load any locations"
Planning needs at least one location. Create one in settings and set a default.

### "Planning action … was already applied"
Another planner applied the same action after this page loaded. Reload the planning page; the action is gone and the order already carries the change.

### "… is committed — review on the order"
The target left Draft / Planned between the page load and Apply (the PO was sent or put in approval, the job was released). The action stays open as Review; make the change on the order.

### Mechanics
Actions are rows in `planningAction` (`type` Order / Make / Expedite / Defer / Cancel / Increase / Decrease; `status` Open / Dismissed / Actioned), written by `generatePlanningActions` after every MRP run as a diff against the previous run. Apply runs as one transaction per batch: the claim (Open → Actioned) and the change commit together. The horizon is `itemPlanning.planningHorizonDays`, else `companySettings.defaultPlanningHorizonDays`; 0 at either level means no horizon. The tolerance is `companySettings.rescheduleToleranceDays`. The owner ladder is `itemPlanning.responsibleEmployee` → `itemPostingGroupResponsibility` → `location.responsibleEmployee` → `companySettings.defaultResponsibleEmployee`.
</AgentContext>
