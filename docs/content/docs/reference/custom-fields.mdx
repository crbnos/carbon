title: Custom fields
description: Company-defined extra fields that attach to core records like customers, parts, and orders.

Carbon ships a fixed schema for every entity, but your process almost always needs one more field: a customer's "PPAP level", a part's "RoHS status", a job's internal "line number". <Term id="custom-field">Custom fields</Term> let each company add its own fields to a core record without a schema change. Define one under **Settings → Custom Fields** and every record of that entity shows it on its form, saves it alongside the built-in fields, and exposes it through the API.

## Defining a field

<Screenshot label="Settings → Custom Fields: the entity catalog with Table, Module, and Fields columns, and the field form with name, data type, and tags" caption="One row per eligible entity; the field form locks its data type after creation." />

<FieldTable>
  <Field name="Name" type="text" required>The label shown on the record's form. Unique per table, per company.</Field>
  <Field name="Data Type" type="enum" required>One of nine types (below). **Once saved, the type can't be changed**; delete and re-create to switch.</Field>
  <Field name="List Options" type="text[]">Required only for the **List** type: the dropdown's choices.</Field>
  <Field name="Required" type="boolean">The field must be filled before the form saves. Boolean fields are never treated as required.</Field>
  <Field name="Tags" type="text[]">Scopes the field to records carrying a matching tag; leave empty to show it on every record of the table.</Field>
</FieldTable>

The nine data types each render a specific input: **Boolean** (toggle), **Date** (date picker), **List** (dropdown of your options), **Numeric**, **Text**, **File**, and three reference types (**User**, **Customer**, and **Supplier**) that store a pointer to an existing Carbon record rather than free text.

<Callout type="note" title="The data type is permanent">
Existing values are stored as-is, so Carbon locks the type after creation. Picked Text and need Numeric? Create a new field and migrate the values; there is no in-place conversion.
</Callout>

## Which entities support custom fields

The catalog is curated, not universal — the settings page lists one row per eligible entity with its module and field count. Coverage spans most modules: **Sales** (customer, sales order, sales invoice, RFQ, their contacts and lines), **Purchasing** (supplier, purchase invoice, supplier quote, RFQ lines), **Items** (part, tool, material, consumable, costing/planning records; see [items](/docs/reference/items)), **Resources** (employee job, work center, equipment, department, location), **Inventory** (shipment, warehouse transfer, picking list), **Production** (job), and **Accounting** (account, payment term, journal). An entity not listed on the settings page isn't supported yet.

## How values save, and where they reach

Custom inputs render below the built-in fields on the record's form and save into a single `customFields` JSON column that every core table carries — no schema change per field. That column is exposed on the API like any other: readable and filterable on the entity's endpoint, with the caveat that its keys are field IDs, not display names, so pair an API read with the definitions from the settings catalog.

<Callout type="warn" title="CSV import and export skip custom fields">
The CSV flows map built-in fields only; neither import nor the table download touches the `customFields` column. Populate custom fields on the form or through the API; see [import and export](/docs/reference/import-export) for what CSV does cover.
</Callout>

## Internals and troubleshooting

Definitions live in the `customField` table (`20240311021818_custom-fields.sql:21`); the form validator is `customFieldValidator` (`settings.models.ts:109`). The eligible-entity catalog is `customFieldTable`, seeded from `20240511125727_seed_custom_fields.sql` onward; the settings page renders it in `CustomFieldsTable.tsx:32`. Forms drop in the shared `<CustomFormFields table="…" />` (`components/Form/CustomFormFields.tsx`; rendering switch at `:75`), inputs are named with a `custom-` prefix, and route actions collect them via `setCustomFields(formData)` / repopulate via `getCustomFields` (`utils/form.ts`). The nine types are the `DataType` enum (`modules/shared/types.ts:83`). Swagger exposes `rowFilter.<table>.customFields`.

### "Required" on a custom field that won't submit
Requiredness is enforced by a runtime validator the form registers per table (`CustomFormFields.tsx:44`), separate from the entity's zod schema. Fill the field or clear its Required flag. Boolean fields are never treated as required, even with the flag on (`CustomFormFields.tsx:31`).

### List custom field rejected on save
A List field with no options or an empty option fails the validator's refine (`settings.models.ts:121-131`). Give it at least one non-empty choice.

### The Data Type dropdown is disabled when editing
By design: the form sets `isReadOnly` on the type select and shows "Data type cannot be changed" (`CustomFieldForm.tsx:110-116`). Delete and re-create to switch types.

### Custom-field values missing from CSV import/export
Expected — the `import-csv` edge function maps only built-in fields and the download omits the JSONB. Use the form or the API.

### The entity I want has no Custom Fields row
Only entities in the code-managed `customFieldTable` catalog are eligible; there's no way to add one from the UI.
</AgentContext>
