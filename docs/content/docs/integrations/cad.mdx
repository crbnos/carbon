## Onshape

Connect to **Onshape** over **OAuth** to bring CAD data into Carbon. No keys to paste.

<Steps>
  <Step>
  ### Authorize over OAuth

  Start the connection and Carbon opens an Onshape popup.
  </Step>
  <Step>
  ### Approve read and write access

  Carbon asks for read access to your Onshape documents and write access. Write is what lets Carbon register the release webhook it listens on, so everything below depends on it.
  </Step>
  <Step>
  ### Tokens stored

  Carbon stores the connection, the access and refresh tokens, and can then pull from your Onshape documents.
  </Step>
</Steps>

<Callout type="warn">
Onshape only appears when its OAuth client is configured server-side (`ONSHAPE_CLIENT_ID`) — see
[Environment variables](/docs/platform/self-hosting/environment-variables).
</Callout>

## Two pipelines

Carbon has two Onshape implementations, and a company runs exactly one of them. **Pipeline** is where you
choose.

**Legacy** is the default, and nothing changes for a company that never touches the setting. It reacts to
releases in Onshape and finds the Carbon item by part number and revision.

**Onshape v2** replaces that lookup with a link. When you create a part from Onshape, link one you already
have, or import an assembly's <Term id="bom">bill of materials</Term>, Carbon records which Onshape part the item came from and
follows that link ever after. The two numbers no longer have to agree, so renaming a part on either side
keeps them connected, and nothing can attach to the wrong item because two numbers happened to look alike.

<Callout type="warn" title="Switching to v2 leaves the items legacy brought in unlinked.">
They were only ever matched by number, so they carry no link and v2 cannot see them. Saving the switch tells
you how many are in that state, and **"Link to Onshape"** on a part's menu adopts one. While v2 is selected
the legacy settings are ignored, so the two pipelines never act on the same release.
</Callout>

## Settings

<FieldTable>
  <Field name="Connection">Established by OAuth — no keys to paste. Carbon stores the access and refresh tokens for you.</Field>
  <Field name="Pipeline">**Legacy** (the default) or **Onshape v2**. Exactly one runs, and the other's settings do nothing.</Field>
  <Field name="Sync released assets">Legacy. Off by default. When a part or assembly is released in Onshape, Carbon attaches its CAD model to the Carbon item carrying the same part number, and a released drawing's PDF to the item it documents. It never creates an item.</Field>
  <Field name="Import released revisions">Legacy. Off by default. Brings an Onshape release into Carbon's engineering data rather than only its files. Turning it on reveals the mode below.</Field>
  <Field name="How a release lands">Legacy. Either **Create a change notice** (the default) or **Create the revision directly**. See [Releases](#releases).</Field>
  <Field name="Attach assets when a revision is released">Under **Onshape v2**, on by default. Pulls the 3D model onto the linked item when Onshape releases a revision, which is what covers releases nobody started from inside Carbon. It does not affect importing a bill of materials or creating an item from Onshape — those always bring their models.</Field>
  <Field name="When a revision is released">Under **Onshape v2**. **Do nothing**, **Create a change notice** (the default), or **Create the revision directly**. See [Releases](#releases).</Field>
  <Field name="Allow syncing unreleased versions">Under **Onshape v2**, off by default, so the pickers offer released revisions only. On, you also get **"Import an unreleased version"**. See [Unreleased versions](#unreleased-versions).</Field>
  <Field name="Webhook signing secret">Optional, under **Security**, and it applies to both pipelines. Your Onshape company's webhook signing key. Set it and Carbon rejects any inbound webhook that does not verify against it.</Field>
</FieldTable>

Carbon registers one Onshape webhook, and that single subscription feeds whichever pipeline is selected. One
consumer being on is enough to receive release webhooks; the subscription is removed only once they are all
off.

<Callout type="warn" title="A read-only connection can't run any of this.">
Registering the webhook is itself a write, so a connection authorized before Carbon asked for write access
cannot sync anything. Refreshing a token can't widen its scope. On the legacy pipeline, enabling either
setting on such a connection turns it back off and tells you to reconnect, rather than saving a switch that
is on but does nothing. On v2 the save keeps your settings and reports that the release webhook could not be
registered.
</Callout>

<Callout type="note" title="Leaving the signing secret blank accepts unsigned webhooks.">
This is the default and matches how the integration has always behaved: the callback URL plus the
active-integration check are what protect the endpoint. Set the secret and every delivery must carry a valid
signature. Carbon accepts either of your Onshape company's signing keys, so rotating one is not a cutover, and
rejects a delivery whose timestamp is more than five minutes old. The keys are company-level in Onshape, so
rotating one affects everything else consuming that Onshape company's webhooks.
</Callout>

## Working from Onshape

On the **Onshape v2** pipeline, three places in the app reach into Onshape, and each one writes the link.

| Where | What it does |
| --- | --- |
| **"From Onshape"** on the parts list | Creates a Carbon part from a released revision. Onshape supplies the number, revision and name; you choose <Term id="replenishment-system">replenishment</Term> and tracking, because those are business decisions no CAD file states. The 3D model follows on its own. |
| **"Link to Onshape"** on a part's menu | Points a part you already have at an Onshape revision. This is how you adopt hand-built parts, and everything the legacy pipeline left unlinked. |
| **"Import from Onshape"** on a bill of materials | Reads a released assembly and writes it into that part's method. |

<Callout type="warn" title="Linking replaces what Onshape owns, and only that.">
The item's name is replaced immediately, its bill of materials on the next import. Everything Onshape does not
have is kept: routing and operations, costing, planning, tracking type, unit of measure, supplier parts,
posting groups and tags. If the two numbers differ, Carbon keeps its own and tells you so. The link is the
join from then on, not the number.
</Callout>

## Importing a bill of materials

Pick a released assembly, read the preview, confirm. Nothing is written until you confirm, and every line is
resolved through the link rather than by part number.

The preview labels each line with what the import will do to it.

| Label | What happens |
| --- | --- |
| **Update** | The line is linked at this exact revision. Its quantity and position are refreshed. |
| **New part** | Carbon has never seen this CAD part. It is created and linked. |
| **Revision missing** | Carbon has the part but not at this revision. Skipped — new revisions arrive through a release, not through an import. |
| **Ambiguous** | Two Carbon items claim this part at this revision. Skipped for a person to resolve. |

The preview counts separately any Onshape rows that cannot be imported at all: a line with no part number, or
one sitting under a line that has none. Give them a part number in Onshape to include them.

A skipped line is left alone, never deleted — whatever the Carbon method already held for it survives the
import untouched. The import pulls the 3D model for the assembly and for every part it resolved in the same
run. There is no separate asset sync to enable and no setting to turn it off: if you asked for the bill of
materials, you get the geometry that goes with it. When anything needs attention, Carbon notifies whoever started the import, naming the parts and
the reason.

<Callout type="note" title="A subassembly is created as something you make.">
A row that arrives with its own parts is created as **Make** / <Term id="make-to-order">Make to Order</Term>, because the import is about to give it a
bill of materials; a row with no children is created as **Buy** / <Term id="pull-from-inventory">Pull from Inventory</Term>. For a part Carbon already
has, replenishment is your decision and stays yours: if it gains a bill of materials but is still set to Buy,
the import says so rather than changing it, since planning would otherwise raise a purchase order for
something Carbon now knows how to build.
</Callout>

<Callout type="warn" title="Onshape imports into a draft, and only a draft.">
The target method must be **"Draft"**, and not one an open <Term id="change-order">change notice</Term> owns. Create a new version to import
into when it is not. An item whose revision is in **"Production"** is refused outright while the company
enforces PLM release control; raise a change notice instead.
</Callout>

### Unreleased versions

With **Allow syncing unreleased versions** on, a second button appears: **"Import an unreleased version"**. It
walks you through document, then version, then assembly, because an unreleased version is not listed
company-wide the way a release is. Onshape stamps a revision only on release, so what you pick can land only
on an item's initial revision, and a part Carbon already holds at a named revision is skipped. Models are
still exported. Prefer a released revision wherever there is one.

## Releases

Releasing in Onshape is what creates the matching revision in Carbon. Both pipelines offer the same two
outcomes, on **How a release lands** for legacy and **When a revision is released** for v2, and v2 adds
**Do nothing** for companies that want the models without the engineering change.

| Mode | What Carbon does | Review step |
| --- | --- | --- |
| **Create a change notice** (default) | Opens one **"Draft"** [change notice](/docs/reference/change-orders) per Onshape release, pre-populated with the released parts | Yes. Nothing changes on the live item until someone releases the notice |
| **Create the revision directly** | Creates the new item revision immediately and active, copying the previous revision's attributes and bill of materials | No. There is no notice and nothing to approve |

### What a release produces

An Onshape release arrives as one event per released element, and Carbon groups them back together, so a
release of nine parts becomes **one** change notice with nine affected items, not nine notices. Each affected
item carries change type **Revision** at the revision letter Onshape assigned, so `A` in Onshape is revision
`A` in Carbon rather than whatever Carbon's own numbering would have picked next. See
[Change types](/docs/reference/change-orders/change-types) for what a Revision creates on release.

The notice opens in **"Draft"**, named after the release, assigned to the user who last saved the Onshape
integration so it lands in a real person's queue, and carries the Onshape document, version, and element in
**Reason for Change**. From there it is an ordinary change notice: a human walks it through **"Start"**,
**"Engineering Complete"**, **"Implementation"**, and releases it. Read
[Lifecycle & release](/docs/reference/change-orders/lifecycle) for what release applies.

Re-releasing a revision Carbon already holds is skipped, so a redelivered webhook or a repeated release can't
duplicate a revision. If someone already has an open change notice on the same part, the import adds its own
alongside it. Carbon allows parallel notices on one part, so review both before releasing either.

### What a release skips

<Callout type="warn" title="A release never invents a part Carbon has not seen.">
On **Onshape v2**, a release is applied to the item linked to that Onshape part. If nothing is linked, the
release is reported and skipped: create the part with **"From Onshape"**, or import the assembly it belongs
to, and release it again. The legacy pipeline refuses the same case for the same reason — a part minted from a
webhook would land on Carbon's defaults for tracking and replenishment and mislead planning.
</Callout>

<Callout type="warn" title="A released drawing is not a part.">
Onshape releases a drawing as its own element sharing the number of the model it documents. On **Onshape v2**
the drawing is skipped rather than guessed at, so a released drawing produces no item, no change notice line
and no attachment. On legacy it is kept off the change notice for the same reason, and its PDF still reaches
the item through asset sync. Either way, read a notice as the release's engineering changes, not as a complete
manifest of what was released.
</Callout>
